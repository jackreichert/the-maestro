# the-maestro

An agent skill that turns the session at the root of a multi-repo directory into a dispatcher. It routes work to background agents, never blocks the prompt, and keeps a ledger so "what did we get done today?" is already written down.

## Executive summary

**What it is.** the-maestro is a skill for AI coding agents (Claude Code, Codex, Copilot, or anything that loads `SKILL.md` skills). You run it from a **container directory**, the parent of your repos, not from inside one of them. The agent there does not implement features. It resolves which repo a request is about, writes a self-contained brief, hands the work to a background agent, and goes back to the prompt. Alongside the skill is a set of small, dependency-free Node scripts that hold the parts that must be exact: the ledger, the PR board, the watchers, the PR size gate, the branch sweep and the cost metrics.

**Who it is for.** Anyone who works across several repositories with agents and is tired of three things: a prompt that is busy whenever an agent is, a day's work nobody wrote down, and agents that quietly commit to the wrong branch or open oversized pull requests.

**The problem it solves.** One long agent session does everything in sequence, re-reads its whole history on every turn, forgets what it was doing after a compaction, and has no record of what finished. the-maestro splits the roles: a thin dispatcher with a durable record, and disposable workers with narrow briefs.

**Eight core ideas.**

- **Dispatch, don't do.** Anything beyond a quick lookup goes to a subagent. Reads go to a scout first, writes to a worker, each with a brief that carries its own scope, verify command and guardrails.
- **Never block.** After launching an agent the dispatcher ends its turn. It does not poll, sleep or read a transcript. Completion arrives as a notification, and a new message mid-flight is additive, not an interrupt.
- **One writer per repo.** Two agents editing one checkout corrupt each other's work. Worktrees are for repos that are genuinely busy, and an optional claim lock makes the rule visible across sessions.
- **The ledger.** An append-only JSONL log (`journal.ts`) records what started, finished, blocked and is waiting on you. A board, a standup, a status footer, a handoff note and a search index are all generated from it.
- **Tickets.** Problems that should outlive the conversation become tickets in a separate skill ([xenophon](https://github.com/jackreichert/xenophon)); the ledger links to them instead of copying them.
- **Reviews.** The maestro works well with [mithril](https://github.com/jackreichert/mithril), a code-review skill with specialist review agents. It plugs in at three places: the preflight a worker runs on its diff before handing back, the recorded smells run that `pr-open.ts` requires in repos listed in `pr_smells_repos`, and the first pass on a teammate's PR. Without mithril the maestro still works; those steps are skipped.
- **The event loop.** One loop watches everything you would otherwise poll (CI, a run, review activity, new messages, a reminder time) and wakes a cheap runner only on a change that matters, so waiting costs one wake per event.
- **The Podium.** A local web page (and a Markdown twin) over the ledger: what needs you, what is in flight, your open PRs, and drafted GitHub comments waiting for your approval. You answer asks and reorder priorities there, and nothing reaches GitHub until you press a button.
- **The library.** Agents record each fact they establish, with evidence. A composer pass turns those into short, checked pages that the next agent reads before it re-derives anything.

```mermaid
flowchart LR
    You([You]) --> O[Orchestrator<br/>at the container root]
    O -- "brief and dispatch" --> A[Background agents<br/>one writer per repo]
    A -- "completion notification" --> O
    A -- "learned, agent-retro" --> L
    L -- "composer" --> LIB[(Library pages)]
    O -- "journal.ts start, done, ask" --> L[(Ledger<br/>ledger.jsonl)]
    L --> B[Generated board:<br/>CURRENT.md, standup, footer]
    L --> P[Podium<br/>web page and Markdown]
    P -- "answers and priorities" --> L
    O -- "xenophon" --> T[(Tickets)]
    S[Supervisor<br/>launchd, optional] --> E[Event loop<br/>watches and inbox]
    E -- "events wait, exit 10" --> O
    E -- "refresh" --> P
```

## Quick start

You need Node.js 24 or newer (nothing is installed to run the scripts: they use only `node:` built-ins, and Node strips the types from the `.ts` modules itself; `ledger-index.ts` needs a Node build whose `node:sqlite` includes FTS5), an [Obsidian](https://obsidian.md) vault or any folder you are willing to treat as one, and an agent harness that loads `SKILL.md` skills.

```bash
# 1. One copy, where your agent already loads skills. Symlink other harnesses to it; never clone twice.
mkdir -p ~/.claude/skills
git clone https://github.com/jackreichert/the-maestro ~/.claude/skills/the-maestro
mkdir -p ~/.agents/skills && ln -s ~/.claude/skills/the-maestro ~/.agents/skills/the-maestro

# 2. Tell the scripts where the ledger lives (a real folder you choose; there is no default and no guessing).
export VAULT_ROOT="/absolute/path/to/your/vault"

# 3. Smoke test. --project is the name of your container folder and is required unless your config sets `project`.
node ~/.claude/skills/the-maestro/scripts/journal.ts status --project my-workspace
```

`status` only reads, so on a new vault it prints an empty ledger; the first entry you log (below) creates `$VAULT_ROOT/Projects/my-workspace/Journal/`. If it says the vault path is not set, the agent process did not inherit `VAULT_ROOT`: fix your shell profile or pass `--vault <path>` on that command.

Then open an agent session **in the container directory** and ask it to orchestrate something small. If the skill does not load, the harness is not reading that skills directory: check the product's skill path and add another symlink.

Log some work by hand to see the ledger:

```bash
J=~/.claude/skills/the-maestro/scripts/journal.ts
M=(--project my-workspace --model "Some Model" --used "skill:the-maestro,tool:journal.ts")
node $J start "Port the calendar fix" --repo billing-api "${M[@]}"
node $J done "Port the calendar fix" "${M[@]}"
node $J status --project my-workspace
```

Every new ledger entry needs `--model` and `--used`, so the record says which model did the work with what. Unknown history is `unrecorded`, unmeasured tokens are `unmeasured`; do not invent either.

Decide whether the skill keeps itself current. Until you answer, `prime` ends its first lines with `auto_pull is not set` each session (unset is different from off, so a new install is asked once rather than silently opted out). Answer it now, or let your agent ask:

```bash
node ~/.claude/skills/the-maestro/scripts/journal.ts autopull on    # fast-forward the checkout at session start when it is clean and only behind; or: off
```

See [Updating](#updating) for what `on` does and never does.

Optional next steps: install xenophon against the same `VAULT_ROOT` for tickets, install [mithril](https://github.com/jackreichert/mithril) for code reviews, write a config file ([Configuration](#configuration)), keep the loop and the Podium running without a session ([Running it unattended](#running-it-unattended)), and set `ledger_root` if you want the day-to-day ledger outside your vault so it stays out of vault search.

## Updating

At the start of a session `journal.ts prime` fetches this skill's own checkout and says so in one line when it is behind, ahead, diverged or dirty; it is silent when the checkout is current, is not a git repository or has no upstream branch. `update_check: off` (or `--no-update-check`) skips the fetch.

Keeping the checkout current is opt-in. Until you answer, `prime` adds one more line each session: `auto_pull is not set`. Your agent asks you once and records the answer; you can also do it yourself:

```bash
node ~/.claude/skills/the-maestro/scripts/journal.ts autopull on    # or: off
```

That writes this line into the `maestro-config` block of `~/.config/the-maestro/config.md` (creating the file if needed, leaving every other line alone), or set `MAESTRO_AUTO_PULL=on` in the environment:

```
auto_pull: on
```

With `auto_pull: on`, `prime` runs `git merge --ff-only` and nothing else, and only when the checkout is clean and purely behind its upstream. It never merges, rebases or resets, and a dirty, ahead or diverged checkout is only reported. `auto_pull: off` keeps today's behaviour (report, never pull) and silences the extra line.

## Concepts

### The container directory

the-maestro runs from the directory that holds your repos. That directory is not itself a git repository, so everything that needs a project name (the ledger, tickets) takes it explicitly. The orchestrator is the only thing that runs at that level.

### How a request flows

```mermaid
flowchart TD
    U([User message]) --> G{Greeting?}
    G -- yes --> B[Greet, then the board:<br/>standup, in flight, blocked,<br/>awaiting you, shipped today]
    B --> R
    G -- no --> R[Resolve: which repo?<br/>Question or task?]

    R --> O{Repo has CONTEXT.md<br/>in the vault?}
    O -- no --> D[New-repo discovery:<br/>write CONTEXT.md]
    D --> C
    O -- yes --> C{Classify}

    C -- "already known /<br/>ledger or agent ops" --> I[Answer inline]
    C -- "needs a look at code" --> S[Stage 1: dispatch a<br/>read-only scout]
    C -- "file and change<br/>already named" --> W

    S --> ACK1[One-line ack.<br/>End the turn, never block]
    ACK1 -. completion notification .-> SR[Scout reports anchors<br/>and a recommended shape]
    SR --> Q{Is the scout's answer<br/>the deliverable?}
    Q -- yes --> REL
    Q -- no --> T

    T[File a vault ticket<br/>xenophon] --> W[Stage 2: brief and dispatch<br/>a worker, one writer per repo,<br/>guardrails in the brief]
    W --> L1[journal.ts start]
    L1 --> ACK2[One-line ack.<br/>End the turn]
    ACK2 -. completion notification .-> WR[Worker reports:<br/>commits, tests, findings]

    WR --> INC{Incidental findings?}
    INC -- yes --> TK[One ticket per problem,<br/>in the repo it lives in]
    TK --> L2
    INC -- no --> L2[journal.ts done / ask / log]
    L2 --> REL[Relay the substance:<br/>links, not bare ids]
    I --> F
    REL --> F[Close with the status footer:<br/>agents running, awaiting you]

    U2([New message mid-turn]) -. "additive, not an interrupt" .-> R
    WR -. "needs a user decision" .-> ASK[journal.ts ask<br/>goes on the awaiting-you board]
    ASK --> B
```

The dotted edges are asynchronous: the dispatcher never waits on them. A new message while agents are running is handled alongside the work already in flight.

### Scout, then worker

A read-only scout is dispatched first, so the dispatcher never greps the repos itself. When the work is real, a worker gets a brief with a write scope, a verify command and the standing rules block (`scripts/brief-block.ts` prints it). The brief fields are in [reference/brief.md](reference/brief.md), and the routing and concurrency rules are in [reference/dispatch.md](reference/dispatch.md).

### The ledger and the board

`ledger.jsonl` is the only source of truth. `CURRENT.md`, the dated archives, per-stream pages and the standup are generated from it and safe to read or edit. Items fold by id: `start` opens one, `done`, `resolve` or `drop` closes it, and `ask` puts a question on the awaiting-you board. Work can be grouped into **streams** (named workstreams, usually epics). Ids are four lowercase characters, are not ticket ids, and are always quoted with their one-liner, never bare.

### Asks have a template

An ask is a gate, not a note. `journal.ts ask` needs a one-line question, what is blocked, two or more options each with its cost (`--option "<option> -- <cost>"`), a recommendation, at least one openable link and what was checked, and it exits non-zero naming every missing field, writing nothing. The Podium shows an ask under fixed headings (Question, What is blocked, Context, Options, Recommendation, Links, What I checked) with the answer box last; asks written before the template keep a plain layout. Run-this (`--paste`) asks and two-way asks with a default are exempt. See [reference/ledger.md](reference/ledger.md).

### Tickets

A ticket is a problem with evidence, kept by [xenophon](https://github.com/jackreichert/xenophon) under `$VAULT_ROOT/Projects/<repo>/Tickets/`. A ledger line is a record that work happened, linked to the ticket by id. Closing one does not close the other. Without xenophon the maestro still dispatches and still journals; it just has nowhere durable to put a bug.

| | the-maestro | xenophon |
|---|---|---|
| Answers | What is in flight, blocked or done today? | What problem needs fixing, and what do we know? |
| Writes | `$LEDGER_ROOT/Projects/<container>/Journal/` (falls back to `$VAULT_ROOT`) | `$VAULT_ROOT/Projects/<repo>/Tickets/` |
| Id | four characters, `k3mp` | `{repo}-014` |
| Lifetime | the session and the day; `roll` archives finished lines | until you close it |

### Non-blocking waits: the event loop

Waiting on something outside the session (CI, a run, review activity, a message) is a registered **watch**, not an agent polling. One loop checks every watch, compares each with its last state and records an event only when its type says something changed. A cheap runner follows [playbooks/event-loop.md](playbooks/event-loop.md) and wakes the orchestrator only on an actionable event.

```mermaid
flowchart LR
    W[(watches.jsonl)] --> P[Check: each watch's<br/>type.check]
    P --> D{Diff against the<br/>stored state}
    D -- "no change" --> S[Sleep, adaptive pace] --> P
    D -- "info event" --> G[(digest.jsonl)] --> S
    D -- "actionable event" --> G
    G --> X[run exits 10 with the digest]
    X --> K[Runner wakes the orchestrator]
    P -. "quiet hours" .-> Q[Exit 3, or only<br/>notify-overnight watches run]
```

### PRs: draft only, sized, linked

In repos listed in `review_note_repos`, a push needs a vault Reviews note for the head commit with a filled Naming pass (and the org's reviewer checklist when one is configured); `review-note.ts push`, `pr-open.ts` and the git-guard hook enforce it, and reviewer briefs treat naming as a finding rather than a nitpick. A reviewer guide's skim-safe label is for human reviewers only.

Pull requests open as drafts, assigned to you, through `pr-open.ts`, which checks the body and runs the size gate; a PR is done only when its `gates` and `test` checks are green on GitHub. Every PR body carries Context, Reviewer guide, Risk and blast radius, Rollback / flag and How to verify locally sections, plus a small mermaid diagram when the PR is stacked or wide, a Stack section naming the base PR when it is stacked, and a Review order line in the Reviewer guide once it passes a few code files (Evidence and Questions for reviewers are advisory), all written in the author's own voice and free of private-workspace references and of commit, file or line counts the page already shows; `pr-open.ts` refuses without them (`n/a, <reason>` is allowed, a bare placeholder is not). It checks structure, not truth: the risk line format, a fenced verify command and secret or attribution-shaped content are machine-checked, while whether the risk is honest or the review order is best stays a reviewer's call. `{{file:path}}` tokens in the body (optionally with a line range, `{{file:path#R25-R31}}`) become links to that file in the PR's Files changed tab once the PR exists (`pr-guide-links.ts` backfills an open PR). In repos named in `pr_smells_repos` it also refuses until a report-only smells review is recorded for the head commit (`pr-smells.ts record --repo <repo> --summary "..."`) and its `Smells:` line is in the body; docs-only diffs are exempt ([details](reference/git.md#smells-gate)). The template, the enforced-versus-advisory table and the settings are in [reference/git.md](reference/git.md#pr-body). It also enforces one PR per ticket: when another open PR in the repo carries the same ticket key in its branch or title, `pr-open.ts` refuses (a develop PR and its staging twin, and release PRs, count as one; a stack passes with a warning, and a smaller ticket is preferred for a separate unit of work), so oversized work is split into smaller tickets rather than fanned into several PRs ([details](reference/git.md#one-pr-per-ticket)). In repos that promote work through an integration branch and then a release-candidate branch, both PRs open together and the release-candidate twin waits for the integration twin. In this repo, and in any repo named in `leak_gate_repos`, `pr-open.ts` also refuses a PR that adds an org term, a personal absolute path, a person's name or a configured customer name, and the `gates` workflow fails the same PR in CI (`pr-leaks.ts`; set the `LEAK_TERMS` secret there, since the name list is never committed). Reviewers always check the diff for customer names and client-identifying references.

```mermaid
flowchart LR
    F[Feature branch] --> PD[Draft PR into the<br/>integration branch]
    F --> PS[Draft twin PR into the<br/>release-candidate branch]
    PD -- "merged and validated" --> OK[Twin may be promoted and merged]
    PS -. "blocked until then" .-> OK
```

The twin rule applies only to repos named in `twin_flow_repos`; an empty list turns it off. The PR board shows each twin as "develop twin merged, OK to merge" or "blocked on develop twin #N" and never calls a blocked one ready. The Podium's Open PRs tab applies the same rule to any repo that has both a `develop` and a `staging` branch: a staging PR stays out of the Ready band while its develop twin (an open or merged PR on the same head branch, or one differing only by a `-staging` or `-develop` suffix) is unmerged or cannot be found, and its row says which twin it waits on. The branch check and the merged twins are read once per refresh and cached, never on a page load.

### The scripts shelf

Agents write throwaway scripts all day, and a script written into `/tmp` is written again tomorrow. An optional shelf (off until `scripts_dir` is set) gives them one place to look first and one place to leave work.

```mermaid
flowchart LR
    A[scratch/<br/>one-offs, 3-line header] -- "named in 2+ ledger rows,<br/>idle 3+ days: promote" --> B[helpers/<br/>--help, idempotent,<br/>read-only unless named otherwise]
    B -- "a cheap model should run it" --> C[playbooks/<br/>steps, exit codes,<br/>what to report]
    A -- "idle over 14 days:<br/>delete-candidate" --> X[you decide]
```

Prod-check scripts (anything that reads a live system by name: a location, job or sensor) take those identifiers from a known-good sibling script or from the real UI or URL, never from assumption. When a lookup matches nothing, the script prints what does exist and exits non-zero. A fixture the same agent wrote does not validate a name, because it will contain whatever the agent assumed. The brief's scripts line carries this rule.

`journal.ts roll` (and `journal.ts scratch`) only proposes: it never moves, edits or deletes a file.

### Picking work, and what comes back

The user's ranked priorities live in `priorities.md` in the status directory and can be reordered by hand at any time, so the orchestrator reads them fresh (`journal.ts priorities show`) before every pick. When a slot frees it takes the top unblocked item of the highest-ranked stream and states the pick in one line; streams not on the list wait unless named. Before any agent goes out it checks the work is still live: the PR is still open, the ticket is not superseded or done, no user-only decision is outstanding, no agent holds the repo, and the item is sized to a draft. Failures go back to the queue with a note. Every agent writes its full report to a file and hands back a headline paragraph (under 150 words) plus the path, so the orchestrator relays the headline and the detail stays out of its context. The review queue cap gates only the push of a finished branch as a draft PR, never dispatch: while the queue is full the work keeps being built, tested and reviewed locally, finished branches are held as ready to push with their head sha in the ledger, and they are pushed when a slot opens. Repos the user reviews alone (`self_review_repos`) sit outside the cap and are listed as their own section in the PR digest, `status` and the Podium. Details: [reference/dispatch.md](reference/dispatch.md#picking-the-next-item).

### Bolero: working a queue until it is done

Bolero is the mode for handing the orchestrator a whole queue of tickets and having it loop until the queue is done. A read-only scout sizes the queue, the orchestrator groups it into lanes, and each lane gets one writer in its own git worktree. Each time an agent reports, the orchestrator relays the headline, logs it, merges the finished branch on a local integration branch only when that stream has a standing approval to merge locally, runs the full suite, and dispatches the next slice. It stops only when completely blocked: a decision only the user can make, failing tests nobody can explain, or an external dependency. The name is the musical form, one short theme repeated with voices added each pass. The procedure, a lanes-plan template and a stop checklist are in [bolero/SKILL.md](bolero/SKILL.md).

Getting the user's open PRs to mergeable is the orchestrator's own job: it fixes review threads and blockers, merges the base in to clear conflicts only where the user has granted that as a standing approval (otherwise it is one ask on the board), has a fresh agent re-review each fix (verified by running it, with PR state read live), and re-pushes until the PR is mergeable. Merging, undrafting, approving, rebasing, force-pushing, protected branches, secrets and external sends stay the user's ([reference/prs.md](reference/prs.md#unblocking-your-own-prs-is-autonomous)).

Context cost is managed two ways. Agents write full reports to files and hand back a few lines plus the path, and long standing rules live in files a brief points at. For the orchestrator itself, compaction is the rollover (a hook cannot open a fresh session), so every decision is logged to the ledger the same turn and the `SessionStart` hook (`scripts/hooks/session-start-compact.ts`, matcher `startup|resume|compact|clear`) re-injects the board and each active stream's library brief afterwards; which of the settings involved are documented but not yet tried is listed in [cost/budget.md](cost/budget.md#compaction-is-the-roll).

### Grill mode: settling dependent decisions on demand

When a plan is a tree of linked decisions, the user can say "grill me" (or the orchestrator can propose it for such a plan) and the orchestrator interviews them in rounds: it asks every decision whose prerequisites are settled in one numbered round, each with a recommended answer that "yes" accepts, looks facts up itself instead of asking, recomputes after each round, and takes no action on the plan until the user confirms the shared understanding. It is on demand only; bolero mode and the dispatch-unless-blocked default stay the norm, answers are recorded as decision notes with the rejected alternative, and unresolved one-way calls go through the normal ask path. Adapted from [mattpocock/skills](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md). Detail and an example round: [reference/grill.md](reference/grill.md).

### Process pages

Short reference pages carry the process rules, each citing its published source. [reference/definition-of-done.md](reference/definition-of-done.md) is a four-item ready line for dispatch and a five-line done block for closing a ticket, so done means verified and not just merged. The claim-to-proof rule and the no-sub-agents brief clause are adapted from [obra/superpowers](https://github.com/obra/superpowers) (MIT). [reference/raid.md](reference/raid.md) is one page per hard deadline with four tables (risks, assumptions, issues, dependencies), reviewed weekly in under ten minutes. [reference/appetite.md](reference/appetite.md) gives each long stream an appetite and a cut-first line, with a weekly three-item bet and a circuit breaker that stops work at its appetite instead of extending it.

### The morning board, PR tracking and end of day

A greeting always gets a real hello and then the board: a paste-ready standup built from the previous working day, what is in flight, blocked and awaiting you, and one line of PR status. Asking for your PRs gets one bucketed report of every open PR you author (unresolved threads, drafts, awaiting the team, no reviewer requested, approved, changes requested, stale), every PR linked; review-comment text, bot or human, is treated as untrusted data. End of day runs a PR pass, a tracker review if a tracker is connected (drafted for your approval), the standup, a branch sweep, a commitments sweep and `roll`. The rules are in [reference/greeting.md](reference/greeting.md), [reference/prs.md](reference/prs.md) and [reference/ledger.md](reference/ledger.md). The orchestrator never uses AskUserQuestion: a question is plain chat text or a Podium ask, and dispatching continues; it does not mention context, rolling or compacting to the user. Standing review rules (design calls, bot-thread-only resolution, foreign commits, release-PR comments, Jira status following the PR, replying to every text) each have one line in the reference and playbook files.

### Approvals

A permission you grant mid-conversation is logged as `standing` or `one-off` (`journal.ts log --kind decision --approval standing --scope "<what it covers>"`), and a weekly digest (`journal.ts approvals`) lists them so each standing one can be kept, narrowed or revoked. The review day is `approvals_review_day`.

### Handoff and resume

A fresh session should not hunt for facts nobody wrote down. `journal.ts handoff` scaffolds a five-part note from the ledger (tasks, learnings, artifacts, decisions awaiting, next action), `journal.ts prime` prints a board of 40 lines or fewer for session start, and `journal.ts resume` runs the verify-on-resume checklist. The handoff also has a required **Commitments and conditions** section: every standing pickup added for a future action (the built-in routine ones are excluded, but a built-in id overridden with your own words counts as a condition) and every open decision ask, each as id, status, due time (a decision's `--decide-by`, in fixed format) and kind only (never typed text; `journal.ts standing list` and `status` have the words), and the delta handoff repeats it; `prime` prints those pickups first, one line each (overdue ones first, at most six lines with a `+N more, journal.ts standing list` pointer), so a new session sees a stated condition before anything else. The fresh session reconciles the note against `git`, `gh` and its agent list before trusting it. A fresh session reads the Podium's front page (`journal.ts start-here`, then `start-here --stream <Stream>` for one stream's tab) before the ledger board, and [playbooks/podium-fresh-context.md](playbooks/podium-fresh-context.md) is the ten-question eval that checks a cheap, fresh agent can answer from the Podium alone.

**Two windows on one ledger.** Every ledger row, event mark and handoff names the window that wrote it, so two orchestrator windows can share a ledger and still be told apart; the one exception is the Podium web writer, which stores its rows with no window. The window id is `--window <id>`, else the session id (`--session <id>`), else `MAESTRO_WINDOW` (an override a hook or shell can set), else `CLAUDE_CODE_SESSION_ID`, else `c<CLAUDE_PID>`, else `p<parent pid>`. Claude Code exports `CLAUDE_CODE_SESSION_ID` and `CLAUDE_PID` into every Bash tool call and hook of a session, so every separate `journal.ts` process of one window resolves the same id with no setup and nothing is stored on disk; two windows never share one. Only the last fallback, the parent shell, is unstable (each Bash tool call is a new shell, so the same window gets a new `p<pid>` per call): when it is the one in use, `prime` and the text form of `status` print a `Window id ... is UNSTABLE` line saying to export `MAESTRO_WINDOW`. A window that runs `/clear` may get a new session id; treat the id as the id of that session. Leases and event routing (below) build on this id. The id is cut to 12 letters, digits, `_` and `-`, so no free text reaches a row. Rows written before this have no `window` and read as before. `status --footer` adds a `**Window:**` line (and `Window: <id>` in the `--line` form) naming the window of the session it measures, and only when that session is pinned (`--session <id>`, `--stdin`, or `CLAUDE_CODE_SESSION_ID` naming a transcript); with no pinned session it measures the newest transcript, which may belong to another window, so no window is named. `events wait` and `events ack` record the window on the `seen` and `handled` rows they write; `seen` is per window (see **Routed events** below). **Window-scoped rules.** A rule or note given in one window must not bind the others, so `rule`, `note` and `log --kind decision|note` take `--scope window|global`, and `decide` takes `--binds window|global` (its `--scope` already names where the decision is written). `decide --binds window` is the command for an instruction such as "pause X here today": it writes one row for this window and no file; `--binds global` writes the file as usual and marks the row global. `window` stores `ruleScope: window` beside the row's `window`; `global` stores `ruleScope: global`; a row with no `ruleScope` (everything written before this) reads as global. `prime` and the text `status` list the scoped rules that bind the running window (its own window-scoped rules plus the global ones, newest five) and add one FYI line counting other windows' window-scoped rules, whose text never appears; `status --footer` adds a `**Rules:**` count line the same way. Rows with no scope are not listed there. With `--approval`, `--scope` keeps its older meaning, the approval's own scope text. A rule stops binding when it is lifted (`drop <id>` or `resolve <id>` on the rule's id, which also removes it from other windows' FYI count), and a window-scoped rule also expires 24 hours after its window last wrote a row; global rules never expire. The brief block tells agents to use `decide --binds window` (or `--scope window`) when relaying an instruction the user gave in one conversation. `--scope window` and `--binds window` are refused when the window id is unstable (see above), since the rule could never be matched again; another window's scoped rules are also kept out of `triage` (and so `triage --apply`), `standup` and `status --full`. A handoff is created exclusively: the note is written to a temp file and hard-linked into place, so it appears whole or not at all and two windows rolling at once never overwrite each other. When a name was taken by another window the roll writes the next free suffix (`b` to `z`) and says which names it skipped; `--force` and `--out` keep their meaning (`--force` overwrites on purpose, `--out` refuses a path that exists).

**Leases: two windows, one item.** A window that starts or briefs an item takes a lease on it, so another window working the same project is refused instead of starting it too. A lease is two kinds of ledger row (`lease`, `unlease`) folded in file order, so the ledger stays the only store and nothing sits on disk beside it. Ledger appends are ordered by the operating system, so when several windows race for one item the earliest lease row wins and every later reader folds to the same holder; a window that wrote a losing row re-reads, finds it is not the holder, writes nothing more and exits 1. The refusal reads `<id> is leased by <window> until <time>` and names the escape: wait, work another item, or pass `--steal <window>`. A steal names the window it takes the lease from: `--steal <window>` is refused (exit 1, nothing written) unless that window holds the lease when the row is appended and again when the ledger is re-read afterwards, and the steal row records it as `from`, which the fold honours only while that window still holds the lease. So when several windows steal from the holder they all observed, the first row wins and every other exits 1, however their reads and appends interleave. A bare `--steal` reads the current holder once and then names it, so it is only as safe as that read: a bare stealer that starts after another steal has landed sees the new holder and legitimately steals from it. Name the window when more than one window may be stealing. A lease lasts `lease_ttl_minutes` (default 60) from the holder's last row; any row the holder writes renews it, so a window that is working keeps its leases and one that died, or whose id changed at `/clear`, lets them lapse without anyone cleaning up. `done`, `drop` and `resolve` end the lease, and `release <id>` frees it early (`--force` for another window's; `--force --from <window>` frees it only while that window still holds it, so a force never frees a lease stolen after it read, and a bare `--force` names the holder it read). A lease is advisory about starting work: it stops a second `start` or `brief`, and it does not stop a window that writes rows to the item some other way. `status --json` adds a `leases` object (this window, how many live leases it holds and how many other windows hold, and each held item with its holder and expiry), text `status` lists them, and the footer adds a `Leases: N mine, M other` part whenever any live lease is held, this window's own included, and leaves it out only when none is.

**Routed events: an event goes to the window that owns its stream.** With two windows on one ledger, an event used to go to whichever window waited first. Now `events wait` hands a window only the events it owns, and nothing sits beside the leases to say who that is. An event names a repo; the window that holds a live lease on an open item of that repo (the item's own `repo`, or any item of the stream the `status_repo_streams` setting maps the repo to) owns the event, and if several windows qualify the one whose lease runs longest does, ties going to the lower window id, so every window computes the same owner from the same ledger. An event nobody owns (no repo, no live lease, no ledger root configured, or the owner's lease lapsed) goes to the first window that takes it, and a lapsed owner's events therefore fall to the other windows instead of waiting for a window that is gone. `wait` marks what it takes as seen first and then re-reads the inbox: of two windows that both read an unowned event as free, only the one whose `seen` row comes first in the file keeps it, so none is printed twice. Callers that share one window id (the event-inject hook and a background `events wait` in the same session) are told apart by a claim file: each takes an event by exclusively creating `<event dir>/claims/<hash of window and event id>`, so exactly one of them delivers it, owned or not. `seen` is per window: each `seen` row names its window, an event is offered to a window once, and one window's mark never hides an event from another (a mark written before windows were recorded counts for all of them). Nothing is hidden from `events list`, which shows every unhandled event to every window, so a window that took an event and died before acting, or a window starting up, still finds it there; `--json` adds `seenWindows` and, where a window owns the event now, `owner`, and `--unseen` means unseen by this window. Because `wait` marks before it prints, an event it took is not offered again even if the process dies mid-print; `events list` is the way back to it. A window that is only waiting writes no ledger rows, so its leases lapse after `lease_ttl_minutes` like any other idle window's; a window that expects a long wait can renew with `lease <id>`. If a lease changes hands in the moment between two windows' reads, an event can reach both: delivery is at least once, never zero.

### The Podium

The Podium is the board you glance at. `journal.ts web` serves it as a local page bound to `127.0.0.1` (the URL is printed), and `journal.ts podium` writes the same board as one Markdown note. Both are built from the ledger, the cached PR list and the priorities file, and a `status-refresh` watch keeps them current. The tabs are **Home** (streams over the last 14 days, what needs you, what is blocked or in flight, shipped today, cost), **Open PRs**, **Others' PRs**, **Scripts** (the commands you are blocked on, then a catalog the Podium can run), then one tab per stream, ordered by today's priorities. A stream tab adds that stream's epics, what is left, and a link to its library.

The page can write in seven places, each behind a per-start token, a same-origin check and an exact request shape: today's priorities (add, reorder, delete), an answer to an ask, a comment on a blocked item (which can unblock it), the Approve, Edit and Reject buttons on drafted GitHub comments, the Open PRs Refresh button, Run on a reviewed command ([details](#running-a-reviewed-command)), and "Mark done (I ran it)" on a script you are blocked on ([details](#scripts-you-are-blocked-on)). Everything else is read-only, and GitHub is called only by Approve and Refresh. Endpoints, guards and the design system are under [web.ts](#webts).

For a little delight, every minute or two a small line-art music character (a walking eighth note, a waddling metronome, a baton leading a parade of notes, a cello on wheels, a dancing treble clef, a self-drumming drum, a piano-key caterpillar, a rolling record) walks in from one page edge, crosses behind the content in soft pastel strokes, and leaves by the other. It is decoration only: it takes no clicks, takes no space, is hidden from screen readers, stays still under reduced motion and in a background tab, and a small music-note toggle in the corner switches it off for good (remembered in the browser). `?walker=<note|metronome|baton|cello|clef|drum|keys|record>` repeats one walker for previewing.

Home is set as a score, after a design concept, and wears its names (it is ordered by what needs acting on, not by when each part was built: Cues first, then open work, open PRs and what is blocked, then the score, Movements, Coda, the deck and Brass; the rule is in [docs/design.md](docs/design.md), and every tab shares one 12-column grid of full, half and third widths): a title page (the baton, the wordmark, the freshness pill and a Refresh button that reads "da capo"), a sticky tab row with a stream picker ("Voice": a listbox with each stream's colour and cue count, "tacet" for none; arrows, Home, End, type-ahead, Enter and Escape work), the cue line (a tempo word such as Allegro with a one-line gloss, then the counts), then **Strings / The score** (a staff per stream), **Woodwinds / Cues** (each ask marked with a rehearsal letter A, B, C and so on, over the real answer card), **Held / Fermata** (blocked), **Shipped today / Coda**, **Underway / In flight**, **Movements / Epics** (a roman numeral and a row of measures per epic: a filled note is a task done, a hollow one in progress), **Rehearsal** (local review), **Percussion / The deck** (shipped above the line, asked below), **Brass / Cost** (each metric with a dynamics mark, pp to ff, from its 7-day change; the day's tempo, a pendulum that swings right as the day's shipped work fills toward twice its 7-day median, counting finished work items and not merged PRs separately; a daily-limit gauge in words, such as "Tokens read per turn: 417k, limit 200k"; and the model mix as a ring with each goal as a tick and in words. When the newest measurement is not from today or yesterday the section is muted, says "Last measured <date>" and shows no live-looking percentage; the daily table is written by `node scripts/token-metrics.ts --write`) and **Continuo / Open work**. Every section is wired to the real data it names; where nothing exists it says so in the same style ("tacet", "No limit set") rather than disappearing.

Home also moves a little. When it opens (and when you come back to it from another tab) the score's notes drop onto their staves, cues and shipped rows rise, and the bars fill from the left, in about half a second; the playhead sweeps the staves once and a refresh sweeps it again. A task that ships while the page is open lands with a small spring, and an answered cue sends a note flying to the coda. Nothing loops: the baton's tip pulses three times when the number of asks that need you changes and then rests, and an occasional glyph stirs on its own for at most five half-second beats per page load (and not while you type or a menu is open or the tab is hidden). With `prefers-reduced-motion: reduce` none of it runs. Only transform and opacity change. The rules live in `scripts/web/client/src/home-motion.ts` and `home-ambience.ts`.

Home keeps the local review queue to a compact Rehearsal section: the count of branches with commits nobody has pushed, the top three (repo, branch, verdict, age), each with a Review button that opens the Open PRs tab, where the full list sits under its own "Waiting for local review" heading with the diff commands. Both views read the one `/api/local-review` payload the page already loads, so there is no second fetch.

### Reviewing PRs, and what the Podium holds back

`pr-state.ts` reads a PR's real state (reviewer verdicts, unresolved threads, checks, mergeability) instead of trusting `reviewDecision`, and `prs-snapshot.ts` builds the bucketed PR board from it. A fresh agent re-reviews a fix and records SHIP IT or NEEDS WORK for the exact head commit (`review-verdict.ts`); a PR with resolved bot threads is held until one exists. `merge-sweep.ts` closes ledger rows whose PRs merged. If [mithril](https://github.com/jackreichert/mithril) is installed, its review agents do the reviewing here.

Comments that would be posted as you do not post themselves. When a teammate's ready PR has waited past `teammate_review_minutes`, the [teammate review playbook](playbooks/teammate-review.md) checks it out read-only, runs a first pass, and `teammate-review.ts submit` queues one review draft under a lenient bar (only a stated-input correctness bug, a listed security class or a deploy that cannot roll back blocks). For your own PRs, `reply-drafts.ts` sorts unresolved threads: a thread with a person in it becomes a draft, and a thread with only bots in it is answered directly. The queue is `drafts.jsonl` beside the ledger; the Others' PRs and Open PRs tabs show it, and only the Approve button reaches `gh`. Details are under [web.ts](#webts) ([drafted comments](#drafted-comments-approve-edit-reject), [teammate review](#reviewing-a-teammates-pr-that-has-waited), [replies](#replies-to-comments-on-your-own-prs)).

### The library and agent retros

Facts that took effort to establish should not be re-derived. An agent records one with `journal.ts learned` (claim, evidence, `verified-at`, confidence; secret-shaped text is refused), and a question the library could not answer with `journal.ts miss` (`find` writes one itself when nothing matches). Before an agent closes a briefed item it writes an `agent-retro` of what it learned (`done` refuses without one, or `--no-retro "<why>"`). The `library-due` and `retro-due` event types report when learned rows, misses and retros are waiting, and the orchestrator then dispatches the composer ([playbooks/composer.md](playbooks/composer.md)) or the retro review ([playbooks/retro-review.md](playbooks/retro-review.md)).

The composer is the only writer of library pages, and only through `library-write.ts` (a lock, the same checks as `library-check.ts`, a secret and PHI scan). `library-brief.ts` puts the three best pages into a dispatch brief, and `journal.ts brief` does that for you. The page template and vocabulary are in [reference/library.md](reference/library.md).

## Running it unattended

Nothing here is required: a session can run the loop itself. For a setup that survives closed terminals, two optional macOS LaunchAgents keep the long-running pieces alive and a few hooks keep a session oriented.

```mermaid
flowchart LR
    LA1[LaunchAgent: loop supervisor] --> EL[event-loop.ts run --serve]
    LA2[LaunchAgent: Podium web] --> WEB[journal.ts web]
    EL -- "heartbeat, inbox, digests" --> D[(event_dir)]
    EL -- "status-refresh" --> PG[Podium page]
    D -- "events wait" --> S[Session]
    D -- "unseen for 3 min,<br/>nobody listening" --> W[Optional wake launcher<br/>or one fixed text]
    H[SessionStart and PreCompact hooks] --> S
```

- **Loop supervisor.** [loop-supervisor.ts](#loop-supervisorts-keep-the-loop-alive-without-a-session) runs `event-loop.ts run --serve` and relaunches it, including when its heartbeat goes stale. A session then only waits on the inbox with `event-loop.ts events wait`.
- **Podium web.** [install-podium-web.ts](#install-podium-webts-keep-the-podium-page-up-without-a-session) keeps `journal.ts web` up at a fixed port, so the footer link always answers.
- **Run from a runtime worktree.** launchd re-runs a script from the same path after every relaunch, so install from a worktree detached at the default branch, not from a checkout where a branch can move. The loop installer refuses a branch checkout unless `--allow-branch` is passed. To update the daemons, fast-forward that worktree, then `launchctl kickstart -k` each agent: the loop and the web one are separate processes, and restarting the loop does not restart the web server (rebuild the page first with `npm run build:web` for the web one). `auto_pull` keeps your own skill checkout current and does not restart anything.
- **Hooks.** You merge the entries `scripts/hooks/print-settings-snippet.ts` prints into your own settings file. They load the board at session start and after a compaction, write a handoff and a decision scan before a compaction, track leases for dispatched agents, surface unseen events, and ask before risky git commands. Every one is optional and fails open. See [Loading the board automatically](#loading-the-board-automatically) and [Rolling continuously](#rolling-continuously).
- **Text alerts and wake-ups.** `notify_command` sends a batched one-line text for a short allowlist of events when no session has seen them, and `wake_launch_command` can open a session when nobody is listening ([Text alerts](#text-alerts), [Session launcher](#session-launcher-nobody-is-listening)).
- **Health at a glance.** The `Loop:` line in the footer, `prime` and `session-start.ts` says whether the loop is running ([Loop health](#loop-health-is-it-actually-running)).

### journal.ts

The ledger tool. `journal.ts --help` (or `-h`, or `help`) lists every command with a one-line summary, and `journal.ts <command> --help` prints that command's usage and flags. Help is answered before anything else runs: it never starts the command, never needs a project or a ledger root, writes nothing and exits 0. An unknown command prints the same list and exits 1. Both come from one table in `scripts/lib/journal/help.ts`, and a test fails when the table lists a flag the code never reads. A bare `--` ends the flags, so `journal.ts log -- --help` logs the words `--help` instead of printing usage. `--project <name>` is required on every command except `autopull`, `settings` and `web`, unless the `project` config setting (or `MAESTRO_PROJECT`) names one; an explicit flag wins and there is no built-in default. Common flags: `--vault`, `--project`, `--json`, `--dry-run`, `--include-archived`. Every `--json` output goes through one shared print path (`printJson` in `scripts/lib/json-out.ts`, and the same scan inside the web Podium's `sendJson`, which exempts only the edit-token reply); a test fails on any script that hands `JSON.stringify` output to `console.log`, `console.info`, `process.stdout.write` or `writeSync(1, ...)`, on one line or several, or through a variable filled from it (a `[dry-run]` echo included; it goes through `dryRunJson`). It does not follow a wrapper helper that prints for the caller, so review has to catch that. The path applies the same secret scan as printed text: a string value or object key shaped like a secret is replaced in place by `[withheld: secret shape]`, so the output keeps its structure and still parses. The root is `--vault`, then `LEDGER_ROOT`, then `VAULT_ROOT`. Every new row needs `--model "<name>"` and `--used "skill:x,tool:y"` (`--tokens` and `--harness` are optional).

| `start-here [--stream <name>] [--json]` | The first page a fresh reader needs, as text with no web server running (80 lines at most): this week's goals, today's priorities, up next (the top five of `next`, with score and why; left out of a single stream's view), the five most urgent asks with their recorded stakes (door, decide-by, recommendation, else `no decision fields`), conditions and standing pickups, what is in flight, what happened on the previous working day, asks answered in the last two days, and per stream where its notes live (counts, from the stream home base; `Notes not read` when `vault_root` is unset). Each block ends in a `+N more` pointer to the command with the full list. `--stream` narrows every block to one stream; `--json` prints the data the text is made from |

Roll at end of day, or when the board feels crowded.

`CURRENT.md` is a slim view, small enough to read in one go at session start: today's priorities (when set), the in-flight rows, the asks awaiting you and the paste blocks. Row text is clipped and each section shows at most 12 rows, with a count of the rest. Everything else is a count and a link: queued, blocked and done work is listed in full on the generated stream pages (`Streams/<Stream>.md`, plus `Streams/Other.md` for items with no stream), and older dated archives are listed on `Archive.md`. Nothing is dropped, it is one link away. `priorities set` re-renders it. The detailed rules for each command are in [reference/ledger.md](reference/ledger.md).

**Standing pickups.** The handoff is a snapshot of open items, so a duty that has no open item (keep the event loop alive, chain the next queued item when an agent finishes, sweep merged PRs, sweep branches and worktrees, run the daily cost experiment, reconcile tracker transitions) used to live only in habit. They are rows now: each has a trigger, an action, who runs it (a model tier) and when it last ran. `journal.ts prime` prints the rows needing attention (at most six lines, inside its 40) and `handoff` prints every row in a `Standing pickups` section, from the same function, so the two cannot disagree. A row is enforced one of two ways, and `add` refuses a row with neither: a runtime **check** (built-in: `loop-alive` is the loop lock held plus watches live and unexpired, `queue-moving` is not (queued items with nothing in flight), `tracker-transitions` is no done item with an unrecorded tracker transition) whose answer is the row's status, or a **cadence** (`--every-hours N`), which makes it overdue when its last run is older (never run counts as overdue). `done` on a checked row re-runs the check and refuses when it fails, so a row cannot be marked done on a claim; on any other row it refuses without `--evidence`. Nine rows are built in (`loop-alive`, `chain-next`, `merge-sweep`, `branch-sweep`, `epic-briefs`, `notes-reachable`, `library-fresh`, `cost-experiment`, `tracker-reconcile`); `add` with the same id replaces one and `retire` hides it. The store is append-only (`add`, `ran`, `retire` lines); a corrupt line is skipped. A check that throws, or names an unknown check, reads as failing rather than as fine. A cadence row is recorded as run by the machine when it did the work: a `journal.ts roll` whose worktree sweep finished (not `--dry-run`, not `--no-worktree-sweep`, not cut short by the sweep budget, and with no fetch, prune, scan or removal failure in any repo) appends a `ran` line for `branch-sweep` and prints `standing  branch-sweep  recorded`; a sweep with such a failure prints `standing  branch-sweep  not recorded (...)` naming the repos and the row stays overdue. The evidence is the sweep's counts and says that remote branches were not swept; those stay a listing for approval (`branch-sweep.ts`). A row enforced by a check, a retired row and an unknown id never get a `ran` line from a roll.

**Streams and registries.** If `$LEDGER_ROOT/Projects/<project>/streams.json` exists it is the registry: stream names fold to the canonical spelling on write and on read, an unknown name is rejected with a suggestion unless you pass `--new-stream`, and an archived stream rejects writes. Without the file stream names are not enforced. Model and tool tags are normalised either way: a built-in table (`scripts/lib/ledger-tags.ts`, extended by a `models` section in the same file) folds `--model` aliases to one canonical id, and `tool:` marks in `--used` lose script extensions and case. This happens on write and again on read, so history rolls up without rewriting the ledger. An unknown model warns and is written as-is. Rows written by scripts with no model involved carry `--model n/a`, and `usage` prints the unrecorded share.

**Claims.** `claim` writes the whole claim to a temp file and hard-links it to `Claims/<repo>.lock`, or to `Claims/<repo>@<scope>.lock` when it names a `--worktree` (or `--branch`), so two windows on different worktrees of one repo each hold their own claim. A claim with no scope, including an old `<repo>.lock`, conflicts with every claim on the repo; `release <repo>@<scope>` (or `--worktree`) frees one worktree. The link is atomic and fails if the lock exists, so of any number of racing processes exactly one wins, the lock never appears half-written, and the rest exit 1 and name the holder. `claims` flags a claim as stale when its pid is gone on this host or it is older than `--stale-hours`. Nothing deletes a stale claim for you.

**Backup.** The ledger is one file. Make `$LEDGER_ROOT` a local git repository and set `ledger_git_autocommit: on`; `roll` then runs `verify` and, if it passes, commits the changed files under that root as `chore(ledger): roll <date>`, staging each path explicitly. It never pushes.

### pr-state.ts

- `pr-state.ts <owner/repo#N | PR URL>... [--json]` reads each PR live and prints a first line `STATE: open|closed|merged` (a closed or merged PR is never ready, since GitHub keeps `CLEAN` on closed PRs), then its head sha, base, draft flag, `mergeable` and `mergeStateStatus`, `reviewDecision`, and for each reviewer the latest non-comment review with the commit it was on and a verdict word: `APPROVED-on-head`, `APPROVED-stale`, `DISMISSED`, `CHANGES_REQUESTED` or `COMMENTED-only`. Verdicts come from the review history, because an empty `reviewDecision` also appears after a push dismisses an approval.
- It lists unresolved threads split human and bot (path:line and the first 200 characters), a check summary, a `PUSH WARNING: a push will dismiss N approval(s): <who>` line whenever approvals sit on the current head (rulesets that dismiss on push), and two verdict lines. `READY-FOR-REVIEW: yes|no (reasons)` needs an open PR, not a draft, zero unresolved threads, no conflicts, and checks neither failing nor pending. `READY-TO-MERGE: yes|no (reasons)` needs all of that plus `mergeStateStatus` CLEAN, and no standing `CHANGES_REQUESTED`; `CLEAN` already carries the required approvals and rulesets, so repos that need none can say yes with no reviews. When the state is `BLOCKED` the reasons say what is missing in words (for example "approval dismissed by a push" or "changes requested by X"). `reviewDecision` is not used alone, because some orgs' rulesets leave it empty. `--json` adds `readyForReview`, `reviewReasons`, `readyToMerge` and `mergeReasons`; `ready` and `reasons` stay and mean the merge verdict.
- It fails closed: more than one page of reviews, threads or checks, or a PR it cannot read, makes both verdicts `no`, and so does any merge state it does not recognise. Only logins are printed, never emails. Exit 0 when every PR was read, 2 on bad usage or an unreadable PR. A cheap runner follows [playbooks/pr-state.md](playbooks/pr-state.md), and the standing brief block tells every worker to run it before pushing to a PR branch.

### prs-snapshot.ts

Mid-day PR snapshot and diff, stored under the ledger root.

- `prs-snapshot.ts [--diff] [--dry-run] --vault <path>` fetches the live board; with `--diff` it first prints the actionable changes since the last snapshot (a new human review, a review decision flip, a new human-opened thread, a merge or close, a draft promoted to ready), then overwrites the snapshot unless `--dry-run`. Bot activity is summarised as one count line.
- `prs-snapshot.ts --ready` adds the readiness report: PRs that are ready to merge (approved, not a draft, zero unresolved review threads, `mergeable` MERGEABLE, no open twin) and approved PRs that are not, each with the reason. After a merge it re-asks `mergeable` for the open PRs in that repo until two known answers agree (a stale cached MERGEABLE is not trusted). A PR holding a resolved review-bot thread also needs a SHIP IT from a fresh agent, recorded for its head commit with `review-verdict.ts record` (refused when the reviewer is the fixer), or it is listed as held ([details](reference/prs.md#re-review-before-ready); `rereview_gate` turns it off). `prs-snapshot.ts ready <snapshot.json>` prints it for a file, offline, with the file's age (it is not a merge gate).
- `prs-snapshot.ts --stacks` adds the stack report: a stack is a PR whose base is another open PR's branch in the same repo, and any stack deeper than `stack_max_depth` (default 3) or whose oldest PR is older than `stack_max_age_days` (default 5) is named with its chain and the bottom PR to drive to merge. `prs-snapshot.ts stacks <snapshot.json>` prints it offline. A snapshot taken before creation times were recorded reports depth only. The limits are a judgement, not a measured optimum.
- `prs-snapshot.ts diff <old.json> <new.json>` is the pure diff of two files: no network, no write.

### podium-gate.ts

The Podium v1 gate: a check that runs against a live Podium (or a throwaway one), not a document. It reads the Podium over HTTP and reports each criterion as `PASS`, `FAIL` (built, but short of the bar) or `NOT BUILT` (that piece is not in this build yet). A missing piece is a report line, never a crash, so the gate runs the same on a half-built Podium and on a finished one.

```bash
node scripts/podium-gate.ts                 # start a temp Podium with fictional data, check it, remove it
node scripts/podium-gate.ts --url <base>    # check a Podium already running (journal.ts web prints its URL)
node scripts/podium-gate.ts --json          # the results as JSON
```

| Criterion | Passes when |
|---|---|
| `tokens` | `theme.css` carries the type, grid, hairline, chart and status tokens, and the three fonts are served from the Podium's own origin with no off-origin link on the page |
| `home` | `/api/projects` has a status row for every stream, with links and a weekly series; `/api/charts` has a throughput series; `/api/state` has the needs-you (asks) and done lists |
| `shared-docs` | every project tab (`projects[].docs.shared` in the stream home payload) has a list whose items carry a title, author and date and no absolute path; a `{state: 'missing'}` entry reads as not built |
| `handover` | every project in every stream's home payload can answer the six new-engineer questions: what the project is, how to run it locally, how to run its tests, what is blocked, what was decided and where, and what to do next |
| `plain-language` | this checkout's library check flags a bare ticket id in page prose and spares one cited as evidence |

Some criteria are targets for pieces still being built and report `NOT BUILT` until those land, so a non-zero exit on a current checkout is expected. Exit 0 when every criterion passes, 1 when any is `FAIL` or `NOT BUILT`, 2 on a usage error or when a `--url` Podium does not answer at all. The library rule is read from this checkout, not from the server. Pass counts alone do not clear the gate: [playbooks/podium-handover-eval.md](playbooks/podium-handover-eval.md) is the scored run that checks a fresh agent can use one project tab, and [playbooks/podium-fresh-context.md](playbooks/podium-fresh-context.md) does the same for Home.

### Ledger drift: agents the ledger does not know about

The ledger only knows what was written to it, so an agent dispatched without `journal.ts start` leaves the footer saying "0 in flight" while it runs. The footer and the `continuity` tick therefore compare the two. The harness keeps one transcript per subagent under `<projects_dir>/<session>/subagents/` with a `.meta.json` beside it; a transcript written to in the last two minutes is a running agent, and only agents the orchestrator spawned (`spawnDepth` 1) count. An agent is accounted for when an in-flight row (or one closed in the last ten minutes) holds its description as whole words, or the description names the row's id. Anything else is untracked, and the footer says so: `ledger drift: 3 untracked agents (agent-dispatch.ts and agent-return.ts not in settings.json: print-settings-snippet.ts has the entries)`. The parenthesis names the usual cause: the dispatch and return hooks exist but nothing installs them, so check `settings.json` against `hooks/print-settings-snippet.ts`. The tick records the count in its state (`drift`) and raises one event when untracked agents first appear, not every five minutes.

"Running" is inferred from the last write: an agent that finished under two minutes ago still counts, and one waiting on a tool for longer than that does not. The check never writes to the ledger and never reads the settings file's contents beyond whether the two hook commands are present.

### status-page.ts

The Podium is the always-current status page, one Markdown note (`The-Podium.md`) in the status directory, built for reading in Obsidian or any Markdown viewer. Run it as `node scripts/journal.ts podium [--snapshot] [--dry-run] [--status-dir <dir>]` (`status-page` is an alias and `status-page.ts` is the script behind it). It reads `journal.ts status --json` and `triage --json`, a GitHub search of your open PRs (retried three times on a gateway error) and the files beside the page, then writes the page through a temp file and a rename. A failed ledger read exits non-zero and leaves the old page alone. A failed GitHub read does not: the page is written from the last cached PR data under a warning (see below). Ledger and GitHub text is treated as untrusted: URLs and `obsidian:` targets are dropped from it and brackets are escaped, so the only live `obsidian://open` links on the page are the ones the generator builds from notes that exist in the vault.

A vault note path in ask, working-on and queued text (`Plans/x.md`, `Projects/<project>/Research/y.md`) becomes a clickable `obsidian://open` link when the note exists in the vault. A bare path is looked up as written, then under the ask's ticket project, its stream's repo and the page's project. Missing paths, `..` paths and secret-file names stay plain text. A bare `obsidian://open` URI in ask text (`file` may carry encoded slashes, `%2F`) is read the same way: when its `vault` is this vault and the note exists it becomes the page's own link, and a note that sits in a sibling folder of the same project (`Plans`, `Research`, `Reviews`, `Runbooks`, `Knowledge`, `Archive`) from the one the text names is found there. A URI that does not resolve is still dropped from the Markdown page.

Only one rebuild runs at a time. It holds `.now.lock` in the status directory (the holder's pid and start time inside); a second run waits up to 10 seconds for it and then stops with "a status page refresh is already running". A lock whose process is gone, that is older than 30 minutes (a guard against a reused pid, set above the slowest run), or that cannot be read is taken over, so a crashed run never blocks the page and a slow live one is never overtaken. `--dry-run` takes no lock.

Every good GitHub read is saved with its fetch time in `.now-prs.json`. When a later read fails, the page is still written from that cache with a bold warning under the title that names the cache time (or, with no cache, says the PR tables are empty because they could not be read, not because nothing is open), and the command prints a note on stderr. A cache that is damaged or not shaped like a search result counts as no cache.

The page, top to bottom: a freshness line with both times (`Updated 3:05 pm ET · PR data 3:02 pm ET`; the PR time carries its date when it is from an earlier day, and reads `PR data unavailable` when GitHub has never been read); **Start here**, the same block `journal.ts start-here` prints (this week's goals, priorities, the top five asks, conditions, in flight, yesterday, recent answers, where each stream's notes live), built by the same reducer so the two cannot disagree, and replaced by one line saying why when it cannot be read, so a broken Start block never stops the page; **Today's priorities** (from `priorities.md`, each with its stream's awaiting, in-flight and open-PR counts when it names a stream; otherwise the line `Priorities not set for today — orchestrator will ask`); **Working on now**, one table of the in-flight ledger items only, grouped by stream (stream, id, what, ticket link, model, and how long it has run with its start time in your zone); **Queued**, right after it, one table of the queued items (to-dos not started), grouped by stream (stream, id, what, ticket link, how long each has waited); **Needs attention now**, grouped under a heading per stream, one list item per ask: its id, the decision needed from you in bold, the context, clickable ticket, tracker and PR links (PRs as plain `#123`; ids such as `ABC-123` never break across lines), and its age once it is old, with the `> answer:` stub on the line directly under it. An ask that carries decision fields shows them as one italic segment on its own line (door, decide-by, class, recommendation, and what happens if silent), and the Status table's awaiting cell gains `(2 one-way · next by 2026-10-09)` Ask text is shown whole, never clipped; elsewhere on the page, long text is cut at a word boundary only; **Open PRs**, led by a `Review queue: N of 4` line (the non-draft PRs against `review_queue_cap`, with what a full queue means for dispatch), then one table per stream that has any (ticket, develop PR with its base, staging twin with its base or `none`, tl;dr) with a stack diagram; **Library**, one line per stream with a link to the library INDEX of each of its projects, or `no library yet` (a link is built only when that INDEX note exists, and the section is left out when the vault name or the stream-to-project map is not configured); **Other status and findings** (in-flight work with its age, blocked items, recent done, deferred); and **Status** at the very bottom, the reply footer unrolled: one row per stream (done today, in flight, queued, awaiting you, to run, blocked), an agents line (in-flight ledger items; the live agent roster belongs to the harness and stays in the reply footer) and the session line (turns, percent of the roll, read per turn, `roll soon` or `roll now`). The Status numbers are formatted from the `footer` object that `status --json` carries, the same rows `status --footer` is printed from, so the two cannot disagree. Rivendell and Narnia, like any two streams, are separate rows and separate groups.

| File in the status directory | Role |

| `The-Podium.md` | The page. Regenerated; safe to edit in the places listed below |
| `NOW.md` | The page's old name. Now a tiny pointer note linking to `[[The-Podium]]`, regenerated by the same command so old bookmarks and links still land. A leftover `NOW.md` page that holds answers or ticks you have not reported yet is migrated once: they are carried into `The-Podium.md` before the pointer replaces it. Nothing install-specific is built in. The status directory is `status_dir`, else `<vault_root>/Projects/<project>/Status`; the stream order is `status_streams` (then repo streams, then streams seen on the board, `other` last; streams named in today's priorities move to the front in priority order, matched ignoring case, in both the web tabs and the Markdown page), a PR's stream comes from the ledger first (board items that name a tracker key in the PR's title or branch, directly or through `ticket-map.json`, or whose refs name the PR as `<repo>#N` or `gh:pr:<repo>#N`; the stream with most such items wins), then `stream-overrides.json`, then `status_repo_streams`, then `other`; tracker keys link through `tracker_url_base`, ticket notes through `obsidian_vault` and `ticket_note_path`.

**Keeping it current.** Register a `status-refresh` watch and the page regenerates by itself: once the ledger has been quiet for 15 s after a write (never more than 60 s late), after a PR event, and at least every 10 minutes. GitHub is read only when the PR data is dirty or over 5 minutes old, never in quiet hours, and nothing is written within 60 s of your own edit of the page. The same watch keeps the current PR board from going stale: when the newest stored board is over 10 minutes old, one GitHub search rewrites `prs-current.json` (no per-PR calls, never in quiet hours; a failure is retried after 10 minutes and reported once as an informational line). The footer's review queue and the push gate's stored fallback read whichever of `prs-current.json` and `prs-snapshot.json` is newer. The refresh never touches `prs-snapshot.json`, which stays the baseline `prs-snapshot.ts --diff` compares against and is written only by that command, so the greeting's diff still reports everything since the last greeting.

```mermaid
flowchart LR
    L[Ledger write] --> S[signature changes]
    P[pr-watch / pr-merged event] --> D[.now-dirty-prs touched]
    S --> W{settled 15 s,<br>or 60 s since the first change}
    D --> W
    I[10 min idle tick] --> E
    W --> E{your edit under 60 s old?}
    E -->|yes| X[wait, retry next check]
    E -->|no| Q{quiet hours, or PR data<br>clean and under 5 min old?}
    Q -->|yes| C[cached PRs]
    Q -->|no| H[GitHub read]
    C --> N[The-Podium.md]
    H --> N
```

**Answering from the page.** Only the asks and the priorities are editable; **Working on now** and **Status** are regenerated and nothing typed there is read as an answer. Under an ask you can write `> answer: <text>`, a `> discuss: <topic>` line (talk it through in chat first; the topic is optional), tick its `- [x]` box, or edit the priorities list. The watcher reports an edit once the page has been quiet for 20 seconds, so a half-typed answer is not taken for the answer, and writes it to the ledger first as an `answer` or `discuss` row on the ask (`journal.ts answer <id> --text "..."` and `journal.ts discuss <id>` write the same rows by hand). The ask stays open for `resolve`, and the page renders the recorded answer back under it, so an answer survives regeneration and a session that ends before it is acted on. Regenerating also keeps any such edit that the `status-watch` event type has not reported yet (an answer whose ask left the board moves under `## Unprocessed answers`), and if you save while a regeneration is writing, it reads the page again rather than overwrite you.

```mermaid
flowchart LR
    G[status-page generator] --> L{.now.lock free?}
    L -->|held by a live run| Wt[wait up to 10 s, else stop]
    L -->|free or stale| R[read GitHub]
    R -->|ok| C[.now-prs.json]
    R -->|failed| K[cached PRs and a warning]
    C --> N[The-Podium.md]
    K --> N
    N --> J[You edit it inline]
    J --> W[status-watch event type]
    W --> E[actionable event: ask id and text]
    E --> O[Orchestrator resolves the ask or updates the priorities]
    O --> G
```

### web.ts

`node scripts/journal.ts web [--port <n>] [--status-dir <dir>]` serves the Podium as a local web page. It is a small Node server (plain TypeScript, no framework) over the same ledger, PR cache and priorities the Markdown page is built from, and the Markdown page keeps regenerating unchanged beside it. It binds `127.0.0.1` only (port 0 by default, so the OS picks one, and the URL is printed). It is read-only except for five things: today's priorities, answering an ask, commenting on or unblocking a blocked item (see [Unblocking an item from the page](#unblocking-an-item-from-the-page)), deciding a drafted GitHub comment (see [Drafted comments](#drafted-comments-approve-edit-reject)) and the Open PRs Refresh button (see [Open PRs tab and the Refresh button](#open-prs-tab-and-the-refresh-button)). Three `POST` routes (`/api/priorities/move`, `/add` and `/delete`) rewrite `priorities.md` and, for each accepted edit, append one note to the ledger that is closed in the same write, so the day's history shows the change (see [Editing priorities](#editing-priorities-from-the-page)). A fourth, `POST /api/asks/answer`, closes an ask in the ledger (see [Answering an ask](#answering-an-ask-from-the-page)). It writes nothing else (not the rest of the ledger, the PR cache or the rest of the page), every other method is 405, and the only time it calls GitHub is when you press Approve on a drafted comment: PR data is whatever the last page refresh cached in `.now-prs.json`, with a `stale` flag when that is over 15 minutes old. Every request opens a fresh store, so a `streams.json` edit made from the command line shows on the next request.

#### Answering an ask from the page

An opened ask card shows its decision, recommendation, door, default and context, and an answer box with three buttons: `Send answer` (Cmd/Ctrl+Enter in the box does the same), `Take recommendation` (only when the ask carries one) and `Skip` (only on a two-way ask; a one-way ask, or one with no door recorded, shows no Skip and the server refuses a skip of it with a 409, writing nothing). A blank answer is refused; there is no approve-as-asked shortcut. The page posts `POST /api/asks/answer` with one of three exact bodies: `{id, mode: "text", answer}` (1 to 1000 characters of plain text, whitespace folded to single spaces), `{id, mode: "recommend"}` or `{id, mode: "skip"}`. For the last two the server builds the text, so the page never sends words it did not write: `Take the recommendation: <the ask's recommendation>` and `Skipped: no decision wanted on this one.`

There is one recorder. The server closes the ask with the same function behind `journal.ts resolve <id> --answer "<text>"`, so a web answer and a command-line answer are the same `resolved` row (the web row carries no model or usage marks, since no model wrote it). It then writes the answer into the ask's `> answer:` stub in `The-Podium.md` (or, when the page has no such stub, under `## Unprocessed answers`), and leaves the status watcher's baseline copy of the page (`.now-seen.md`) alone. That is how the orchestrator hears of it: the answer is an edit the watcher has not reported, so the `status-watch` event type raises one actionable event, `ask <id> (decision: ...) answered on the page, already recorded and closed: <text>`, once, and then adopts the page as its baseline. The ask is already closed in the ledger, so the session acts on the answer and does not resolve it again. If a page rebuild comes before the watcher looks, the generator carries the answer forward under `## Unprocessed answers`, so the event is not lost; the next rebuild after the report drops it. An answer the session records itself with `journal.ts resolve` never touches the page and raises nothing. The "already recorded and closed" wording needs the watcher to know the web server's ledger (the configured project); otherwise the line reads a plain `answered:`, so check the ask is still open before resolving it. If the note is missing, only the ledger is written and no event is raised (there is no page for the watcher to read).

A follow-up is queued with the answer. When `journal.ts resolve` or a web answer closes an ask (not a skip) and the ask's text or the answer names a pull request (`owner/repo#4071`, a `/pull/4071` URL, `PR #4071`, or a bare four- or five-digit `#4071`; a bare `#12` or a hex colour does not count), the same call appends a queued to-do, `Follow up on <PR> (ask <id>): <answer>`, in the ask's stream, repo and ticket, with the PR in its refs. One open follow-up per ask: a second resolve does not queue another. The automatic closers (age-out, settle, `--resolves`) never queue one.

Refused with nothing written: a blank answer or a `recommend` on an ask that has none (422), an id that is not an open ask (404), an ask already closed (409), and an ask that already has an answer typed in the note and not yet reported by the watcher (409: that answer is waiting to be recorded, and a second one would double it; clear the stub or let the watcher report it first). If a page rebuild holds the page lock for more than about two seconds the answer is refused as busy (409) and the page says to try again. The ledger row is the source of truth: if the note cannot be updated after the row is written, the answer stands and the server logs it. Same guards as the priorities routes: loopback `Host`, this server's own `Origin`, same-origin fetch, JSON body of at most 2 KB, and the per-start token.

#### Unblocking an item from the page

Every row of the Blocked list (Home, a stream tab, and the Blocked tile view) has a **Comment** button that opens a labelled box with two buttons: `Unblock` (Cmd/Ctrl+Enter in the box does the same) and `Comment only`. Sample data draws no box. The page posts `POST /api/blocked/comment` with the one exact body `{id, mode: "unblock" | "comment", comment}`; the route sits behind the same per-start token, same-origin check and small JSON body as the answer route. The comment is plain text of 1 to 400 characters, whitespace folded to single spaces; an empty one, one with control characters, and one shaped like a secret or personal data are refused (422) and never echoed back.

- `Comment only` appends one `comment` row (`of` the item, `by` the `podium_author` setting, `source: podium`) and the item stays blocked. `comment` is a non-item row kind, like `answer`.
- `Unblock` appends three rows in one write: the same `comment` row, a `resolved` row that closes the block (what `journal.ts resolve <id>` writes, with `unblocked: true`), and a queued `wip` row for the same work (what `journal.ts queue "<text>"` writes, with `unblocks: <block id>`, the block's stream, repo and ticket, and no gate). Its text is the block's text followed by ` -- <author>: <comment>`, so the board, a brief written from it and whoever starts it all carry the comment. The `chain-next` standing pickup (the `queue-moving` check: queued items and nothing in flight) is what moves it on; no other event is raised.
- It is idempotent. The same comment on the same item is recorded once (`same: true` in the reply, with the queued id on an Unblock), and a repeated Unblock with the same comment answers ok. A different comment on an item already unblocked, a comment on a closed block, and an unblock someone else did first by command line are refused (409); an id that is not a blocked item is 404.

  B["Blocked row<br/>comment box"] -- "POST /api/blocked/comment" --> W["blocked-write.ts<br/>token, shape, scan"]
  W -- "Comment only" --> C["comment row<br/>stays blocked"]

#### Drafted comments: approve, edit, reject

Comments the orchestrator writes for GitHub (review comments on a teammate's PR, replies to others' comments on your own) do not post themselves. They go in a queue, `<ledger root>/Projects/<project>/Journal/drafts.jsonl`, an append-only file beside the ledger whose rows fold to one state per draft: `pending`, then `posted`, `rejected`, or `failed`/`uncertain` when GitHub did not take it. A producer adds one with `node scripts/drafts.ts add` (one JSON draft on stdin; adding the same `key` twice is a no-op); there is no approve command in the CLI, and a draft always starts pending whatever the row says.

The **Others' PRs** tab lists every open PR (drafts included) that a teammate has in the `review_queue_orgs` owners (default `gh_org`), one row each, in five sub-tabs. Each PR is in exactly one, by this precedence: **Stale** (the gate, last and muted, never the default), then **In review** (you have a review draft waiting on it, or you posted a review the author has not pushed after), then **Threads open** (any unresolved thread, Copilot, bot or human; a PR with open threads is never ready), then **Not ready** (draft, checks failing or pending, merge conflict, changes requested, a `release/` branch or a blocking label such as WIP, hold or do not merge, or no ask yet; each row carries its reason chips), then **Ready for approval**, which opens first. A repo with no checks, or a mergeability GitHub has not computed yet, does not hold a PR back. Every label carries its count. Inside a sub-tab the longest wait leads, so the most blocked person is on top, and every row says `Waiting N h` from the PR's latest ask. A PR is never listed twice. A PR sits in the four active sub-tabs only if it was **opened less than 72 hours ago** (`others_prs_open_hours`) or had **activity in the last 48 hours** (`others_prs_active_hours`); activity is a push, a review or comment, a review re-request (a new request for you included, which is how GitHub's updated time moves) or a Slack post or reply carrying the link. Otherwise it is in Stale, and with no activity for more than 3 days (`others_prs_drop_days`, never below the stale window) it leaves the tab entirely. A request for you, or an @-mention, is no longer an exemption: an old request does not pin a PR, and a fresh one is activity. Ages under three days read in hours ("Updated 2 h ago", "Open 5 h", "Waiting 30 h"), then days. **The latest ask** is the newest Slack post carrying the PR link, or any reply under it, in the slack-watch `engineering*.md` notes of the container project's `Slack` folder in the notes vault (a local file read, ET times parsed, no network call); a PR never posted ages from the time it was opened (GitHub gives this tab no ready or re-request time). A stale row shows the author, "Last ask N h ago" and why ("no activity for 60 h, opened 4 d ago"), and leaves Stale for its normal sub-tab by itself the moment there is activity. A non-draft PR with no requested reviewer, no review and no Slack post is "Not asked yet" under Not ready. There is no signal for a review agent running, so that does not place a PR in In review. Each row has `repo#number` linked with the author beside it (display name and login when GitHub gives a name, else the login; draft cards and the Decided list name the author too, from the draft's own `author` or else the list), title, base, last update and age, whether you are a requested reviewer, the review state in words (review required, approved, changes requested), the open thread count and how many of those Copilot opened, and the draft status: "Draft ready" (the draft card with Approve, Edit and Reject sits inside that row) or "No draft yet". Your own PRs, bots and `self_review_repos` repos are left out. Every other repo in those owners is listed whether or not you were asked; another person's PR in a repo named by `hands_off_repos` carries "Hands off: the repo owner's call" unless you are a requested reviewer there (PRs by `hands_off_owner` are in scope), and the teammate review helper (`REVIEW-WAIT`) skips them under the same rule (an @-mention alone does not lift it). The list is `.now-others-prs.json` in the status directory, written by the same `status-page.ts` rebuild that refreshes your own PR cache (so on the `status-refresh` cadence and by the Open PRs Refresh press, never in quiet hours or on a cached-only render), as one scoped GraphQL search (`lib/teammate/others.ts`); `GET /api/others-prs` only reads that file, so opening the tab makes no GitHub call. A failed read keeps the last good list and the tab says so and how old it is. Each sub-tab shows 25 rows and a "Load more" button adds 25 per press (client-side and per sub-tab; the cache already holds the full list), with "Showing N of M" in a polite live region and keyboard focus moved to the first row the press added. Rows with a waiting review draft and rows where you are a requested reviewer lead their sub-tab and are never held behind the paging. A draft whose PR is no longer listed (or that someone else has already approved) keeps its card under "Drafts on PRs not listed above", so a pending draft is never hidden; when review drafts wait outside the open sub-tab the tab says so and offers a jump to In review (they sit there, not under Ready for approval); the Needs-you row "Open the draft to approve" links to `#tab=others-prs&draft=<id>`, which opens the sub-tab that holds that draft and scrolls to and focuses its card, Approve included, and the Decided list sits at the bottom as before. Each draft card: Each sub-tab is paged, 25 rows to a page (client-side and per sub-tab; the cache already holds the full list), with the shared pager ("Page N of M", Previous and Next, described under Pagination below), the rows that need you above the paging on every page, and the page and range in a polite live region.
Each draft shows its repo, PR link, `file:line`, Blocking / Suggestion / Reply in words, and the text. **Approve** posts it as you through `gh`; **Edit** changes the wording first (the approve then posts exactly what you saved); **Reject** needs a reason, records it and posts nothing. Enforced in code, not described: `POST /api/drafts/approve` is the only path that reaches `gh` (`lib/drafts/post.ts`, pinned by a test that scans the sources), it needs the page's token and origin like every write, it posts only the text the page showed (a draft edited since is refused), and it writes an `approve` row and a `posting` row before gh runs, so a second approve, a crash or a retry can never post twice. A `gh` call that was cut off is `uncertain` and is never retried by itself. The body limit for these three routes is 24 KB (prose), not the 2 KB of the other writes. The tab needs no configuration.

#### Reviewing a teammate's PR that has waited

With `teammate_review_minutes` set, `pr-watch` reports `REVIEW-WAIT` for a ready PR by someone else (not a bot, not you, not a `self_review_repos` repo) that no human has reviewed or decided after that many minutes. The [teammate review playbook](playbooks/teammate-review.md) then checks the head out read-only in a detached worktree, runs a scripted first pass (PR body, earlier bot findings, CI rollup, test command per changed package) and a scripted `npm ci` where needed, and hands one reviewing agent a lenient brief. `scripts/teammate-review.ts submit` applies the bar in code: a finding blocks only for a correctness bug with a stated input and failure, a security issue of a listed kind (secrets, PHI or PII, auth or tenant scoping, injection, a customer reference) or a deploy that cannot roll back; everything else is a suggestion, at most three. A second agent, `mithril-smells`, runs beside the reviewer on any diff that changes source; its smells go in as `source: "smell"` findings that carry a stated maintenance cost, can never block or change an approval, are dropped when the reviewer already raised the same file within 3 lines, and have their own cap of two; the smells pass is for a PR's first review only, and `submit` drops smell findings once another review of that PR is on record. The playbook also carries the wait-gate exceptions, the bot-thread triage and the later-round rule as judgement the run applies by hand (not enforced in code). The result is ONE review draft in the queue above: it opens with a specific compliment (a generic one is refused), carries each finding as an inline comment on a line that is in the head's diff (anything off the diff is dropped, never posted loose), is an APPROVE review when nothing blocks and REQUEST_CHANGES when something does, and ends by telling the author to resolve the suggestions however they think best. Approve on the Others' PRs tab posts it as one GitHub review; nothing is posted before that. A review is pinned to the head commit it was written against: at approve time the live head is read, and when the PR has moved the review is re-pinned to the new head only if the push touched none of the files it comments on, otherwise it is refused ("PR moved since this draft; re-prepare it") and stays pending. A refusal from GitHub shows its own reason (`message` and `errors` from the response body), not just the status line. An approving review is also refused while Copilot has an unresolved thread open on the PR: the count is read live from GitHub at approve time, not at submit, so a thread that opened or closed since is honoured; a PR whose threads cannot be read is refused too (409, `copilot`, nothing posted or recorded). A backmerge (head branch named `backmerge/...` or `back-merge-...`) is exempt, and so is a review that requests changes. The refusal leaves the draft pending, and an approve body carrying `as: "comment"` posts the same review as a COMMENT review instead (the `approve` row records the event). A failed review draft whose PR you then reviewed by hand does not keep inviting a second Approve (GitHub refuses it with HTTP 422): each page rebuild (`status-page.ts`, never a page load, and only when a failed review draft exists) reads the PR's reviews, and when one of yours was submitted after the draft was made it records an `already-reviewed` row, which settles the draft as rejected with the reason "Already reviewed" and the review's link in the Decided list. `GH_LOGIN` must be set for this; a GitHub failure leaves the draft as it was.

#### Replies to comments on your own PRs

For a PR you authored, `scripts/reply-drafts.ts threads` lists the unresolved review threads that wait on you, and `submit` takes the replies an agent wrote (`fixed`, `decline` with a reason, or `question`) and routes each by who is in the thread, in code: a thread with any person in it becomes a draft in the queue above and waits for Approve, Edit or Reject on the **Open PRs** tab, which shows the drafts as a section per PR under the table; a thread whose every other participant is a bot (`[bot]` logins, accounts GitHub marks as bots, and Copilot and the security scanner) is answered at once and, for `fixed` and `decline`, resolved. The bot path re-reads the thread from GitHub itself and refuses one with a person in it, the queue refuses a reply addressed to a bot, and an unknown or missing author counts as a person, so a person's comment can only reach GitHub through your Approve. A reply that goes out without approval may not @-mention a person. The bot path keeps its own log beside the queue (`bot-replies.jsonl`): a thread in the same state is never answered twice, and a call cut off mid-way is not retried. Only review threads are covered; plain PR comments are not, and a thread with more than 50 comments (or a PR with more than 100 threads) is refused rather than classed from part of it. Playbook: [playbooks/reply-drafts.md](playbooks/reply-drafts.md).

#### Open PRs tab and the Refresh button

The Open PRs tab (`#tab=open-prs`, beside Home and Others' PRs) lists every open PR you authored, from the same cache the Markdown page's PR section reads, so it costs no GitHub call to open. Rows are grouped by whose move it is, then by repo: **ready to merge** is pinned first (approved by someone's latest review and nobody's standing changes request, zero unresolved threads, mergeable with no conflict, not a draft; the count in the headline filters to just those), then yours, the orchestra's, and drafts. An approved row folds the approvers ("Approved · 2") behind a disclosure. The approvers come from the review history the PR search reads (the latest APPROVED, CHANGES_REQUESTED or DISMISSED review per reviewer), so someone who approved and later requested changes is not listed; a PR cache written before that field existed falls back to GitHub's own decision until the next refresh. A plain PR is one row: number, title, base, four gates (CI, merge, review, threads), and age. A develop PR and its open staging twin (the same head branch, or one differing only by a `-develop`/`-staging` suffix, or the cached develop twin of the staging PR) are one card with a lane per PR, each with its own base and gates; the card sits in the band of its most urgent side (so it never reads Ready to merge while one PR needs fixing), every count is in PRs, and a search or lens that matches either side keeps the pair whole. When the develop PR has merged while its staging twin is still open, the card keeps the develop PR as a lane marked Merged (and the Markdown page's develop column reads `#N merged`) until the staging PR merges too; then neither shows. A PR stacked on either side nests under the card. Search and lenses (failing CI, conflicts, threads, staging, stacked) filter the same list. A "PR data <time>" line says when GitHub was last read and warns when that is older than 15 minutes or the last read failed. The PR search is one page of up to 100 PRs, and it is scoped to `gh_org` when that is set, so without it the tab includes your repos in every organisation.

The Refresh button asks for newer data without a new GitHub query path. `POST /api/prs/refresh` touches `.now-dirty-prs`, the same marker the `status-refresh` watcher reads, and then runs `status-page.ts` once, the existing rebuild, which does the GitHub read and takes the existing page lock. The marker alone was not enough: it says nothing when the refresh finishes or fails, does nothing when no watcher is running or it is quiet hours, and waits for the watcher's settle time. The watcher will see the marker too and may do one more rebuild afterwards. The button reads "Refreshing..." and ignores clicks while the refresh runs (the server also answers 409 to a second press), the tab polls `GET /api/prs/refresh-state` every 2 s, and when the refresh ends the table and the "PR data" line reload. A GitHub failure (the rebuild keeps the old cache and reports why) shows as a failure with the reason; another rebuild holding the page lock shows as "already running". The route takes `POST` only, takes no arguments (the body must be exactly `{}`, and the paths come from the server's own configuration), is bound to `127.0.0.1` like every route, and carries the same token and same-origin checks as the other writes.

#### Scripts you are blocked on

When a tool call is denied, or a command only you can run is in the way (a ticket close, an allow rule, a settings change), the agent does not paste a block into chat. It registers a **script**, which puts it on the Scripts tab with an explanation and raises a Needs-you ask that links to it:

```bash
node scripts/journal.ts script add --kind one-time \
  --title "Close ticket the-maestro-359" \
  --what "Closes one vault ticket." \
  --why "The agent's vault write was denied; the ticket blocks MAESTRO-359's PR gate." \
  --after "The ticket is closed and the PR gate passes." \
  --blocks ab12 --blocked-by "repo-worker: ship the Scripts tab" \
  --model "<name>" --used "skill:the-maestro" \
  -- node ~/.claude/skills/xenophon/scripts/ticket.mjs close the-maestro-359 --project the-maestro
```

- **One-time or reusable.** A `one-time` script is a single act (close this ticket); once it runs, or you mark it done, it leaves the active list and is kept in **History**. A `reusable` script is a tool you will want again (refresh a cache); it stays listed with its last-run time and result, and its ask still resolves the first time.
- **What the tab shows.** "Blocked on you" first, then "Reusable", then a collapsed "History". Each card carries what it does, why we need it (with the ledger or ticket id it unblocks), what happens after, who was blocked, and the exact command in a code block with a copy button, plus the created and last-run times.
- **The Needs-you card** carries the same what/why/after inline and links to the entry. The ask is a paste ask, so its card has the Run button described below; a paste ask takes none of the recommend/default/door fields, because it is a command to run and not a decision.
- **Running it.** Either press Run on the ask (the [reviewed-run route](#running-a-reviewed-command) re-reads the block file and applies every guard), or copy the command, run it yourself and press **Mark done (I ran it)**. Either way the ask resolves and a one-time script moves to History. A reusable script is re-run by copying it; **Mark run** records the run. The page never runs a script it merely lists.
- **`journal.ts script list [--all] [--json]`** shows what is waiting (and History with `--all`); **`script ran <id> [--result done|failed]`** records a run from the command line (`done` also resolves the ask; `failed` leaves it waiting).
- **Storage.** `Projects/<project>/Journal/scripts.jsonl` (append-only, like `drafts.jsonl`) holds the entries and the runs; the command is also written once to `Journal/script-blocks/<id>.sh`, the only copy the Run button executes and the one the tab shows, so what you review is what runs. Registering the same script again while it still waits returns the existing entry.
- **Refused at registration, writing nothing:** a command the run guard would refuse (a paste-lint finding such as bare `node` for a `.ts` file, a secret file name, an environment dump), a secret-shaped value anywhere in the entry, a command over 8000 characters, prose over 600 characters or on more than one line, a missing field. Name a variable, never its value.
- **The write route.** `POST /api/scripts/ran` takes only a script id, behind the same per-start token, own-origin and exact-body checks as every other write. It closes the ask with a sentence the server composes, never text from the page, and refuses to mark a finished one-time script again.

#### Running a reviewed command

Two places on the page can run a command on the machine the server runs on: a **Run** button on an ask that carries a paste block (`journal.ts ask --paste <file>`, which is also how a registered script runs), and the **Scripts** tab (`#tab=scripts`), which lists a declared catalog under the scripts you are blocked on. Either way you review the exact command first, then press Run; nothing is copied into a terminal.

The page never sends command text. It sends an ask id (or a script name and its arguments) and the sha256 of what it showed you. The server re-reads the command (the ask's block file named in the ledger, or the catalog file), runs the guards on it, and runs it only if its hash is still the one you reviewed; a changed command answers `changed` with the new text for a second review. The six `POST /api/run/*` routes (`preview`, `start`, `poll`, `kill`, `resolve`, `catalog`) all need the same per-start token, own-origin and exact-body checks as every other write.

- **An ask's block** is refused if it breaks any [paste-lint](#paste-lintts) rule, names a secret file (the `.env*` and `ssm-*.json` families, templates excepted; the built-in matcher always runs, and your own secret-file hook, `~/.claude/hooks/secret-file-guard.mjs`, is asked as well when installed), prints the whole environment (`env`, `printenv`, `export -p`, `/proc/*/environ`), holds a secret-shaped line, is over 64 KB, or cannot be shown by the page exactly as it is. A word that builds a dot-file or `ssm*` name with a glob or an expansion is refused too. These are text checks, so they can be evaded; the floor under them is enforced at runtime: on macOS every run is wrapped in `sandbox-exec` with a profile that denies reading the secret files (templates stay readable) however a glob or expansion names them, and the child's environment is scrubbed. Where `sandbox-exec` does not exist, only the text checks, the scrubbed environment and your review apply. It runs as `/bin/zsh -c <block>` in your home directory with a 5 minute limit.
- **A catalog entry** (`podium/scripts.json`) declares an id, description, group, the command as an argv list, an args schema, `readOnly`, a model `tier` and a timeout. It is spawned with no shell. Each argument is validated against its schema (a string needs an anchored pattern, an integer a range, an enum a list; unknown names are refused) and appended as its own argv element, so `$(...)`, quotes and `;` stay literal. Placeholders (`{node}`, `{home}`, `{ledger}`, `{vault}`, `{project}`) come from the server's settings, never the request. An entry that fails validation is dropped and listed on the tab, and an entry that can write needs an explicit confirm.
- **While it runs**, output is read by line and any line the secret scan flags is replaced by a marker before it is stored; output is capped at 256 KB. The page polls for new output. There is at most one run per ask or script at a time (four overall), Stop kills the whole process group, and so does the timeout. The child gets only an allow-listed environment (`PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_ALL`, `TERM`, `TMPDIR`), so a block cannot read the server's tokens or database URLs from its environment; anything left in the run's process group when it ends is killed.
- **Afterwards**, one ledger row of kind `run` records the source, target, hash, status, exit code and duration, never the output. For an ask, **Resolve the ask with this result** closes it with an answer the server composes from its own record (status, exit code and duration); the output stays on the page, because it is untrusted text and does not belong in the ledger as your answer.

#### Editing priorities from the page

Home's priorities can be reordered (drag, or the move up and move down buttons), deleted (with an Undo for a few seconds) and added (a stream picker from the known streams plus free text), and the heading shows `N of <cap>`. The file `priorities.md` stays the source of truth: the server keeps no copy, re-reads it on every request, and writes it back through a temp file and a rename. Lines it does not own (headings, comments, prose) stay where they are, and an item keeps its own bullet, number style and checkbox. You can keep editing the file by hand: each edit names the text it expects at the index it acts on, so a list changed by hand since the page was drawn is refused as a conflict and the page reloads the real list, and an edit that lands between the server's read and its rename is detected and re-applied. The cap is `priorities_max` (default 5): adding past it is refused with "remove one first"; a list already over it is shown with a warning and can be reordered and shortened but not added to until it fits. `journal.ts priorities set` enforces the same cap. When `vault_root` is set, each accepted edit also rewrites every project's own file for today (`Projects/<project>/Status/priorities/<date>.md`) through the same function `priorities set` uses: the projects the streams map to get their items in list order, a project the list no longer names is cleared, its carried section is kept, and a project with no vault folder is skipped. A project file that cannot be written is logged and never fails the edit, since `priorities.md` is already written. The next roll's carry-over therefore starts from the lists you edited, not from stale ones.

What makes a write safe, in order: the server is bound to `127.0.0.1`; `Host` must be the bound address; a write must carry this server's own `Origin` (a missing `Origin` is refused for a write, though not for a read) and `Sec-Fetch-Site: same-origin`; the body must be `application/json` with a declared length of at most 2 KB (a cross-origin page cannot send that content type without a preflight, and the server never answers one); the `X-Podium-Token` header must equal the token the server made at start (32 random bytes, read by the page from `GET /api/edit-token`, which a foreign page cannot read: no CORS header, `Cross-Origin-Resource-Policy: same-origin`, and a rebound host is refused). The body must be exactly the shape of its route (`move {from, to, text}`, `add {text, stream?}`, `delete {index, text}`; an unknown key is refused), text is 1 to 200 characters of plain text with no control characters or angle brackets and no ` | `, and a stream is up to 40 letters, digits, spaces, dots, dashes or underscores. The page draws all of it with `textContent`. Error bodies carry a code and a fixed message, never the request's text. The token is a same-origin proof, not a login: any program on this machine that can reach `127.0.0.1` can read it, which is the same trust the read endpoints already extend.

Day math follows one rule (`scripts/lib/day-basis.ts`): an age counted from a row's stamp (queue age, the stale in-flight count) runs to the UTC day, the same basis as the stamp, and an ask's age is whole days in the page zone, the figure the web card and the age chart show; a date you type (`defer --until`) is read in `watch_tz`. Two conventions to know: the done-today list and footer follow the ledger's UTC date, as `journal.ts status` does, while `today` and the charts use the page's time zone, so in the evening they can disagree; and the `asks` list also carries the paste asks, each with the path of its block (`paste`, named only, the server never opens the file) and no decision fields. The server re-reads the client directories when a request names a file it has not seen (at most once per second), so a module a later build adds is served without a restart; code under `scripts/` still needs one.

An ask card shows the ask as written, laid out for reading: the decision first, then its decision fields (recommendation, door, default) as labelled lines, then the context. A one-line context that is long, or that carries `(1) ... (2) ...` or `(a) ... (b) ...` markers, is cut into short paragraphs, a `Label:` sentence gets its label in bold, and the markers become a list; nothing is dropped or reworded, and the ledger row is untouched. A context the writer broke into lines is left as written. On the Markdown page a long ask's context sits as nested bullets under its line, above the answer stub; a short one stays on the line. With line breaks in the text, the first line is the decision and every later line is the body, line breaks kept (a numbered list renders as a list); a one-line ask is cut after its first question mark, and the rest follows whole. A vault note the body names, as a path or as an `obsidian://open` URI for this vault, is resolved by the server (a note in a sibling project folder is found) and linked under the note's name; a GitHub pull request or issue URL and a Jira browse URL link under a short label (`#590`, `AB-12`). A bare `https://` or `obsidian://open` URL in the body is a link, through the same limits as every other link on the page (http and https, or `obsidian://open` with only `vault` and `file`; any other scheme or Obsidian action stays plain text). The Markdown page still drops URLs from ledger text. An ask that carries decision fields lists its recommendation, its door (a missing one reads as one-way), what happens if nobody answers (two-way asks only), its decide-by and any class other than standard. A pull request the ask names that is no longer open links to its `github.com` pull URL when the ask's own text contains that URL; the server makes no GitHub call.

Live updates: once the page holds data from a real server it opens `EventSource('/api/events')` and, on each `changed` event, reloads `/api/state` and `/api/charts`. If the stream errors or the browser has no `EventSource` it polls every 30 s and returns to the stream when it reconnects. Only the newest request's answer is applied and only when its `seq` differs from what is shown, so a slow reply cannot overwrite a newer one and an unchanged board is not redrawn. New data is held, not drawn, while a mouse press is in flight (so a redraw cannot swallow a click), while an answer is being sent, and while a field with text has focus; it is shown as soon as that ends, and the label says `· update waiting` meanwhile. Half-typed answers, unfolded asks and the control that has focus come back after a redraw. If a reload fails while the stream is up the page retries after 5 s, then every 30 s, and goes back to the stream alone once one works. A small label beside the freshness pill says `Updates live`, `Checking every 30 s` or `Offline, retrying`; it is absent for bundled sample data. The logic is in `client/src/live.ts` (no DOM, tested under node). Each open page holds one HTTP/1.1 connection to the server for the stream, and browsers allow six per origin per tab group, so around six or more tabs on the same address will stall the rest. The `stream-homes.json` watch only wakes the hub: no client view reads the home mapping yet, so a change there refetches state that looks the same. A change to a ticket, a brief or a document wakes it the same way.

The page checks every payload against its contract and skips rows that do not fit; the header line counts what was skipped (rows, priority items, fragments, chart rows, day entries and chart tables). It runs on current evergreen browsers: link checking uses `URL.parse` where it exists and `new URL` otherwise, and fragment lookup uses `Object.hasOwn` (Chrome 93+, Safari 15.4+, Firefox 92+).

Links to the web open in a new tab so the Podium stays put. A pull request link on `github.com`, and a ticket link on an Atlassian tenant you list in `podium_trusted_atlassian_hosts`, get a tab name per item, so clicking one again refocuses its tab instead of adding another. Every other web link, including every ticket link until you list its tenant, opens a fresh tab with `rel="noopener noreferrer"`. A page cannot pick which browser window a tab lands in, only a tab name, and a name is only reused when `noopener` is off. That exposes `window.opener` to the destination, so it is limited to those hosts; any Atlassian tenant can be registered by anyone, which is why none is trusted by default.

#### Vault reader and ticket rollups (`scripts/lib/vault/`)

The stream home base reads a notes vault (tickets, project docs) through one guarded reader and nothing else. It reads only the folders it is configured for (`Projects/<project>/Tickets` and its `Archive`, the document folders and `Briefs`), opens only `.md` files, and refuses everything else with a reason. Before anything is listed, stat-ed or opened it checks, in order: the path is plain and relative (no `..`, backslash or NUL), no segment is a secret-file name (environment files, SSM exports, Terraform variables and state, keys and certificates, SSH keys, registry auth files, `credentials*`, password databases), the path is inside a configured scope, no component is a symlink, and its real path is inside the real root. The file is then opened with `O_NOFOLLOW` and judged on its descriptor (regular file, size cap: 256 KB for a ticket). A denied name is never opened, never listed and never repeated in a response; results carry vault-relative paths only. The server stays read-only.

Tickets are parsed and rolled up in process (a port of the ticket tool's reader and rollup, so nothing is spawned). `tickets-parity.test.ts` runs the real ticket tool on a throwaway fixture vault and asserts the closed, blocked and points numbers match; set `XENOPHON_TICKET_SCRIPT` to point at another copy of the script. That parity is held by the tests, not checked at runtime. All test vaults are built from code with fictional names, plus decoy secret-pattern files holding canary strings that must never appear in any output.

#### Epic documents and the epic brief

Each epic in the home base response carries `docs` and `brief`. A document belongs to an epic because the note says so: its frontmatter names the ticket it serves with `ticket: <id>` (or `tickets: [a, b]`, or `epic: <id>`), and the server walks that ticket up to the epic whose tree holds it, so a plan written for a child ticket lands on the epic without anyone naming the epic. `ticket: none` marks a note as project-level. The note's kind is its `kind:`, else its `type:`, else its folder; its date is the first of `updated`, `last-updated`, `date` and `created`. Documents may sit in any project the epic's tickets live in. A document shown on an epic is not listed again on the link rail. Documents outside the vault are lines of the form `- [label](https://...) · uat` in the epic ticket's `## Links` section, and only http and https links without credentials are kept. `docs.groups` lists the documents by kind (at most 20 each, `more` counting the rest) and `docs.unattributedRecent` counts notes from the last 30 days in the epic's projects that name no ticket.

The brief is one short note per epic at `Projects/<project>/Briefs/<epic-id>.md` (at most 8 KB; a longer one is reported as too long and not shown). It is parsed into a typed block tree, never Markdown or HTML: headings of level 3 and 4, paragraphs, lists with one level of nesting and quotes, with runs that are plain, bold, italic, code or a link. The server builds every link: a web link must be http or https, and a `[[wikilink]]` becomes a link only when it names exactly one ticket or document it has already read. The "What done looks like" section is filled from the epic ticket, so the brief never carries a second copy.

```mermaid
flowchart LR
  N[Note with ticket: id] --> W[Walk to the epic that holds the ticket]
  W --> D[epic.docs by kind]
  B[Briefs/epic-id.md] --> J[Judge freshness]
  T[Ticket tree and attributed docs] --> J
  J --> F[brief: fresh, stale or missing, with the reasons]
```

Freshness is computed, never claimed. A brief carries a `basis` line (for example `closed 12 of 37 · blocked 2 · points 20 of 60 · open`, the exact line `ticket.mjs brief` writes) written when it was last revised. It is stale when that line no longer matches the epic, or when any ticket in the epic's tree or any attributed document was updated after the brief's `updated` date, and `staleBecause` says which. An open epic whose brief is missing or not fresh gets one unknown (`brief-missing` or `brief-stale`) with the fix in its text.

#### Roll guidance

`journal.ts roll` ends its archive step by writing `GUIDANCE.md` beside the ledger, prints the same lines, and `journal.ts prime` shows them in the next session (outside the board's 40-line cap; a note older than three days is not shown). It is derived from the ledger by script, with no model call, and is at most a header plus four lines: **Stalled** (an item in flight longer than three times the median finished item of the last 14 days, never under 24 hours), **Reworked today** (every item, open or finished, that has a `rework` row dated today), **Cost most** (the largest `--tokens` item and the largest stream by tokens, among items started or finished today and everything still open; a count passed to `done` wins over the one on the opening row; unmeasured rows count as zero) and **Do first** (a blocked item whose `--gate` has cleared, else an item that answers one of today's Podium priorities when any does, else the first blocked item, else the first in flight, in board order; items whose gate is still waiting, on hold on purpose (by text, for items with no gate) or waiting on the user are skipped). A section with nothing to say is left out; `--dry-run` prints the note and writes no file.

#### Epic briefs at the roll

The built-in standing row `epic-briefs` is checked at runtime, not described. For every open epic that a ledger item dated today touched (found by walking the ticket up to its top ancestor, through `ticket-map.json` too), it requires a fresh brief, judged by the same code and the same fingerprint as the home base, and it requires every note written today in that epic's projects to name a ticket or say `ticket: none`. `journal.ts roll` prints what is owed beside the archive output and does not block the roll; the row stays failing on the board, and `standing done epic-briefs` refuses until the list is empty. With no `vault_root` configured the check cannot look, so the row fails (`could not be checked: no vault root is configured`) and the roll prints that line; an unread vault is never a pass.

```mermaid
flowchart LR
  L[Ledger items dated today] --> E[Open epics they touch]
  E --> B{Brief fresh?}
  E --> N{Notes written today name a ticket?}
  B -- no --> F[Failing row and a line in the roll]
  N -- no --> F
  B -- yes --> OK[Row ok]
  N -- yes --> OK
```

The agent brief carries one line for this: attach a note you write to its ticket (or mark it `ticket: none`), and refresh the epic's brief when you change the epic's state.


#### Unreachable notes at the roll

The built-in standing row `notes-reachable` runs `journal.ts notes-check` as its runtime check, so it cannot be marked done on a claim: `standing done notes-reachable` refuses while any note under an active stream is listed on no stream tab, and `prime` shows the row as failing with the first note. `journal.ts roll` prints the same list, for the same `notes_check_since` window, (`Notes reachability: N of M notes ...`, each note with its reason and fix) beside the epic-briefs lines and never blocks the roll; nothing here blocks a PR. With no `vault_root` the row fails and the roll says the check could not run.

#### Project handover

Each project a stream covers gets a handover in the home base response (`projects`, sorted by project), so a new engineer can start from one page. Sections: `overview` (the first paragraph of `CONTEXT.md`, then its `## Now` and `## Next` lines), `run` (one entry each for `setup`, `run`, `test` and `deploy`, filled from pages in `Runbooks` or `Knowledge` whose frontmatter has `tags: [<kind>]`), `blocking` (blocked tickets, tickets waiting on an open ticket, and tickets with a question waiting, each with the reason; `clear` when none), `work` (open epics with closed of total, the open tickets by priority, and open PRs that name them), `library` (the lines of the generated block of `INDEX.md`, grouped by kind, with a link when the page is found) and `docs` (the `DECISIONS.md` note, up to five plans with active ones first, and shared documents).

A section that cannot be filled comes back as `state: 'missing'` with a one-line `fix` (for example `No runbook tagged "test"`), never as an empty list, so the page can say what is absent. Shared documents are always `missing` until a register of them exists. `CONTEXT.md` and `INDEX.md` are read through the same guarded reader as everything else (`INDEX.md` is admitted by its own scope); a symlinked or secret-named file is refused and shows as missing. The response carries `obsidian://open` and http(s) links only. This slice is the server payload; the tab layout comes separately.

#### Stream mapping (`stream-homes.json`)

An optional `stream-homes.json` in the status directory maps a stream to its work: `projects`, `epics`, `exclude`, `done` (an epic id mapped to `verified`), `docs`, `runbooks` and `pins` (a label with either an http or https `url` or a vault-relative `note`). It is checked by rule tables: a bad entry (a `..` path, a `javascript:` URL, an unknown stream, a wrong type) is dropped and shown as an unknown on the page, never a failed page. Without the file, streams are mapped automatically. Each root ticket (an epic when it has children) goes to exactly one stream by the first rule that decides: the config lists it; the stream has the most ledger items linked to a ticket in its tree (a tie is ambiguous and shown on both streams, claimed by neither); it carries a `stream-<name>` label; its project is listed under exactly one stream. A stream's `exclude` removes an epic from that stream under every rule. Epics are rolled up recursively and every number states what it counts; the page never estimates a date or a velocity.

#### Link rail and PR matching

The top of a stream tab, under the heading, is the stream's **definition of done** ("Cadence / What done looks like"), centred, then the links. The definition is read at request time from where it is written: each open epic's `## What done looks like` and each mapped project's `Projects/<project>/CONTEXT.md` section of the same name (nothing is copied or invented). A checklist (`- [ ]` / `- [x]`) shows done and open items with "N of M checked"; an epic with plain text shows its closed tickets of all; a met definition carries a Fine mark. With nothing written it says which file to add it to. Five definitions to a page. The `done` field of `GET /api/streams/<name>/home` carries it. Each definition has an **Edit** button: it opens the section's markdown in a labelled textarea (Ctrl or Cmd Enter saves, Escape cancels, a refusal shows in an alert under the field) and **Save** writes it back to the note it was read from through `POST /api/done/save`, replacing only the `## What done looks like` section and bumping the note's `updated:` date; the new text shows when the page next updates. A stream with nothing written and an open epic offers **Write it here**, which adds the section to its first open epic. The page sends a stream and a source, never a path. Below it, the `links` groups Pinned, Epics, Docs and Runbooks sit side by side in columns, five rows to a page, paged. The stream tab uses Home's names (Cues, Fermata, In flight, Coda) with the plain meaning read to a screen reader, and the 14-day score follows the board. Pull requests are not repeated there; the Pull requests section already lists them with their status. A link is drawn only after the same link policy as every other link (an unsafe address becomes plain text), says what it is in words (note, tracker, web), and sits in a row at least 24 px tall. Below 960 px both are closed disclosures.

The home base response carries `links`: groups in a fixed order (`pinned`, `epics`, `docs`, `prs`, `runbooks`), each at most 50 links with `more` counting the rest, and an empty group left out. The server builds every URL: a note becomes an `obsidian://open` link with only `vault` and `file` (the vault name is `obsidian_vault`), a pin must be http or https, and anything else is dropped. Documents come from each mapped project's `CONTEXT.md`, `DECISIONS.md` and the `.md` files in `Plans`, `Research`, `Reviews` and `Runbooks` and in one level of subfolder under each (`Research/<topic>/x.md`; deeper folders are not read); only the first 4 KB of each is read, for its title, `status`, `updated`, the tickets it names and its `stream:` field (a stream name, or `none` for a note kept off every stream tab). Plans that are active or in review come first, then the newest. A mapped project with neither `CONTEXT.md` nor `DECISIONS.md` is listed as an unknown. A pull request is attached to a ticket row when the ticket id, or its tracker key, appears in the PR's branch name or title at a token boundary (`x-05` does not match `x-051`); a row shows at most three PRs and `prsMore` counts the rest, and a PR that names no ticket stays out of the rows (it still appears in the stream's `prs` group).

**Shared documents.** The home base response also carries `shared` (at most 50 documents, newest first, with `sharedMore` counting the rest): the documents recorded with `journal.ts shared` for the stream's mapped projects. The server reads each project's own ledger and re-checks every row against the write rules, so a hand-edited row with an unsafe link or a secret-shaped file name is left out. It builds the links (an `http(s)` link as given, a vault file as `obsidian://open` with only `vault` and `file`, nothing for a file under the container root) and sends paths relative to their root, never absolute. The tab lists them in a "Shared docs (n)" disclosure in the rail: the title (a link only through the link policy), what it is in words (web, note, file), who shared it and when, and the reason when one was given. Only a pointer is shown, never the document's contents.

The stream tab draws the home base (`web/client/src/home-view.ts`, wording and counts in `home-text.ts`). It fetches `GET /api/streams/<name>/home` once the board is up, checks it with `sanitizeHome` (rows and epics that fail their rules are dropped and counted; an epic whose counts do not add up to its total is dropped, so a progress sentence never contradicts its rows) and fills its own slots, so it never rebuilds the ask rows. With no server, or no home base, the tab simply has none: no sample epic stands in. Each epic shows one sentence with its denominator (`9 of 14 closed (64%)`, plus `6 of 14 verified` when the epic needs it), a bar that repeats the sentence for sighted readers only, its next ticket and its unknowns count (a button that opens the unknowns list). What's left lists In progress, Blocked and Not started, five rows to a page (In progress eight), paged; unknowns sit in a closed disclosure. Every empty section folds into one `Clear:` line, and opening an ask folds the others, so one answer form is open at a time.

#### Pagination

Every list the Podium used to cut off with "Show all", "Show more" or "Load more" uses one pager (`web/client/src/pager.ts`): a page size per list (Cues, Coda and a stream's Needs you six; a stream's epics three; its ticket groups and link groups five, In progress eight; each Others' PRs sub-tab 25), "Page N of M" with the row range, and Previous and Next buttons. The pager is a named `nav` ("Cues pages"), the buttons are named for the list ("Next page of Cues"), the count sits in a polite live region, and the buttons stay focusable at either end (marked `aria-disabled`) so pressing Next never drops keyboard focus. A list that fits one page shows no pager. The page is kept by list key in `PAGES`, so a live refresh redraws the list on the same page (and a page past the end is clamped when the list shrinks).

#### Podium design system

**The browser tab is the first glance.** While asks need you, the tab title reads `(n) Podium` (n counts every stream, whichever tab is open; blocked items never count, they are not your hand) and the favicon, a baton, lights its tip in the accent. With nothing waiting, or on sample data, it reads `Podium` and the tip stays grey. Both icons are static SVG files served beside the page. The header's wordmark is the same baton, drawn inline with presentation attributes only (no style attribute, so the CSP holds), and its tip carries the same cue; on hover the baton dips 8 degrees around its grip and returns, a downbeat, and under reduced motion it stays still.

**The notation rule.** The page borrows music's notation, not its spectacle, and a mark ships only if data or something you just did produces it. Musical words are set in the display face's italic (`--font-serif`), never in labels, buttons or counts, and each carries `lang` so a screen reader pronounces it. The scope line above the cue line ends in a tempo for the counts it scopes: *Tacet* when nothing is waiting or in flight, *Adagio* when only work is in flight, *Andante* for one or two waiting (asks plus blocked), *Allegro* for three to five, *Presto* for six or more or three blocked. It is a button that opens the rule in place, with the tempo in force set in primary ink; the cue line stays the source of truth. An empty section says what empty means first, then a rest in the same italic: `Nothing needs you right now.` *tacet*, `Nothing is blocked.` *a tempo*, `Nothing shipped yet today.` *before the downbeat*, *rest* for nothing in flight or queued. Errors never get one. Every panel ends in *Fine* and a final double barline, so the foot of the page says there is nothing more below. The freshness pill's dot is a metronome: it ticks once (an opacity dip) each time the pill is redrawn, every minute, while the data is fresh, and once the data is stale it stops and turns the warning colour beside the Stale words. No new timer, and the pill is not a live region. While the board loads, the cue line's place holds a five-line staff with one note head gliding along it (transform only; it rests at the left under reduced motion), and the page still announces Loading the board once. A copied answer is marked with a single thin barline and *unresolved*, in the status and on the ask's row: the answer is on the clipboard, not in the ledger, and the cue line's counts do not drop. When the page can write, that becomes a final double barline and *resolved*.

The page is laid out for a glance: a header whose cue line reads `3 need you · 1 blocked · 3 shipped today · 2 in flight`, then the tabs, then the open tab's body (Home's layout is described above). Status is always a word or symbol as well as a colour. Each ask is one row (id, decision, stream, age); clicking the row, or Enter on the decision, opens its context, links and answer form in place, and Escape in the answer folds it back. Long lists are paged, not cut off behind a Show all: Home's Cues and Coda and a stream's Needs you show six to a page, so Blocked and Shipped today stay in view however many asks are open.

Each count in the cue line is a button that filters the board. Pressing `blocked` shows only the blocked items (the heading and the rows come from the same bucket the count does, so they always agree); pressing it again, or `Show everything`, brings the whole board back. The counts stay the totals for the open tab, the filter is kept in the URL fragment (`#tab=dashboard&show=blocked`) so a reload or a shared link shows the same view, and a filter that matches nothing says so. A stream-tag link opens that stream's full tab board, while the tab buttons keep the filter.

- **Tokens.** Every size, space, radius, shadow, duration, easing and colour is a CSS custom property in `scripts/web/client/theme.css`, and components reference names only (custom properties inherit into the shadow roots). Type is three self-hosted open-licence faces in three roles (a display face for the wordmark, the cue line and large numerals; a text face for everything else; a mono for ids), served from the page's own origin under `font-src 'self'`, on a scale of about 1.2 (12 to 36 px plus a 48 px display step); spacing is a 4 px scale with a 12-column grid token set; and colours are roles (`--surface-page`, `--text-secondary`, `--accent`, `--critical`, ...) with one accent. Chart series keep the validated categorical palette, with light-mode slots 2 to 5 darkened in OKLCH (hue and chroma kept) so every series marks 3:1 against the chart and page surfaces, and are never used for status. Hairlines, elevation, status glyphs and chart grid, axis and label styles are tokens too. [docs/design.md](docs/design.md) gives the principles, the font choices and the token reference.
- **Dark mode.** Follows `prefers-color-scheme`; the dark block redefines the same role names. `scripts/web/client/test/theme-contrast.test.ts` checks every text pair at 4.5:1 and the focus ring, control outlines and chart series colours at 3:1, in both modes, so a token edit cannot drop below WCAG AA. `theme-tokens.test.ts` loads the theme in a headless page in both modes and fails if any token the client reads is undeclared in either.
- **Forced colours.** Under `forced-colors: active` (Windows contrast themes) anything that was only a fill or a shadow gets a system-colour border: chips, ids, badges, the freshness pill, an opened ask and skeleton blocks; the selected tab keeps a 4 px `Highlight` bar and legend swatches keep their series colour with an outline.
- **Reduced motion.** Movement only marks a state change (tab panel fade, tab underline, ask confirmation, skeleton pulse); hover and press change colour, shadow and a 0.97 press scale. Under `prefers-reduced-motion: reduce` every duration token is 0 ms and the skeleton stops pulsing.
- **States.** Loading draws a skeleton of the page, a failure shows what failed with a Reload button, empty sections say what empty means, and on sample data an opened ask has no answer form (the section head says why) instead of a disabled one. The page loads once: its freshness pill turns into a stale warning 15 minutes after the data was generated. Answering is saving: `Send answer` (or Cmd/Ctrl+Enter), `Take recommendation` and `Skip` (two-way asks only) post to the server (see [Answering an ask](#answering-an-ask-from-the-page)); a saved ask shows the answer under a final double barline and `resolved`, and leaves the board on the next update. A refusal shows the server's reason on the card and keeps the typed text. A blank answer is refused; there is no approve-as-asked shortcut. How this works is said once, under the Needs you heading, not on every ask.

### event-loop.ts

One loop for every "wake me when X happens". The orchestrator appends a **watch** (`type`, `target`, an optional `done_when`, and a `report` note saying what it wants back) to an append-only registry; `run` checks them all and records an event only when the type's `diff()` says something changed.

| Command | Purpose and key flags |
|---|---|
| `add --id <id> --type <type> --target <t>` | Register a watch. `--done-when <rule>`, `--report <text>`, `--ttl-hours N` (default 24; 72 for `pr-watch`), `--interval S` (override the type's default cadence), `--notify` / `--no-notify` (opt this watch in or out of notifications), `--notify-overnight` |
| `list [--json]` | The live watches |
| `remove <id>` | Retire a watch (its type may clean up its own files) |
| `adopt <queue-file> [--until ISO]` | Write the adopt record (`adopt.json` in the event dir): the queue file a fresh session should read and work. Expires after 24 hours unless `--until` says otherwise, so tomorrow's session is not taken over by an old queue. Only the path is stored; a secret-shaped path is refused. `adopt` alone shows it, `adopt --clear` removes it |
| `digest [--peek]` | Print and consume the pending events; `--peek` leaves them |
| `run [--once \| --serve] [--interval N]` | Check, sleep, repeat (exit codes in the table below). `--once` is one pass. Exit 10 with the digest on an actionable event, 0 when nothing is actionable or no watch is registered, 3 for quiet hours, 2 for a usage error. `--serve` is daemon mode: it never exits on an event (see [the event inbox](#the-event-inbox)).
| `triage-log [--suppressed] [--hours N] [--json]` | The digest triage decisions with their reasons, or only the lines suppressed as noise (see Digest triage) |
| `events [list] [--unseen \| --all] [--json]` | Show the inbox's unhandled events (`--unseen`: not yet seen by this window; `--all`: every one). Every window sees every unhandled event here; `--json` adds `owner` and `seenWindows` |
| `events ack <id...>` | Mark events handled; ids come from `events list` |
| `events wait [--timeout-hours N]` | Block until an actionable event for this window exists (one it owns, or one nobody owns that no window has taken: see Routed events in the ledger section), mark it seen by this window, print it, exit 10 (0 quietly at the timeout, default 6h). An event is offered once per window; a session that dies before acting finds it again with `events list` |

#### The event inbox

`run --serve` does not exit when something happens. Each tick's events are appended to `<event_dir>/events.jsonl` and the loop carries on; it ends only on a crash or a signal. Quiet hours and an empty registry become waits in process. The file is append-only: an `event` row, later `seen` and `handled` rows, folded when read. An event's id is a short hash of its watch, type, time and summary: a line replayed after a crash keeps its time and adds nothing, while the same words at a later time are a new event.

An event row carries a `kind` (`thread`, `reply`, `conflict`, `changes-requested`, `reminder`, ...) and only the allowlisted `fields`: `repo`, `number`, `who` (`bot` or `human`), `count`, `tag`, `stamp` (the UTC stamp in a pulled file's name, from which the file is rebuilt via the registry) and `reason` (one of a closed set of unshared reasons) (`tag` is a plain-token tag name from a tag watch such as slack-watch or notion-watch, whose `-NEW`, `-UNSHARED` and `-CHECK-FAILING` lines get the kinds `tag-new`, `tag-unshared` and `check-failing`, with `count` set from `new=`). Summaries, report text, titles and logins never enter the file. The allowlist is applied where rows are written and again where they are read, so a hand-edited row cannot carry free text to a reader. The digest still holds the full line.

#### Digest triage

Before a tick's events are written to the digest, the pr-watch and pr-checks lines are classified by rules, and every decision is appended to `<event_dir>/triage.jsonl` with the rule that made it and a reason. These always wake: a review that requests changes, a new merge conflict, a new unresolved review thread from a person (not a bot), and a failing check (the line does not say whether the check is required, so any failing-checks line wakes, including pr-watch's `STEER pr <n> failing check <STATE>` steering line). A line no rule covers (a bot thread, a reply, a comment, a plain review, an approval, a Copilot line) is ambiguous. The loop's own health lines (`check keeps failing`, `watch expired`) always wake and are not triaged, whatever the watch type. Lines from other watch types, and info-only lines, are not triaged. A tick with no events writes nothing.

An ambiguous line goes to a triage seam that answers `actionable`, `noise` or `unsure`. Only `noise` with a reason stops a wake: the line is recorded as an info event and logged as noise with that reason. `unsure`, `actionable`, a failure of the seam and a noise answer with no reason all wake, and so does a noise answer on a line by a person (the code, not the prompt, holds that: only a bot login can go quiet). The running loop wires Haiku behind the seam: one `claude -p --model haiku` call per ambiguous line, using the existing Claude Code login (no API key is read), with a 60 second timeout, no built-in tools, no hooks (`--settings '{"disableAllHooks":true}'`), no MCP servers (`--strict-mcp-config`), no saved session, an empty temp directory as its cwd (so no project CLAUDE.md or settings), `MAESTRO_TRIAGE_CHILD=1` in its environment (event-inject and session-start-compact exit 0 at once when they see it, so a triage child never claims real inbox events), and the line sent on stdin. A non-zero exit, a timeout, a kill, a throw or an answer that is not a clean JSON verdict is `unsure`, so a failure only ever wakes. The seam is synchronous, so each tick has a 90 second total triage budget: a call may start only while budget remains, and the lines after it wake as `unsure` (logged with "budget ran out"). A tick therefore ends within 90 seconds plus one call. The line is passed as fenced data and the noise-needs-a-reason rule still applies. Set `MAESTRO_TRIAGE=off` to use the rules-only seam instead (it always answers `unsure`, so nothing is suppressed); `tick` called directly with no `triage` also uses it, so no model runs unless the loop's `run` is the caller. Once an hour the running loop adds one info event listing how many lines were suppressed since the last sweep (it never wakes), and `event-loop.ts triage-log [--suppressed] [--hours N] [--json]` prints the logged decisions or only the suppressed ones.

#### Quiet wakes

Some events are mechanical, so the loop handles them itself instead of waking the orchestrator (`scripts/lib/quiet-wakes.ts`, applied in the same tick step as triage). `continuity` events are info only: they never wake, and a failed step shows up in the hourly sweep. The `wake` watch named `merge-sweep-hourly` makes the loop run `merge-sweep.ts --close-ledger --json` itself, which closes every row whose linked PRs have all merged: with no findings the event is suppressed and one ledger note is written (naming the rows it closed); with any finding (merged, stale, closed-unmerged or unknown rows) or a sweep that could not run, it wakes and the findings are appended to the digest line. A `LEFT-OPEN-SET` line for a PR that `gh pr view` reports `MERGED` closes the rows linked to it (when all their PRs merged) and is suppressed with a ledger note, or wakes if the close failed; a PR that closed without merging, one that is still open, or a `gh` failure wakes (fail open), and so does an event whose ledger note could not be written, and so does an event whose rule itself threw (gh or the sweep could not start). A suppressed event is logged to `triage.jsonl` as noise with the rule's name (`continuity-info`, `merge-sweep-clean`, `left-open-set-merged`), so the hourly TRIAGE-SWEEP line lists it and `triage-log --suppressed` shows it; it is stored in the inbox as an info event, never actionable. Without the outside-world deps (a bare `triageEvents` call) only the continuity rule applies.

**Exit codes of `run`.** The runner wakes the orchestrator only on 10.

| Exit | Meaning | Do |
|---|---|---|
| 10 | Actionable events; stdout is the digest | Read the ACTION lines, handle them, then relaunch `run` |
| 0 | `no watches registered`, or `run --once` found nothing actionable | Nothing to watch |
| 3 | Quiet hours began (`QUIET-HOURS stop until <time>`) | Relaunch after the time given |
| 2 | Usage or configuration error, a malformed watch, a broken overlay type, or another loop holds the lock | Read the stderr line; never delete the lock |
| other | The process crashed or was killed | Read stderr, then relaunch (a dead owner's lock is taken over) |

Target = the status directory, one watch, registered by `session-start.ts`; see [playbooks/event-types/whats-next.md](playbooks/event-types/whats-next.md)) `stall` (reports a dispatched agent with no progress for `stall_minutes`, once per stall, with the item id and its evidence: progress is a commit or an edited file in the agent's worktree, never the lease, which belongs to the orchestrator window; the loop only reports, and the orchestrator stops and re-dispatches the agent by [playbooks/stall-reset.md](playbooks/stall-reset.md); target = the container directory, one watch; see [playbooks/event-types/stall.md](playbooks/event-types/stall.md)), and `notion-watch` and `slack-watch` (tagged-source watchers, with no model: they probe a registry of tagged Notion pages or Slack conversations and report only a change; see [notion-watch](#notion-watch-tagged-notion-pages) and [slack-watch](#slack-watch-tagged-slack-conversations)), and `status-refresh` (regenerates the Podium on its own, with no model: after a ledger write or a PR event, and at least every 10 minutes; target = the status directory, one watch, its refreshes never wake the orchestrator; see [playbooks/event-types/status-refresh.md](playbooks/event-types/status-refresh.md)). A type is a script (`scripts/event-types/<type>.ts` exporting `check(target, ctx)` and `diff(prev, next)`, optionally `done` and `retired`), a playbook (`playbooks/event-types/<type>.md`) and one line in `scripts/event-types/index.ts`. `check` also receives the watch and the state it returned last time (`ctx.watch`, `ctx.prev`).

An org overlay adds types without editing this repo: `<type>.mjs` and its playbook `<type>.md` in the overlay's `event-types/` folder. A duplicate name, a module without `check` and `diff` functions, or a missing playbook stops the loop with an error naming the file.

**Cadence.** Each type declares a default interval, and `add --interval S` overrides it for one watch. The loop checks only the watches that are due and sleeps until the earliest. Defaults: `inbox` 60s, `pr-checks` 180s, `pr-watch` 600s, `pr-merged` 240s, `gh-run` 120s, `reminder` 30s, `suite-done` 30s, `wake` 30s, `status-watch` 30s, `status-refresh` 30s, `roll-maintenance` 900s, `continuity` 300s, `cold-start-gate` 3600s, `library-due` 60s, `retro-due` 60s, `repost-nudge` 300s, `whats-next` 300s, `stall` 300s, `notion-watch` 900s, `slack-watch` 300s. Floors are enforced where the interval is computed (`scripts/lib/cadence.ts`): 120s for network types so GitHub is not flooded, 30s for local ones. A lower `--interval` or setting is raised to the floor, and a setting can only raise it (`watch_network_floor`, `watch_local_floor`; `watch_type_intervals` changes a type's default). The adaptive back-off still stretches intervals when nothing has happened for an hour or two. `pr-watch` declares its own 300s floor, which `watch_min_interval` can raise, and with `watch_quiet_hours_mode: slow` it keeps polling at 1800s in quiet hours.

**Behaviour.** Quiet hours apply (a reminder or wake is held until morning unless `--notify-overnight`): only watches added with `--notify-overnight` keep running through them. A watch expires after its TTL and retires itself when its type says it is done, except a standing watch: one of a type that renews (`pr-watch`, `inbox`, `status-watch`, `status-refresh`, `notion-watch`, `slack-watch`, `roll-maintenance`, `cold-start-gate`, `continuity`, `library-due`, `retro-due`, `whats-next`) added without `--ttl-hours` is marked `renew`, and the loop pushes its expiry out by the type's default TTL whenever less than half is left (even when the loop was down past the expiry), logging it as a `renew` line in `watches.jsonl`. An explicit `--ttl-hours` is honoured and the watch expires as asked; a standing watch registered before this change expires once, and session start registers it again with the flag. Informational events stay in the digest until an actionable one arrives. A failing check keeps its last good state and speaks once after three failures in a row. `run` takes a lock in `event_dir`, so a second loop is refused while the first is alive; the lock is released on exit, Ctrl-C and SIGTERM. Notifications are opt-in per watch: when `notify_command` is set, the actionable events of a watch added with `--notify` are sent to it as one line of at most 150 characters. A reminder notifies by default (`--no-notify` turns that off) and the `inbox` and `wake` types never do; a watch registered before this option has no flag and does not notify. With `notify_command` unset nothing is sent. State lives in `event_dir`: `watches.jsonl`, `state.json`, `digest.jsonl`.

### install-podium-web.ts (keep the Podium page up without a session)

`journal.ts web` runs in the foreground and nothing restarts it, so a server started from a session dies with that session and the footer link (`status_page_uri`, for example `http://127.0.0.1:47700/`) goes to connection refused. A second LaunchAgent, `com.jackreichert.the-maestro-web`, runs `web.ts` at login and relaunches it whenever it exits (throttled to once per 30 s). The installer only fills the plist and prints the commands; you run them:

```bash
npm run build:web                                  # the page is built output (dist/ is gitignored); without it / says "page is not built yet"
node scripts/install-podium-web.ts [--port <n>]   # port defaults to the one in status_page_uri, else 47700
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.jackreichert.the-maestro-web.plist
launchctl print gui/$(id -u)/com.jackreichert.the-maestro-web     # check it is running
npm run build:web && launchctl kickstart -k gui/$(id -u)/com.jackreichert.the-maestro-web   # rebuild and restart after updating the checkout
launchctl bootout gui/$(id -u)/com.jackreichert.the-maestro-web   # uninstall
```

The loop agent's reload (`launchctl kickstart -k` on `com.jackreichert.the-maestro-loop`) does not touch the web server: it is a separate process. Restart the web server too whenever the runtime checkout changes, and rebuild `dist/` first. The server re-reads the client directories when a request names a file it has not seen (at most once per second), so a module a later build adds is served without a restart; code in `scripts/` (the API routes) still needs the restart. A hand-started `journal.ts web` is not restarted by anything, so a stale one answers with old routes until it is killed.

Stop any hand-started server on the port first, or launchd's copy exits on `EADDRINUSE` and retries. Run the installer from the main checkout, not a worktree. The log is `<ledger root>/Projects/<project>/Journal/Supervisor/podium-web.log`.

### loop-supervisor.ts (keep the loop alive without a session)

A launchd LaunchAgent runs `loop-supervisor.ts`, which launches `event-loop.ts run --serve` (the daemon form, which never exits on an event: events go to the inbox) and relaunches it forever. It also watches the child's heartbeat: a loop that is alive but has written no heartbeat for 10 minutes past the wake time it declared is hung, so the supervisor logs it, stops it (SIGTERM, then SIGKILL if it ignores that) and relaunches it at once; one stale reading is forgiven, since after a closed lid the loop needs up to a minute to beat again. For a loop of an older version that still exits on events: on exit 10 it saves the digest to `<ledger root>/Projects/<project>/Journal/Digests/<UTC timestamp>.md` (first line `<!-- seen: false -->`) and relaunches at once; on exit 3 it sleeps until the stated quiet-hours end (at most 12h); on exit 0 or 2 it sleeps 300s (exit 2 is logged and the lock is left alone); any other code sleeps 30s. Digests are written only under the ledger root; with no ledger root the supervisor will not start.

Install (the script only fills the plist and prints the commands; you run them):

```bash
# 1. Stop any in-session loop first (end its background `event-loop.ts run` task, or kill the pid the installer names).
#    Run the installer from the runtime worktree (see below).
node scripts/install-loop-supervisor.ts          # writes ~/Library/LaunchAgents/com.jackreichert.the-maestro-loop.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.jackreichert.the-maestro-loop.plist
launchctl print gui/$(id -u)/com.jackreichert.the-maestro-loop     # check it is running
launchctl bootout gui/$(id -u)/com.jackreichert.the-maestro-loop   # uninstall
```

The plist's `PATH` is node's own directory, `~/bin`, `~/.local/bin` and the system directories, because launchd gives a job no login `PATH`: the notion and slack watchers call `with-env` by name, and it lives in `~/bin`. An installed plist keeps its old `PATH` until it is rewritten: run the installer again with `--force`, then `launchctl bootout` and `bootstrap` (the refusal it prints for a changed plist names the same checkout on both sides when only the `PATH` changed).

Is it alive? While it runs, the supervisor keeps `<event_dir>/supervisor.json` (`{ pid, startedAt }`); a stop by SIGTERM or SIGINT (including `launchctl bootout`) removes it. `journal.ts prime` prints one `Loop supervisor:` line when one is set up and not running: `DEAD (pid N, started ...)` when the record's pid is gone (a crash, a kill -9, a reboot), or `NOT RUNNING (installed at <plist>, never seen alive)` when the plist is installed and there is no record. With neither file, prime says nothing, so an install that does not use a supervisor is never nagged. The check is `kill -0` on the recorded pid, so a pid reused by an unrelated process after a reboot reads as running until the supervisor starts again. A supervisor will not start while another live `loop-supervisor` (its command line is checked, so a reused pid does not count) holds the record for the same event dir: it logs the pid and exits 2, instead of overwriting the record and running a rival loop. `MAESTRO_LAUNCH_AGENTS_DIR` moves the plist directory (default `~/Library/LaunchAgents`). Standing watches keep themselves alive under the supervisor too: see `renew` in the event loop behaviour above. The status page's `Updated <time>` line (and the web page's stale warning) shows when it was last refreshed.

The installer refuses while any loop holds the lock, and while another `*maestro-loop*.plist` is in the LaunchAgents directory (two would run two loops over one registry). It also refuses when its own checkout is on a branch, because launchd runs the supervisor from that path after every relaunch: install from a runtime worktree detached at the default branch (`git worktree add --detach <path> origin/main`, fast-forwarded when you update) so no branch an agent moves can change what the daemon runs. `--allow-branch` overrides that check. The log is `<ledger root>/Projects/<project>/Journal/Supervisor/loop-supervisor.log`; the supervisor keeps it under 5 MB by copying it to `loop-supervisor.log.1` (replacing the older copy) and emptying it in place, so at most one old file is kept. It carries ids, kinds and counts, never event text.

With the supervisor installed (its plist or its liveness record exists), a plain `event-loop.ts run` refuses with exit 2 and says to wait on the inbox instead, so only one runner exists; `run --serve` (the supervisor's own launch), `run --once` and `run --force` are not refused. With launchd holding the lock, a session cannot run the loop itself: it waits on the event inbox with `node scripts/event-loop.ts events wait`. `digest-wait` is the old name of the same command, kept as an alias: it first moves any unseen saved digest into the inbox (and does so again on each poll), then waits like `events wait`. The supervisor does the same move when it starts and after each digest a loop of an older version makes it save, so an event is delivered once whichever path it came in on. A digest is claimed by renaming it and marked seen only after its events are in the inbox, and an event's id covers the digest's save time (from the file name), so a crash in between shows the events again at worst, never twice in the inbox. `node scripts/event-loop.ts digests [--mark-seen]` prints the unseen digests without waiting.

### gh-guard.ts and gh-budget.ts (the GitHub budget)

Every production `gh` call runs through `scripts/gh-guard.ts` (`lib/tool-bin.ts` points `gh` at it; `MAESTRO_GH_BIN` or `MAESTRO_GH_GUARD=off` bypasses it). It logs the call to `<event_dir>/gh-calls.jsonl`, and before a GraphQL call (`gh pr ...`, `gh issue ...`, `gh api graphql`) it reads the real budget from the GraphQL `rateLimit` field at most every two minutes. Under 300 points left, or after a call GitHub refused for rate reasons, GraphQL calls fail fast with `GitHub limited until HH:MM` instead of being sent (a doubling 2 to 30 minute backoff, or the window's reset when known). REST and local calls are never blocked. `journal.ts status --footer` shows `**GitHub:** limited until 9:42 pm EDT (...)` while a block is active.

`gh api rate_limit` is not used: its graphql bucket does not track what GraphQL charges (on 2026-10-15 it said about 4,700 left while every GraphQL call failed).

- `gh-budget.ts report [--hours N] [--json]` prints calls per hour by caller and kind.
- `gh-budget.ts status [--json]` prints the last probe and any block; `gh-budget.ts clear` drops a block.

GraphQL charges by the connections a query asks for, so the costly reads are kept small. `pr-watch` searches the cheap fields of every open PR each tick (about 2 points) and reads threads, comments and reviews by node id only for PRs whose `updatedAt` moved, with a refresh after 10 minutes (open threads) or an hour. The Others' PRs list does the same for thread authors. Measured on 2026-10-15: one `pr-watch` tick cost 103 points and the Others' PRs list about 850 per rebuild before; about 2 and 50 after.

### Loop health (is it actually running?)

A held lock does not mean a working loop, so the loop and the supervisor leave a heartbeat. `event-loop.ts run` (not `--once`) rewrites `<event_dir>/heartbeat.json` (`{ pid, at, tick, watchesLive, sleepingUntil, mode, lastError }`, written by temp file and rename) on each tick, after each watch a tick checks (a tick runs its watches one after another, and a slow `gh` call must not make a healthy loop read `STALLED` or get killed by the supervisor's hang watchdog) and each sleep chunk; the supervisor does the same, with mode `idle`, `quiet` or `backoff`, while it waits between launches. The file holds no event text.

`lib/loop-health.ts` is the one reader. It turns the heartbeat, the loop lock and the supervisor record into a `Loop:` line, shown in `journal.ts status --footer` (bold label), `prime`, `session-start.ts` and the `loop-alive` standing row:

| Line | Meaning |
| --- | --- |
| `ok 2 min` | The owning writer's heartbeat is within its own planned wake time plus 5 minutes. `ok, waking after sleep` right after the machine wakes, before the first new beat |
| `quiet until 07:00 EDT` | The supervisor is waiting out quiet hours, as it said it would |
| `running, no heartbeat yet` | A loop holds the lock but started before heartbeats existed |
| `STALLED 20 min (no heartbeat since ...)` | The writer's process is alive but its heartbeat is past that deadline: it is hung |
| `DOWN since 13:58 EDT` | A supervisor is set up and nothing alive is writing a heartbeat |
| `DOWN, the loop will not start (<reason>)` | The supervisor is alive but the loop refuses to start or keeps crashing (its `backoff` beat carries the last error) |
| `NOT INSTALLED` | `loop_supervisor: required` and no supervisor is set up and no loop is running |

Whatever the verdict, the line ends with ` · 3 unread digests` (`1 unread digest` for one) when digests were saved to the inbox and no session has read them, for example `Loop: ok <1 min · 3 unread digests`. A live heartbeat only proves the process is alive; this part says a result is waiting. The count is the digest store's unseen files (`event-loop.ts digests` lists them and `digest-wait` claims them); nothing is added when there are none.

A heartbeat counts only from its owner: the process holding the loop lock for the loop's beats, the supervisor's recorded pid (with no loop holding the lock) for the supervisor's. A beat from any other live pid, such as a reused one, is ignored, so it can neither vouch for a hung loop nor raise a false alarm.

With nothing set up and nothing required the line is empty, so an install that does not use a loop is not nagged. Set `loop_supervisor: required` to make a missing supervisor loud.

Both processes sleep in chunks of at most 60 seconds and re-read the wall clock after each. A Node timer stops while macOS sleeps, so one long timer would resume late by however long the lid was closed; chunking bounds that to about a minute. Neither process holds the machine awake.

The standing watches (`renews` types such as the PR and inbox watches) keep themselves alive through the loop. A watch added before its type could renew carries no `renew` flag and would still expire; `session-start.ts` marks any such live watch of a standing type as renewing, once, and says so.

### session-start.ts

The first command of every session, and the first thing to run after a compaction. It is idempotent, so running it twice changes nothing.

```bash
node scripts/session-start.ts [--status-dir <dir>] [--project <name>]
```

```
status-watch: registered (added status-watch (status-watch /vault/Projects/my-workspace/Status), expires 2026-10-09T15:00:00.000Z)
status-refresh: already registered (status-refresh, expires 2026-10-08T09:30:00.000Z)
retro-due: already registered (retro-due, expires 2026-10-10T15:00:00.000Z)
Status page: updated 4 min ago (3:01 PM EDT)
Loop: ok 2 min
Event loop: NOT RUNNING. No session starts it: the launchd supervisor is the only runner (restart: launchctl kickstart -k gui/<uid>/<label>). Events already in the inbox still reach you: wait on it with run_in_background: node '/path/to/scripts/event-loop.ts' events wait
```

- **Watches.** For each of `status-watch`, `status-refresh`, `retro-due`, `repost-nudge` and `whats-next`, a live, unexpired watch of that type is left alone; otherwise one is registered through `event-loop.ts add` with the status directory as target, so each type's own validation, singleton rule and default TTL apply. A watch past its expiry that the loop has not retired yet is removed and registered again. A refused registration is printed as `NOT registered (<reason>)` and the exit code is 1, unless another session registered that type in the meantime, which counts as success. An existing watch whose target differs from the resolved status directory is kept but flagged with a `WARNING` line.
- **Standing watches.** A live watch of a standing type that lacks the `renew` flag is marked as renewing, with a `Standing watches:` line saying which.
- **Page age.** The age is the modification time of `The-Podium.md`. Past 15 minutes the line ends `STALE`: the refresh ticks every 10 minutes, so nothing is refreshing it.
- **Podium web.** When `status_page_uri` (the footer link) is an http URL, a connect to its host and port is tried with a 1.5 second cap (a killed child, so it cannot hang); when nothing answers, `Podium web: down (nothing answers at <url>)` is printed, since the page link is useless then. Silent when the link answers or is not an http URL (an `obsidian://` note link is not a server).
- **Loop.** The `Loop:` verdict line first ([loop health](#loop-health-is-it-actually-running); silent when no loop is set up or required), then the loop lock state. The script never starts the loop: the launchd supervisor ([loop-supervisor.ts](#loop-supervisorts-keep-the-loop-alive-without-a-session)) is the only runner, so a session only waits. Either way the line prints the `event-loop.ts events wait` command to launch with `run_in_background`; with no loop it also says how to restart the supervisor, or to install it when it is not installed yet.
- Exit codes: 0 done, 1 a watch could not be registered or the registry could not be read, 2 no status directory (set `status_dir` or `vault_root`, or pass `--status-dir`).

### notion-watch (tagged Notion pages)

Keep a vault note in step with a Notion page without spending model tokens. The work is split in two: the separate `notion-sync` skill pulls pages (`notion-pull`: page, child pages and child databases to markdown, secrets scrubbed, `notion_page_id` / `notion_tag` / `notion_last_edited` / `notion_hash` frontmatter) and records each tag in a registry file; the `notion-watch` event type here watches that registry. The event type is a thin shim over `scripts/lib/tag-watch.ts`, a shared engine for tagged-source watchers (state, rate-limit backoff, failure counting, event wording) that only needs a source to supply `probe` and `refresh`; the shim loads the skill's adapter on first use, so the skill must be installed beside this repo, under `~/dev-env/skills/` or `~/.claude/skills/`, or at `NOTION_SYNC_DIR`.

```mermaid
flowchart LR
  T[notion-watch tick, every 15 min] --> G[one GET per tagged page: last_edited_time]
  G -->|unchanged| Q[silent, zero tokens]
  G -->|moved| P[notion-pull re-renders the note]
  P --> D[diff file beside the note, registry updated]
  D --> E[one line: NOTION-CHANGED tag note diff summary]
  E --> M[the model reads the diff file only]
```

Register one watch per registry: `node scripts/event-loop.ts add --id notion --type notion-watch --target <registry.json> --report "<what to tell the orchestrator>"` (15 minute default, 72 hour lifetime). Tag a page with `with-env NOTION_API_KEY -- node <notion-sync>/scripts/notion-pull.ts <page-url-or-id> --tag <name> --out <note.md> --registry <registry.json>` (`--adopt` to take over a note that exists but was not pulled from Notion). The key reaches the scripts only through the `with-env` helper (or an already-set `NOTION_API_KEY`); nothing opens an env file, and Notion access is read-only (GET and the database-query POST, enforced in the one transport and covered by a test). What each digest line means, and what to do, is in [playbooks/event-types/notion-watch.md](playbooks/event-types/notion-watch.md).

### slack-watch (tagged Slack conversations)

Notice new messages in chosen Slack conversations without spending model tokens. Same split as `notion-watch`: the separate `slack-sync` skill pulls a conversation into a markdown note (`slack-pull --register` records its tag in a registry file) and the `slack-watch` event type here watches that registry. The type is a thin shim over `scripts/lib/tag-watch.ts`; the shim loads the skill's adapter on first use, so the skill must be installed beside this repo, under `~/dev-env/skills/` or `~/.claude/skills/`, or at `SLACK_SYNC_DIR`. A chat only grows, so the shared engine words its change as `SLACK-NEW tag= note= new= file=` (the count of new lines and a file holding only those) instead of a diff.

```mermaid
flowchart LR
  T[slack-watch tick, every 5 min] --> G[one history call per tagged conversation, limit 1, newer than the cursor]
  G -->|nothing newer| Q[silent, zero tokens]
  G -->|newer| P[slack-pull appends to the note and moves the cursor]
  P --> D[new-messages file beside the note]
  D --> E[one line: SLACK-NEW tag note new file]
  E --> M[the model reads the new-messages file only]
```

Register one watch per registry: `node scripts/event-loop.ts add --id slack --type slack-watch --target <registry.json> --report "<what to tell the orchestrator>"` (5 minute default, 72 hour lifetime). Tag a conversation with `with-env SLACK_READ_TOKEN -- node <slack-sync>/scripts/slack-pull.ts <channel-id> --tag <name> --out <note.md> --register`; the watcher never registers anything itself, so the registry is the allowlist. The token reaches the scripts only through the `with-env` helper (or an already-set `SLACK_READ_TOKEN`); nothing opens an env file, and Slack access is read-only. The loop `require()`s the slack-sync adapter, so that file must have no top-level await (a loader that hits one fails the check with a message naming it, and `slack-watch-type.test.ts` runs the installed adapter in a bare launchd-like environment). A conversation the token can no longer read reports `SLACK-UNSHARED tag= reason=` once. The notes may hold direct messages, so Slack events are not in the text-message alert allowlist. What each digest line means, and what to do, is in [playbooks/event-types/slack-watch.md](playbooks/event-types/slack-watch.md).

### commitments-sweep.ts

A decision stated only in conversation is lost at a session roll unless something carries it. `commitments-sweep.ts [--transcript <file.jsonl>] [--projects-dir <dir>] [--vault <root>] [--project <name>] [--json]` reads the user's own typed messages in a session transcript (the newest one in `projects_dir`, found the same way as the footer's Session line, unless `--transcript` names one), skipping tool results, reminders, task notifications, agent hand-backs and pasted content. It extracts sentences that read like a commitment ("we decided", "we agreed", "before prod", "make sure", "remember to", "from now on", "always", "never", "I want", "figure out ... before") and compares each by shared keywords with the open ledger items, the rules filed with `journal.ts rule` and the live standing pickups. **It prints no typed text**: each candidate is its turn number (the Nth typed message, from 1), the line of the transcript file it sits on (and, in `--json`, the record's own uuid and time when it has them), its cue class, its verdict (MATCHED, CHECK or UNMATCHED) and the id of the item that carries it, so a password or any other typed text cannot reach the output, the handoff or `prime`; the reader looks the turn up in the transcript. A ledger id prints only in the shape `journal.ts` generates, and a standing id only if it is lowercase words joined by hyphens (`standing add` now enforces that); anything else prints as `[id withheld]`. Matching is by keywords only, so a model or the user judges the unmatched and CHECK ones; the output says so. Exit 0 when there are no candidates or every one is MATCHED with high confidence (the open item holds at least 60 percent of the sentence's content words), 1 when any is UNMATCHED, 3 when none is UNMATCHED but some need a CHECK (an item shares words but covers too little), 2 on a usage or read error, including a vault and project with no ledger (so a wrong `--vault` cannot report everything UNMATCHED). It is read-only (it never writes the ledger or `standing.jsonl`) and sends nothing anywhere. [playbooks/commitments-sweep.md](playbooks/commitments-sweep.md) tells a cheap runner what to do with each unmatched candidate: a standing pickup, a rule with a memory file, queued work, or skip as noise.

### memory-sort.ts and memory-migrate.ts

Memory is for how to work with the user; project knowledge lives in the library. `memory-sort.ts --memory-dir <dir> [--hints <file.json>] [--json]` is a read-only report with one row per memory file (the `MEMORY.md` index is skipped): `project-fact` (with the library page it would live on, `Projects/<repo>/Knowledge/<name>.md`), `behaviour-rule` (stays), `decision-or-status` (a decision or dated status; the library holds a pointer to DECISIONS.md, never the status) or `unsure` (the user decides), with the reason. It reads the frontmatter type and the description only, prints no file body and exits 2 on a usage error.

`memory-migrate.ts --memory-dir <dir> --vault <root> [--approved <file>] [--hints <file.json>] [--apply]` is a dry run by default. Each project fact is `wait-for-page` (the composer has not written the page), `wait-for-approval` (the page exists with a `verified-at`, the file is not in the approved list) or `point`. With `--apply` (refused without `--approved`, a file of memory names one per line) a `point` file keeps its frontmatter and its body becomes `Moved to the library: [[page]]`. It never writes a library page and never deletes anything. See [playbooks/memory-to-library.md](playbooks/memory-to-library.md).

### rule-hygiene.ts

Rules saved as memory text are read once and often not applied; the ones that must happen belong in a hook, script or check. `rule-hygiene.ts --memory-dir <dir> [--audit <file.md>] [--json]` reads every memory file in the folder (the `MEMORY.md` index is skipped) and expects an `enforced-by` value in its frontmatter, at the top level or under `metadata`: `hook`, `script: <path>`, `check` or `none`. It lists files with no value (`MISSING`) or a bad one (`INVALID`). With `--audit`, it reads the table rows of a repeated-instructions audit, collects the memory names they cite, and marks each one enforced by `none` or by nothing as `PROMOTE`: the user repeated that topic, so the rule is a candidate for a runtime check. It prints no rule text, never writes, edits or deletes a memory file, and sends nothing. Exit 0 when every rule is tagged and no repeated rule is unenforced, 1 otherwise, 2 on a usage or read error. [playbooks/rule-hygiene.md](playbooks/rule-hygiene.md) tells a cheap runner how to report the result as one batch for the user to decide.

### library-check.ts

The library is a set of one-fact-per-page notes (`Projects/<repo>/Knowledge` and `Runbooks`) that agents read before they re-derive something. The page template and vocabulary are in [reference/library.md](reference/library.md), which also states the audience (an engineer, human or agent, new to the project) and the plain-language style every page follows. `library-check.ts [--vault <root>] [--repo <name>] [--json] [<page.md> ...]` checks every page (or the named ones) for the required frontmatter, the controlled vocabulary (`kind`, `status`, `repo`, `composed-by: composer`, and `components` against the repo's `INDEX.md` list), a `verified-at` date, dated evidence on every fact, a plain-language rule (a bare ticket id such as `MAESTRO-149` in page prose is flagged; one cited as evidence at the end of a fact, in inline code, a wikilink or a URL is not, and neither are standards like SHA-256 or RFC-2119), a 150 line budget, links that resolve (the frontmatter links and every `[[wikilink]]` in the body, with or without an alias or `#heading`, against the notes in the vault; the heading itself is not checked), and secret or PHI shapes (including a bare 32-character or longer random-looking token; git shas, digests, UUIDs, paths and slugs are not flagged, and a hex secret reads as a sha). A hit prints the rule and the line, never the matched text. Exit 0 when every page passes, 1 on any finding, 2 on a usage or read error (no vault, an unreadable named page), so a wrong path never reads as a pass. The secret patterns sit behind a small `Scanner` interface in `scripts/lib/library/scan.ts`, so a shared scanner can replace them. `notes-check` also reads `Knowledge/`, so a page with a `stream:` field is listed on that stream's tab.

`library-check.ts --coverage [--vault <root>] [--repo <name>] [--json]` is another separate report: for each project (a folder with a `CONTEXT.md` or `INDEX.md`, or any with library pages) it lists which of the six required page kinds (setup from scratch, run locally, test in staging, verify in prod read-only, deploy path, how it works end to end) no page declares. A page declares one in its optional `covers` frontmatter list (a value outside the required list fails the normal check). Superseded pages do not count. A project with no pages gets a row with `pages: 0` that is missing all six. It always exits 0, or 2 on a usage error (a `--repo` folder that does not exist is one); `--json` prints one row per project (`repo`, `pages`, `covered`, `missing`) for a dashboard to read.

`library-check.ts --stale [--code-root <dir>] [--vault <root>] [--repo <name>] [--json]` is a separate report: for each page it reads the file paths the facts cite as evidence and asks git whether any changed after `verified-at` (a date, or a sha in `YYYY-MM-DD@sha` for an exact range). It lists the stale pages with the files that moved, then the pages it could not check and why (no evidence path, no checkout under the code root, an untracked file); an unchecked page is never counted as fresh. The code root defaults to `MAESTRO_CONTAINER_ROOT` and a repo is looked up at `<root>/<repo>` or `<root>/skills/<repo>`. It always exits 0, so a stale page cannot fail a roll. The built-in standing row `library-fresh` fails once 10 percent of the pages are stale (it never blocks anything, and a caller that does not read the library passes `libraryStale` nothing and sees it ok). Clearing stale pages is the composer's second duty: its playbook ([playbooks/composer.md](playbooks/composer.md), section 4b) lists them with `--stale`, re-reads every cited source for each fact, then updates the line and the page's `verified-at`, or removes a fact it cannot verify. Before writing a page the composer compares its sha256 with the `pageSha` of the page's latest `curated` ledger row; if they differ, or the line says `told-by-jack`, and the source contradicts the fact, it does not overwrite the page: it raises an ask naming both sources and leaves the page stale. A page with no `curated` row has no recorded sha, so only its `told-by-jack` lines are protected. `library-check.ts --human-edited [--ledger-root <dir>] [--project <name>] [--vault <root>] [--repo <name>] [--json]` does that comparison for every page: it lists the pages edited since the last composer write (`HUMAN-EDITED`) and then those with no recorded sha (`unrecorded`), reads the ledger and writes nothing, and always exits 0 (2 on a usage error).

### library-write.ts

The one write path to library pages. `library-write.ts begin` takes the composer lock, which is a ledger lease on the item `library:composer` (30 minutes, renewed by every row the pass writes, lapsing by itself if the pass dies) and prints a holder id; a second `begin` exits 3 while it is held. Every later subcommand takes `--holder <id>` and exits 3 unless the live lease names it. `write <page> --from <staged file>` replaces one page (`Projects/<repo>/Knowledge|Runbooks/<name>.md`, no `..`, no symlink in the path) only when the staged text passes all of library-check's rules, the shared secret and PHI scanner over the whole page, and a comment-split check (a token cut by an HTML comment delimiter is refused); `composed-by: composer` is forced, the new text goes to a temp file and is renamed over the page, and identical bytes write nothing. `retros [--json]` lists the agent retros waiting for the composer (read-only, no lock: the retro id, its item and each lesson with its source `code`, `jack` or `process`; a retro already closed by a retro review is left out), which is the durable intake for what agents learned. `curate <learned id, miss id or retro id> (--page <page> | --reject "<why>") --model M --used a,b` closes one pending learned row, miss or retro with a `curated` row (one row closes one retro, once its lessons are on pages or rejected) (the page's sha256, or a scanned one-line reason; a miss closed with a page names the page that answers it, a miss closed with a reason is out of scope); only a `curated` row may close a learned row or a miss, and `verify` re-checks every curated row. `end` frees the lock. Exit 1 means a check refused the work and nothing was written; messages name the rule and the line, never the match. `curate <learned id> --page <page> --refresh` re-records the sha of a page that learned row already composed, after a refresh `write`, so the latest `curated` row for a page always carries the sha of the last write (a page with no earlier `curated` row cannot be refreshed this way). `write` remembers the sha256 it left on each page in `library-writes.json` beside the ledger, and every `curate --page` (the first close and `--refresh` alike) exits 1 with nothing written unless the page on disk still has that sha, so a hand edit cannot be recorded as composer output (a fact already on an unedited page is closed by a plain `curate --page`; an identical-bytes `write` does not bless a hand-edited page either, it is refused too); `--accept-hand-edit` on `curate` or `write` records the disk as it is, on purpose. `seed --holder <id>` is a one-time step for pages composed before the record existed: it records each unrecorded page's latest curated sha where that equals the disk (a hand-edited page stays unrecorded), and running it again changes nothing. `journal.ts log --kind curated` is refused.

### library-index.ts

`library-index.ts [--vault <root>] [--repo <name>] [--dry-run] [--check]` writes one line per library page (a wikilink, the kind, the read-when line, the verified-at date and a STALE or SUPERSEDED flag) into each project's `INDEX.md`, between `<!-- library-index:start -->` and `<!-- library-index:end -->`. Nothing outside the markers is touched, so the `components` vocabulary in the frontmatter stays a deliberate edit; a file with no markers gets the block appended under `## Pages`, and a project with pages but no `INDEX.md` is named and skipped, never created. A rerun with no page change writes nothing. `--check` prints what would change and exits 1 when any `INDEX.md` is out of date; exit 2 is a usage or read error. `library-check.ts` also fails a whole run when an `INDEX.md` has malformed block markers, since this script refuses to rewrite one.

With `--stale [--code-root <dir>]` the generated line also carries STALE for a page whose cited evidence changed since it was verified (the same judgement as `library-check.ts --stale`); it is opt-in because the line then depends on git state.

### Library eval

`playbooks/library-eval.md` measures whether a fresh agent finds answers in the library: a Haiku runner answers ten questions using only `find`, the project `INDEX.md` files and the pages, a Sonnet grader marks each pass, partial, fail or ungraded against the expected answers, and Opus settles a disputed grade. The target is 8 of 10 at two hops or fewer.

### library-brief.ts

`library-brief.ts --repo <repo> "<task words>" [--tickets-vault <vault>] [--json]` prints a `Library pages for this task` block for a dispatch brief: up to three absolute page paths with their read-when lines, and a warning on a stale page. It ranks like `find` (it asks `ledger-index.ts find`). With no match it still prints the block, saying none were found; a failed lookup exits 2 so the block is never silently missing. `journal.ts brief` runs it for the item's repo and refuses to write a brief when it fails.

### stale-wip-triage.ts

Lists every open in-progress row with its evidence: `stale-wip-triage.ts [--json] [--today YYYY-MM-DD] [--tickets-vault <notes vault>] [--vault <ledger root>] [--project <name>]`. Per row it prints the age, the last row that touched it, its ticket and that ticket's note status (with `--tickets-vault`), its children (rows filed with `log --parent <id>`) and any `owner/repo#N` references in its text. A row whose ticket is closed, or whose children are all closed, is proposed as `CLOSE` with that evidence; the rest are `ASK`, for one batch question with a recommendation per row. It writes nothing; closing is `done`/`drop` after the evidence or an answer. A cheap runner follows [playbooks/stale-wip-triage.md](playbooks/stale-wip-triage.md). New stale rows are then caught by `stale_wip_days` instead of piling up.

### weekly-retro.ts

A ten-minute retro draft from the ledger: `weekly-retro.ts [--days 7] [--stale-days 7] [--json] [--now <ISO time>] [--vault <path>] [--project <name>]`. It prints what finished, how many library misses were logged in the window and how many of those were answered with a page, closed as out of scope or are still open (`misses` in the json), what has been in flight longer than the cutoff, what is blocked, what was dropped, and last week's experiment with its verdict. Read-only; root and project resolve as `journal.ts` does. Reopened tickets, corrections from the user and cost misses are not in the ledger, so the draft lists them as prompts to fill in by hand rather than inventing numbers. Pick exactly one experiment for the coming week and record it as a note, `journal.ts note "Retro experiment: <what>"`; next week's draft shows it, and `journal.ts note "Retro verdict: keep|drop <why>"` settles it. Promote it to a rule only if it held.

It also lists each task finished two or more times in the window, grouped by the first three plain words of its text, and asks of each whether it could have been Haiku plus a script plus a runbook; a yes becomes a ticket to build the script and playbook. The grouping is a rough text match over ledger rows, so it names candidates, not conclusions.
### flow-report.ts

The four flow measures, read from the ledger and printed: `flow-report.ts [--days 14] [--oldest N] [--json] [--now <ISO time>] [--vault <path>] [--project <name>]`. For the window it reports items done (and per week), the median (p50) and 85th percentile (p85) of start-to-done time, work in flight and queued now, and the age of every open item, oldest first. An item starts when it went in flight (its `promote` row if it began queued, else the row that opened it) and finishes at the `done` row that closes it; a dropped item is counted apart and never enters cycle time. Spans print as minutes, hours or days, because most items finish within hours. Quote p85 as the service level ("85 percent of items finish within this long"). Read-only; root and project resolve as `journal.ts` does. Items logged only after the work was done show a near-zero cycle time, so the figure measures the ledger habit as much as the work. A run-quality block follows: send-backs (a `queue` row moving an in-flight item back to queued) per completed item, and silent runs (a briefed item whose report file is missing or empty); rework is the share of completed items with a `rework` row in the window (record one with `journal.ts log <id> --kind rework`), plus the number of rework rows and items.

### pr-size.ts

The size budget gate: `pr-size.ts --repo <path> --base <ref> [--json] [--head <ref>]`. It sorts each changed file into code, test, config, docs or mechanical, and fails when code exceeds `pr_max_code_files` (default 5) or `pr_max_code_lines` (default 400, additions plus deletions). An optional wide tier, off by default, also passes up to `pr_wide_max_code_files` files within `pr_wide_max_code_lines` lines (never above `pr_max_code_lines`); with it on, the summary shows the tier. Tests, config and docs do not count; lockfiles, generated files and pure renames are exempt only in a PR of their own, and migrations count as code. Exit 0 within budget, 1 over budget or mixed, 2 on a usage or git error. `pr-open.ts` honours `waive_size_gate_owners`: in a repo whose GitHub owner is listed (default none) it prints a one-line note and lets an over-budget PR through (the size limits only: code mixed with mechanical files is still refused); there is no flag for it ([details](reference/git.md#pr-size-budget)).

### pr-open.ts

The only way agents and the orchestrator open a PR: `pr-open.ts --repo <path> --base <branch> --title <t> --body-file <f> [--head <branch>] [--dry-run]`. It first checks that the body file exists and passes the body rules (required sections with real content, a Risk line, a fenced verify command, a diagram on stacked or wide PRs, no forbidden content; all configurable), and refuses (exit 1) otherwise. It then runs the size gate, refuses with a split hint (exit 1) when it fails, and otherwise runs `gh pr create --draft --assignee @me`. Draft and assignee are always added and cannot be turned off; no other `gh` flag passes through. `--dry-run` prints the command. Exit 0 opened, 1 refused by the body check or the gate, 2 usage, an unreadable body file, or a git or `gh` error, 3 the PR opened but its file links could not be expanded.

**Ledger link.** Once the PR exists, `pr-open.ts` records `gh:pr:owner/repo#N` and the branch on the ledger row it was opened for (a `ref` row, so nothing is rewritten). The row is `--item <id>`, else the `MAESTRO_ITEM` environment variable, else a ledger id in the branch name (`feat/MAESTRO-6tq3-...`); `--vault` and `--project` override the configured ledger. A link that cannot be written is a warning, never a failed PR.

### pr-ready.ts

The way agents and the orchestrator mark a draft ready for review: `pr-ready.ts --repo <path> --pr <number> [--over-cap "<reason>"] [--dry-run] [--vault <ledger root>]`. `pr-open.ts` only ever opens drafts and drafts are not counted, so the [review queue cap](reference/dispatch.md#review-queue-cap) is enforced here, where a PR actually joins the queue. In a repo whose owner is in `review_queue_orgs` (and that is not a `self_review_repos` repo) it reads the queue (live, else a fresh stored snapshot) and refuses with exit 1 when the PRs waiting on reviewers are at or over `review_queue_cap`; a queue it cannot read refuses too. A PR that would add nothing to the count (a staging twin of an open develop PR, or a PR waiting on its author) is let through. Personal and self-review repos are never gated. `--over-cap "<reason>"` marks it ready anyway: the reason is required, printed, and appended with the repo, PR and cap to `over-cap.jsonl` beside the PR snapshot (a dry run logs nothing). Exit 0 marked ready, 1 refused by the cap, 2 usage or a git or `gh` error. The gap: this is the maestro path, so a hand-typed `gh pr ready` or the GitHub button is not stopped.

### The PR gate scripts

`pr-open.ts` calls these, and the first four have a command of their own so an agent can satisfy a gate before opening the PR. The settings that switch each one on are in [Configuration](#configuration) and [reference/git.md](reference/git.md).

| Script | Does | Exit |
|---|---|---|
| `review-note.ts check\|new\|push --repo <path>` | In a repo listed in `review_note_repos`, a push needs a Reviews note for the exact head commit (file name carries `-review-<sha7>.md`, with a filled Naming pass). `new` writes the stub and `push` checks, then pushes | 0 ok, 1 refused |
| `pr-smells.ts record\|show --repo <path>` | Records that a report-only smells review ran on the head commit (kept in the repo's git directory, never committed); a later push invalidates it | 0 ok, 1 no record, 2 usage or git error |
| `review-verdict.ts record\|show --pr <owner/repo#N>` | Records SHIP IT or NEEDS WORK from a fresh reviewer for a head commit, in `verdicts.jsonl` beside the ledger; refused when the reviewer is the fixer. Also takes `local:<repo>#<branch>` for a branch not yet pushed | 0 ok, 1 refused, 2 usage |
| `pr-leaks.ts --repo <path> --base <ref>` | Refuses added lines, title or body that carry an org term, a personal absolute path, a person's name or a configured name. Prints `file:line label`, never the matched text | 0 clean, 1 a hit or an unusable term list, 2 usage or git error |
| `ci-gates.ts --repo <path> --base <ref> --body-file <path> --title <text>` | Runs the size, body, smells and leak checks with every override removed from the environment, as the `gates` CI workflow does. There is no flag that skips a gate | 0 all pass, 1 one refused, 2 usage or git error |

### merge-sweep.ts

`merge-sweep.ts [--close-ledger] [--json] [--vault <path>] [--project <name>] [--stale-days N]` reads the open ledger rows that name a pull request and asks `gh` what became of each. A row names a PR as `owner/repo#N`, `gh:pr:owner/repo#N`, a github.com pull URL, or `repo#N`, `repo #N` or `gh:pr:repo#N` for a repo whose owner is known (from `repo_owners`, or the row's own `owner/name` repo field); a bare name with no known owner is reported unknown, never guessed. It matches only `wip` and `blocked` rows: a `question` or pending `decision` is skipped (counted as `skipped`) however it cites a PR, since a merge does not answer it. It lists merged rows, stale open PRs, PRs closed without merging and unreadable PRs. With `--close-ledger` (alias `--close`, the only write, local and append-only; it never deletes a branch) it appends `done` to a merged row, only when the row is linked to its PR through refs (as `pr-open.ts` writes it), every PR it names is merged and it is still open; a row with any PR still open, closed or unreadable stays open, a row that only mentions a PR in its text is listed but not closed, and a second run closes nothing twice. Without `--close` it never writes the ledger. When the open rows name no PR at all it prints a `WARNING` and exits 3 instead of reporting clean, since a sweep that cannot see any PR cannot see a merge. Exit 0 clean, 1 something to report, 3 only unknown PRs or a blind sweep, 2 usage or read error. `--json` adds `actions` (rows left for a decision, plus 1 when blind; 0 exactly when the exit is 0), `closedCount` and `blind`. Deleting merged remote branches is a separate step, `branch-sweep.ts --apply --ids`, which prints a `restore <id>: git push origin <sha>:refs/heads/<branch>` line before each delete and refuses a branch with an open PR or one whose PRs it could not read.

### review-harvest.ts

Keeps what reviewers found that the author's own review missed, so a review tool's skills can be sharpened from real evidence and the planning checklist from real prior-art misses. `review-harvest.ts harvest <owner/repo#N>... | --since YYYY-MM-DD` reads each PR you authored through `gh api graphql` (read-only): inline review threads, review bodies and issue comments from Copilot, Aikido and other people, never your own, plus the changed-file list. Your replies are read only to hint a thread's fate and are never stored. Each comment becomes a code-level gist (fences, links and addresses removed; a PHI or secret shape withholds the text). Twin PRs (the same branch opened against two bases) and repeat bot passes collapse into one finding that keeps its thread count, and a second harvest of a PR adds nothing. Mechanical hints mark likely planning misses (a helper that already exists in a shared library, how a sibling integration does the same thing), things CI catches, and comments on code outside the diff.

`review-harvest.ts pending [--skills <dir>] [--json]` lists findings with no verdict, with the skill lines that share the most words with each (a coverage hint; `--skills` defaults to a sibling `mithril/skills`). `review-harvest.ts triage <id> --class mithril|planning|dropped --real yes|no ...` records one verdict: its fate, coverage (covered, partial, not covered), and for a proposed rule the skill, the wording and a source citation or `unsourced`. `review-harvest.ts batch [--since D] [--until D] [--out <dir>] [--write]` renders the weekly note: findings by category, a separate section for **planning misses** (these go to the planning checklist, not to the review tool), the dropped ones with the reason, and candidate rule changes. A candidate is `ready` with two or more findings from two or more distinct changes (twin copies count once) or repos, otherwise `watching`, and `blocked: unsourced` without a citation. Without `--write` it prints; with it, it refuses while any finding in the window is untriaged and never overwrites a note. It writes no skill: candidates are proposals for you to approve.

State lives in `<ledger root>/Projects/<project>/ReviewHarvest/` (`--store` overrides), and notes go to `<vault root>/Projects/mithril/Research/` (`--out` overrides). It runs without a prompt from two places: step 6 of the merge checklist (`reference/ledger.md#on-every-merge`) harvests the merged PR, and the merge-sweep standing pickup harvests the week's merged PRs, then a cheap model triages and writes the note by [playbooks/review-miss-harvest.md](playbooks/review-miss-harvest.md). Exit 0 ok, 2 on usage or an unreadable PR.

### pr-guide-links.ts

`pr-guide-links.ts <repo-path> <pr-number>` expands `{{file:path}}` tokens in an open PR's body into links to that file in the PR's Files changed tab, the same expansion `pr-open.ts` runs after creating a PR. Re-running changes nothing, and a token naming a path outside the diff is an error that writes nothing. The link is the PR URL plus `/changes#diff-<sha256 hex of the path>`, with an optional line suffix from the token (`#R25`, `#R25-R31`, `#L10-L12`; a malformed one is an error). The format was checked against a real PR link from a private repository; an anchor on a line outside the diff's hunks may not expand or scroll, so link ranges inside changed hunks. `pr-guide-links.ts --hunks <repo-path> <pr-number> [path]` writes nothing and prints a token for each run of added lines in the PR's diff. Exit 0 done or nothing to do, 1 an unknown path or a `gh` failure, 2 usage.

### branch-sweep.ts

Lists, across a container's repos, the worktrees and remote branches that are safe to delete, for you to approve in a batch.

- `branch-sweep.ts [--container <dir>] [--repo <name>] [--json] [--no-fetch] [--pr-days <n>] [--explain <branch>]` is read-only apart from `git fetch --prune origin`.
- `branch-sweep.ts --apply --ids <repo:hash,...> [--container <dir>] [--repo <name>]` re-scans each repo and deletes only what still qualifies: `git worktree remove` (never `--force`) for worktrees, and `git push --force-with-lease=<branch>:<listed tip> origin :<branch>` for remote branches, so a branch pushed to after the listing is refused. Local branches are never deleted.
- `branch-sweep.ts --apply-worktrees [--dry-run] [--verbose] [--budget <seconds>]` is the worktree half without the id step, which is what `journal.ts roll` runs. A repo with no linked worktree is skipped without a fetch. A worktree is also kept while it holds this process's cwd or script, or the checkout the installed loop supervisor runs from (the `WorkingDirectory` in its plist); that plist is read as XML text only, so a plist converted to binary format (`plutil -convert binary1`) silently loses this protection. Kept worktrees print as counts by reason (`--verbose` lists them); past the budget it stops at the next repo and names the repos it skipped.

A remote branch qualifies only when it is yours (every commit by one of `git_emails`, or the repo's `user.email`), not protected, and merged into every merge target by ancestry or a merged PR. Squash-merge patch equivalence alone lists it under Review, and `--apply` refuses it. A worktree must also be clean, unpushed-free, free of environment files (an ignored `.env*` or `ssm-*.json` may be the only copy of its secrets, so the sweep lists that worktree for you and never removes it, whatever `sweep_disposable_ignored` says; a file that is a symlink into the [env store](#env-store-movets) does not count, since removing the link leaves the store file untouched; the repo must ignore the link name, because an unignored link is an untracked file and keeps the worktree), unlocked, unclaimed, idle and not a live skill. Any git or `gh` error leaves the item out with the reason. Settings: `git_emails`, `protected_branches`, `sweep_merge_targets`, `sweep_idle_minutes`, `sweep_pr_days`, `sweep_protect_symlink_dirs`, `sweep_disposable_ignored`, `env_store_root`.

When a worktree would otherwise be removed and only real env files stop it, `journal.ts roll` raises one question per worktree (once; the same open question is not repeated): the worktree path, the file names, the suggested store folder (the project is taken from the branch name when it matches a project folder that already exists in the store, otherwise the question says it is unknown) and the `env-store-move` command to run. It never carries a file's contents.

Ownership is decided with a fixed number of git calls per branch (one `for-each-ref --contains`, one `rev-list --parents` and one `rev-parse`, whatever the number of protected refs), so a scan stays fast in repos with many `release/*` branches. Every protected ref, glob-matched ones included, counts when the branch's fork point is worked out.

### suite-run.ts

Runs `tsc --noEmit` and then `node --test` in a worktree as a detached job, so no agent has to wait on a suite. The prompt cache lives 5 minutes: an agent idling longer on a full run pays to write its whole context again on its next turn.

`suite-run.ts start <worktree> [--tests <glob>] [--cmd "<shell command>"] [--skip-tsc] [--timeout-min <n>] [--no-watch] [--json]` writes the job, registers its `suite-done` watch in the event directory (24 hour TTL; `--no-watch` skips it) and returns its id at once (the job id is the head commit prefix plus a time stamp). `status <job> [--json]` looks once and never blocks; it exits 0 when the job passed, 1 when it failed or was lost (the worker died without a result), 4 while it runs, 2 for a usage error or an unknown job. When the job ends it writes `results.json` last, by rename: tsc exit, test counts (pass, fail, cancelled), failing test names and the head sha. Jobs live under `MAESTRO_SUITE_DIR`, else `<event_dir>/suites/<job>/`, with `output.log` and `tests.tap` beside the results. The tests run in a scrubbed environment (temporary home, notifications off, no local config, no journal or note roots, temporary event and status directories, `NODE_TEST_CONTEXT` removed so a job started inside a test run still counts its tests). A run of zero tests (a glob that matches nothing, or a repo that does not use node `--test`) is a FAIL with a note; `--cmd` replaces `node --test` for such a repo and the job then passes on that command's exit code. The type check is `npm run typecheck` when the worktree's package.json defines that script, else `tsc --noEmit`; `results.json` records which one ran (`typecheck`). The type check and the tests share a hard timeout (`--timeout-min`, default 30): on expiry the whole process group is killed and `results.json` is still written with `timedOut: true` and a FAIL. A SIGTERM or SIGINT sent to the worker does the same, stops the children, removes the temporary home and records a `killed` note; SIGKILL cannot be handled, and `status` reports that job as lost. Without installed dependencies `tsc --noEmit` cannot run: that fails the job with a note, or pass `--skip-tsc`.

The rules this serves: never wait on a suite (start a job and exit with a findings note, the `suite-done` watch that `start` registers wakes the coordinating session); reviewers run targeted tests plus tsc only; re-reviews go to a mid tier. See [cost/budget.md](cost/budget.md).

### suite-summary.ts

Runs a repo's test suite in the foreground and prints one compact result, so an Opus agent reads a summary instead of running the suite itself. It uses the suite's own timing: node's `--test-reporter=junit`, `jest --json` or pytest's `--junitxml`, each of which carries a duration per test.

`suite-summary.ts [--repo <path>] [--runner node|jest|pytest] [--typecheck] [--gates --base <ref> --body-file <path> (--title <text> | --title-file <path>)] [--json] [--write-baseline] [--top <n>] [--max-failures <n>] [--slow-factor <x>] [--slow-ms <ms>] [--min-delta-ms <ms>] [--tests <glob>] [--cmd "<command with {out}>"] [--concurrency <n>] [--timeout-min <n>] [--baseline-name <name>]`. The summary has the pass, fail, skip and todo counts, the first failures (test name, file, first error lines), the wall time, the ten slowest tests, and the tests that are more than 2x slower than the baseline (and at least 100ms slower) or over 5 seconds. `--typecheck` also runs `npm run typecheck` when the repo defines it; `--gates` runs `ci-gates.ts` with the arguments given. `--json` prints the same summary as JSON. Exit 0 is green, 1 is a failing test, type check or gate, 2 is a runner error (no report, a crash with no failing test, a timeout, a run where no test ran because none matched or every one was skipped, bad flags).

The baseline is a per-test duration file written by `--write-baseline` from a green run (run it on main). It lives in `<suites dir>/baselines/<repo>-<runner>.json` (`MAESTRO_SUITE_DIR`, else `<event_dir>/suites`), never in the repo, and a worktree shares its main checkout's baseline. With no baseline there is no regression section, which is not an error. The node runner uses the same scrubbed environment as `suite-run.ts`; `jest` and `pytest` run the repo's own toolchain from the repo, and `--cmd` replaces the command (`{out}` is the report path). A new runner is one parser in `scripts/lib/suite-metrics.ts` that returns its test records, plus one case in `runnerCommand`. The same module exports `timeProbe` and `assertWithin`, so a timing probe can be an ordinary test whose regression shows up here.

The rule this serves: Opus reviewers and builders do not loop on full suites; a script or a Haiku step runs `suite-summary.ts` and the reviewer reads the output and does targeted probes. Sonnet and Haiku builders keep looping on tests and gates. See [cost/budget.md](cost/budget.md).

### cache-lint.ts

Checks that the agent-facing docs (`reference/`, `playbooks/`, `bolero/`, `cost/` and `SKILL.md`) keep the rules that avoid prompt-cache expiry rewrites: `node scripts/cache-lint.ts [--root <repo>] [--json]` exits 0 clean, 1 with `file:line [rule] text` per finding. Rules: `suites-line` (the brief's standing block keeps its Suites line with the detached `suite-run.ts` job, the 4-minute ceiling and the targeted-tests-only reviewer rule), `long-sleep` (no `sleep` over 270 seconds, so one wake stays inside the 5-minute cache), and `foreground-suite` (no `npm test` or bare `node --test` in a playbook code block). One blocking call with a long `--timeout` is allowed, because it costs one rewrite rather than one per poll. `cache-lint.test.ts` runs it on this repo, so a doc edit that drops the rule fails the suite.

### token-metrics.ts

Token-cost metrics read from Claude Code transcripts: numeric usage fields, model ids, timestamps and message type metadata only. Message content is never read; for `--leaks` it also keeps tool names, file basenames and result sizes.

`token-metrics.ts [--date YYYY-MM-DD] [--all] [--write] [--compare] [--curve] [--expiry] [--leaks] [--json] [--projects-dir <dir>] [--vault <path>] [--project <name>] [--baseline-until YYYY-MM-DD]`. With no flags it prints today. `--write` upserts the day's row in `Research/token-metrics.md` (idempotent), `--all --write` backfills every day still on disk, `--compare` sets the day against the 7-day median and a baseline and flags any metric that moved more than about 20%, and `--curve` shows cache read per turn by turn-index bucket, `--expiry` lists cache-expiry rewrites per day, and `--leaks` prints avoidable spend ranked by dollars (read-only subagents repriced at Haiku, subagent cache on a 1h TTL, compaction at the roll threshold, huge tool results carried across later turns), each with a fix line; it needs `model_prices`. The method is in [cost/measure.md](cost/measure.md).

The day summary and `--compare` show each cost metric with today, the 7-day median, the baseline, its target and PASS or MISS:

| Metric | Target (`cost_targets` key) |
|---|---|
| Model mix: share of tokens by family (opus, sonnet, haiku), orchestrator and subagents together, by cache-read tokens | opus at most 40% (`opus_share_max`), haiku at least 15% (`haiku_share_min`) |
| The same mix by price: each family's share of estimated dollars, from `model_prices`. Shown only when prices are set; otherwise the output says they are unset | Opus at most 50% of dollars (`opus_priced_share_max`); no Haiku target |
| Estimated dollars per day: orchestrator and subagents, by model and by category (read, write, output, input), from `model_prices`. Writes price as 5m unless usage splits 5m and 1h | informational; a >20% rise against the 7-day median is flagged |
| Wake-ups per prompt: (task-notification + handback wakes) / prompts | at most 0.5 (`wakes_per_prompt_max`) |
| Read per turn: orchestrator cache read per turn | at most 200k (`read_per_turn_max`) |
| Max turns since compact: the longest run of orchestrator turns without a compaction, per session (the day shows the longest) | at most 150 (`turns_since_compact_max`) |
| Small-agent rate: share of subagents that finished in under 10 turns | trend only, lower is better |
| Opus subagents: count and tokens | informational: each should be design, decision or review work |
| Cache-expiry rewrites: turns more than 5 minutes after the previous turn in the same transcript that write at least 30k tokens to the 5m cache, so the cache had lapsed and the whole context was written again. Count, average gap and dollars by model (dollars need `model_prices`); subagent transcripts count | informational: should fall once no agent waits on a suite |

Estimated dollars price each family's tokens (fresh input, 5m cache write, 1h cache write, cache read, output) at its `model_prices` row. The day summary also prints a what-if line: the orchestrator's cost had its tokens been on Sonnet. It is the same tokens repriced, so it ignores quality and any change in how many tokens another model would use. Table rows keep tokens by model (not dollars), so a pruned day is priced with the prices set when you read it.

#### Default prices

`model_prices` is not built in: set it in your config, and a config value is the only source. These are the current Anthropic list prices in dollars per million tokens, fetched 2026-10-02 from <https://platform.claude.com/docs/en/about-claude/pricing>. Paste them as a starting point and re-check the source when prices change.

| Model | Input | 5m cache write | 1h cache write | Cache read | Output |
|---|---|---|---|---|---|
| Opus 5.5 | 4 | 5 | 8 | 0.20 | 20 |
| Sonnet 5.5 | 2 | 2.50 | 4 | 0.20 | 10 |
| Haiku 4.5 | 1 | 1.25 | 2 | 0.10 | 5 |

Cache reads are not a fixed fraction of input: Opus 5.5 reads cost 0.05x input, Sonnet 5.5 and Haiku 4.5 0.1x. That is why one weight per model cannot price the mix.

```text
model_prices: opus: input=4, cache_write_5m=5, cache_write_1h=8, cache_read=0.2, output=20; sonnet: input=2, cache_write_5m=2.5, cache_write_1h=4, cache_read=0.2, output=10; haiku: input=1, cache_write_5m=1.25, cache_write_1h=2, cache_read=0.1, output=5
```

Estimates run a few percent under the billed figure when usage carries no 5m/1h split, because every write is priced as 5m.

Compaction is read from transcript metadata only (the compact-boundary system line and the compact-summary flag), never from message content. The table gains columns for these metrics; run `--all --write` to fill them for days still on disk, since older rows show `-` for them.

The rework rate is not computed from transcripts. It is recorded with `journal.ts log <id> --kind rework` and counted by `flow-report.ts`; corrections from the user are still recorded as ledger notes.

### cost-experiment.ts

The daily cost experiment, in two mechanical steps. The `cost-experiment` standing pickup (every 24 hours, a Sonnet-tier runner) follows [playbooks/cost-experiment.md](playbooks/cost-experiment.md): it refreshes yesterday's row with `token-metrics.ts --date <day> --write`, runs `propose`, writes one proposal from that input, then records it with `write`.

`cost-experiment.ts propose [--date YYYY-MM-DD] [--vault <notes vault>] [--project <name>]` prints, as JSON and without writing anything, the input a proposal is written from. The date defaults to yesterday in `watch_tz`. The metric to work on is the largest regression against the 7-day median (a metric more than 20% worse; the size of the move decides, whichever way that metric gets worse). When nothing regressed it is the model-mix metric furthest from its target: Opus share against `opus_share_max`, Haiku share against `haiku_share_min`, scored as a fraction of the target, so a miss beats a pass and, when both pass, the smaller margin wins. With no number for either, the basis is `none`. The output also lists the experiments already running on that metric, whether today's id is already in the registry, and the approved habits. A day with no row says which `token-metrics.ts` command to run.

`cost-experiment.ts write --date YYYY-MM-DD --practice "<text>" --hypothesis "<text>" --metric "<name>" --threshold "<text>" [--habit <key>] [--dry-run]` adds one row, id `cx-<date>`, to the experiment registry table in `token-usage-strategies.md` beside the token table. Running it again for the same date changes nothing, so a retried run cannot leave two rows for a day. A row that applies an approved habit (`--habit`, one of the keys `propose` lists) starts as `running`; any other starts as `proposed`, and the playbook then raises an ask with a recommendation. Cells are kept to one line with no pipe, and a note with no registry table is refused rather than written blind. The Podium's Cost section shows today's row.

### paste-lint.ts

`node scripts/paste-lint.ts [<file>] [--json]` checks a command block meant for an interactive zsh, from a file or stdin. A file with code fences is read as markdown and only its `bash`, `sh`, `zsh` and `shell` fences are checked; with no fence the whole input is one block. It prints each finding with its line, rule, message and a fix hint, and exits 0 clean, 1 on findings, 2 on bad usage. `journal.ts ask --paste` runs it and refuses a block with findings.

Rules (a table in `scripts/lib/paste-lint.ts`): `psql-uri-dbname` (psql ignores `-d` when given a URI, so the database must go in the URI path), `inline-comment` (zsh has interactive comments off), `string-command-var` (`M="uv run x"` then `$M`; use a function), `modifier-needs-braces` (`"$X:r"` should be `"${X:r}"`), `bare-node-ts` (a bare `node` on a `.ts` file; call the absolute node), `github-merge-approve` (no `gh pr merge` or approve in a block). It is deliberately conservative: it flags only patterns it can recognise on one logical line, so a clean result is not proof. "Prod writes chained with `&&` on their guard" is not checked, because telling a write from a read needs more than the text shows.

### brief-block.ts

### env-store-move.ts

`node scripts/env-store-move.ts <worktree> <file> <project> [--repo <name>] [--store-root <dir>] [--dry-run]` moves one real environment file out of a worktree into the env store and leaves a symlink at its old path. The store lives outside every worktree, as `<store root>/<repo>/<project>/<file>`, with `<repo>/shared/` for repo-wide values, and is never committed; a worktree links only its own project's files plus shared.

- The store root is `env_store_root` (default `~/dev-env/.env-store`). Directories it creates are mode 700; the file keeps its owner permissions and drops group and other access.
- It refuses to overwrite a store file that differs, refuses names that are not env files (`.env`, `.env.*`, `ssm-*.json`; templates such as `.env.example` stay), and never prints a file's contents. It copies, checks the copy byte for byte, then swaps the original for the link, so the only copy is never missing. A rerun that finds the same bytes already stored finishes the swap.
- It is idempotent: a path that is already a link into the store only refreshes the manifest. A link to a different project or file is refused, not re-pointed.
- `<store root>/manifest.json` is names only (mode 600): for each store file, its repo, project and file name, and the worktrees that link to it. No values, ever.

### local-db.ts

`local-db [--var NAME] [--db NAME] [--write] [--info] -c "SQL" [-A -t -x -q -H --csv -F SEP]` (or `node scripts/local-db.ts ...`) runs `psql` against your local Postgres so a worker never sees the connection URL. It reads `LOCAL_DB_URL` (or `--var NAME`) from the dev-env env file inside its own process, parses it as data (nothing is sourced), and hands psql the connection as `PG*` environment variables, never as an argument. The limits are enforced in code and covered by `scripts/local-db.test.ts`:

- The host must be `localhost` or `127.0.0.1`. Ports 5438 and 5439 (the prod and staging proxy ports) are refused even on localhost, as are variable names that look like prod, staging or shared databases, and URLs that carry anything but `sslmode` or `connect_timeout` in the query (`host=`, `port=`, `options=` and `service=` would redirect the connection). The caller's own `PG*` variables are dropped.
- `--db NAME` swaps the database in the URL's path (psql ignores `-d` beside a URI). `--info` prints host, port, database and mode only.
- The session is read-only (`default_transaction_read_only=on`) unless you pass `--write`. In read-only mode, statements that name the setting, `set_config`, `read write`, `set role` or `reset all` are refused. This is a guardrail against mistakes, not a security boundary. For read-only calls the helper prefers `LOCAL_DB_RO_URL` when it is set, and refuses to run if that role is a superuser or holds `pg_read_server_files`, `pg_write_server_files` or `pg_execute_server_program`; give that variable a restricted login role (for example one granted `pg_read_all_data`) for a hard boundary. Every call first checks the role and prints a note when it is privileged, because a superuser can defeat the read-only default and the denylist below with built-in functions or string concatenation inside `DO` blocks.
- psql arguments are an allowlist: `-c` and output-shape flags (SQL comes from `-c` only; psql itself runs at most one backslash command per `-c`). Connection flags, URIs, stdin scripts, `-f`, `-v`, `-o`, `-L` and `-P` are refused: a file or an `ECHO` variable would make psql print lines of files this tool knows nothing about, which the scrubber could not clean. Backslash commands other than the `\d` family, `\l`, `\x` and `\timing` (`\c`, `\!`, `\i`, `\o`, `\copy`, `\set` and the like) and backticks outside quotes are refused, since they could reconnect, run a shell command or write a file.
- Server-side file, program and cross-database access (`pg_read_file`, `pg_ls_*`, `lo_import`, `COPY`, `dblink` and the like) is refused in both modes. With a superuser local role these would read the host's files, which is why a restricted `LOCAL_DB_RO_URL` role is the real fix.
- Output is scrubbed of the URL, the password and the user:password pair, raw and percent-encoded, on stdout and stderr, and a refusal never quotes the URL. Exit 2 means refused.

The secret-file guard is unchanged: it blocks reading env files and lets this command through, because the command line never names one (the test runs the installed guard when it is present). The standing brief block carries a rule telling workers to use it for local verification.

## Configuration

Install-specific values live in one config file and one script, and nowhere else. The file is markdown with a fenced `maestro-config` block, one `key: value` per line (everything else in the file is prose and ignored). Every key is optional and blank values are ignored.

~~~text
```maestro-config
overlay: my-org-maestro
gh_org: my-org
ledger_root: /path/to/ledger
vault_root: /path/to/vault
```
~~~

A leading `~/` is expanded in `ledger_root`, `vault_root`, `status_dir` and `container_root`. A line outside the fenced block is prose and is ignored.

Each setting resolves as: **environment variable, then the user file, then the overlay's `config.md`**. The user file is `MAESTRO_LOCAL_CONFIG` (an explicit path; the empty string reads no file, which is what the tests set), else `~/.config/the-maestro/config.md`. `journal.ts settings` lists the values in effect with the source of each (`node scripts/local-config.ts` prints the same resolution without sources). Keep each value in one place, the user file, and have notes link to it; `journal.ts settings --check` flags notes that copy a value. An environment variable set to the empty string counts as set.

## The overlay model

The skill stays generic and public. Everything specific to one org (repo topology, tracker rules, data rules, release steps, branch bases) goes in an **org overlay**: a separate skill you write, kept outside this repo. Name it with `overlay:` in the config file or `MAESTRO_OVERLAY`. When one is configured the agent loads it by that name and follows it; when none is, the skill is fully generic.

```mermaid
flowchart TD
    subgraph generic [the-maestro: generic]
        S[SKILL.md, reference/, playbooks/, scripts/]
    end
    subgraph overlay [Org overlay: a separate skill]
        C[config.md with a maestro-config block]
        P[Prose: repo topology, tracker and release rules]
        ET[event-types/ scripts and playbooks]
    end
    ENV[Environment variables] --> LC[local-config.ts]
    UF[User config file] --> LC
    C --> LC
    LC --> SC[Every script]
    P -- "agent loads the overlay by name" --> S
    ET --> EL[event-loop.ts]
```

The overlay's `config.md` is found, first hit wins: for a `<plugin>:<skill>` name, `<installPath>/skills/<skill>/config.md` with `installPath` read from `~/.claude/plugins/installed_plugins.json`; otherwise `../<skill>/config.md` next to this skill (found through a symlink too), then `<dir>/.claude/skills/<skill>/config.md` for each directory above this checkout (so a checkout or worktree reached by its real path still finds an overlay in its container's `.claude/skills`; used only when the file's real directory and every ancestor are owned by you or root and not group- or world-writable, since an overlay can name commands), then `~/.claude/skills/<skill>/config.md`. Your git author emails, protected-branch list and other private values belong in the overlay or your own config file, never in this repo.

**A private overlay on a local-only branch.** To keep this repo public but version your overlay beside it, put the overlay on a branch that never leaves your machine, in its own worktree, and symlink that worktree as the skill:

```bash
git worktree add ../the-maestro-private -b local/private feat/my-branch
ln -s "$PWD/../the-maestro-private" ~/.claude/skills/the-maestro
ln -s "$PWD/../the-maestro-private/overlays/<skill>" ~/.claude/skills/<skill>
```

Merge the public branch into it, one direction only, and guard the boundary with a `pre-push` hook in the shared hooks directory that refuses any push naming a `local/*` ref and any push whose added lines match a list of private patterns:

```sh
#!/bin/sh
# pre-push: keep local-only branches and private content off the remote.
zero=0000000000000000000000000000000000000000
patterns="$(git rev-parse --git-common-dir)/hooks/private-patterns.txt"
while read -r local_ref local_sha remote_ref remote_sha; do
  case "$local_ref $remote_ref" in
    *refs/heads/local/*) echo "pre-push: refusing $local_ref, a local-only branch" >&2; exit 1 ;;
  esac
  [ "$local_sha" = "$zero" ] && continue
  [ -s "$patterns" ] || continue
  if [ "$remote_sha" = "$zero" ]; then range="$local_sha --not --remotes=$1"; else range="$remote_sha..$local_sha"; fi
  for c in $(git rev-list $range); do
    if git show --format= -p "$c" | grep '^+' | grep -qiE -f "$patterns"; then
      echo "pre-push: commit $c adds content matching a private pattern; refusing" >&2; exit 1
    fi
  done
done
exit 0
```

Make it executable, check it with `git push --dry-run origin local/private` (must be refused) and `git push --dry-run origin <public-branch>` (must pass), and never pass `-u` for the local branch.

That push hook can only reject a commit that already exists. Put this next to it as `pre-commit`, so a staged test or fixture is refused before the commit:

```sh
#!/bin/sh
# pre-commit: same private-pattern list as pre-push, on the staged diff only.
script="$(git rev-parse --show-toplevel)/scripts/fixture-names.ts"
[ -f "$script" ] || exit 0
exec node "$script"
```

## Safety guarantees

The honest question for every rule is whether it is **enforced at runtime** (a script refuses, so breaking it takes deliberate effort) or only a **convention** the agent is asked to follow (the skill text and the brief say so, and nothing stops a harness that ignores them).

### Enforced at runtime

| Guarantee | Enforced by |
|---|---|
| Every ledger row records the model and tools used | `journal.ts` refuses a new row without `--model` and `--used` (`--allow-unmarked` exists for tests and migrations) |
| A "rule" cites something real | `journal.ts rule` refuses, writing nothing, unless every `--ref` is an existing file |
| The ledger is consistent | `journal.ts verify` checks parsing, unique ids and dangling references and exits 1 on any problem; `roll` runs it before an autocommit |
| Two sessions cannot hold one repo claim | `claim` hard-links a fully written temp file into place; exactly one racing process wins and a reader never sees a partial claim |
| A stream is not archived half-finished | `archive` refuses while it has open items, an unfinished retro or unfilled promotions |
| PRs are drafts, assigned to you, within budget and carry a reviewer guide | `pr-open.ts` refuses a body that fails the body rules (required sections, risk, verify, diagram, forbidden content), runs the `pr-size.ts` gate and forces `--draft --assignee @me` with no way to turn them off. This holds for every PR opened through it |
| Branch deletion cannot take someone else's work or a moved branch | `branch-sweep.ts --apply` re-scans first, never uses `--force`, never deletes a local branch, checks authorship, and pushes with a lease on the listed tip |
| The PR watcher cannot be set to flood GitHub | `cadence.ts` raises any `--interval` or `watch_min_interval` below 300s to 300s |
| A notification cannot inject commands | `notify_command` runs as an argv array with no shell; the summary is one line of at most 150 characters |
| Message text never leaves the inbox type | `inbox` keeps only a hash per line and reports a count; a test covers it |
| Transcript content never reaches the metrics | `token-metrics.ts` copies an allowlist of numeric and metadata fields and drops the rest; a planted-sentinel test checks it |
| One event loop at a time | `event-loop.ts run` takes a pid lock in `event_dir`; a dead owner's lock is replaced, and so is one whose pid is alive but whose command line does not name `event-loop.ts` (a pid reused after a reboot is not a running loop) |
| A script's command is what the Run button runs, and is never run by the server unreviewed | `journal.ts script add` writes the command once to a block file and refuses what the run guard would refuse; the tab shows that file; the only executor is the reviewed-run route, which re-reads the file and checks its hash; a test edits the entry row and shows the preview and the tab still follow the block file |
| A broken overlay type is loud | the type loader rejects a duplicate name, a module without `check` and `diff`, or a missing playbook, naming the file |
| The brief is complete | `brief-block.ts` exits 1 if any slot is empty |
| A request to the Podium web server cannot come from a rebound hostname or a browser-declared cross-site page, and cannot write anything but the priorities, an ask's answer, a comment on a blocked item, the three drafted-comment decisions, the PR refresh, the run routes and the mark-a-script-run route | `lib/web/guard.ts` checks `Host`, `Origin` and the method before any route runs, lets `POST` through only on the paths the server registers as writes (the three priorities paths, the answer path, the blocked-comment path, the drafted-comment approve, edit and reject paths, the refresh path and the script-ran path), and only with this server's own `Origin`, a JSON body of a declared small size and a same-origin fetch, and is the only place a response is written, so the security headers are on every status; `lib/web/priorities-write.ts` and `lib/web/answer-write.ts` then require the per-start token and an exact body shape (as do the drafted-comment and refresh routes in `lib/web/drafts-write.ts` and `lib/web/prs-refresh.ts`). The server tests send hand-built requests with each wrong value and check the response, that the ledger is byte-identical after every `GET`, and that a refused write changes neither `priorities.md` nor the ledger |

### Convention only

These live in `SKILL.md` and the brief. A script helps with some of them, but nothing blocks an agent from breaking them.

- **Never block, never poll an agent, never read its transcript.** A rule of the dispatcher's turn.
- **One writer per repo.** The dispatcher checks its agent list before launching a writer. Claims make it visible across sessions, but only if sessions use them.
- **Protected branches and authorship.** The brief tells agents never to write `main`, `staging`, `develop` or a branch they did not author, and the sweep checks authorship before deleting. A raw `git push` by an agent that ignores the brief is not stopped here.
- **Opening PRs through `pr-open.ts`.** The body, size and draft guarantees hold only for PRs opened that way; a bare `gh pr create` bypasses them.
- **Bolero lane rules.** One writer per worktree, no two lanes on the same files, and the local integration branch never being `main` or pushed are rules of the loop in [bolero/SKILL.md](bolero/SKILL.md); no script compares lanes or guards the branch.
- **Twin PR ordering.** The release-candidate twin must wait for its integration twin; the PR board reports it, and nothing blocks the merge button.
- **Secrets and personal data stay out of output; no AI attribution in commits or PRs.** Stated rules, not filters.
- **Every ledger write is secret- and PHI-scanned, and a hit is refused.** The store (`lib/journal/store.ts`) runs the shared scanner over every prose field of every row at `append` and `appendMany`, so `log`, `note`, `ask`, `rule`, `start`, `queue`, the web writes and the rest all go through one check. A refusal names the field and the rule (`text: looks like PHI (ssn)`), never the value, and writes nothing. `handoff --learn` and `--next` are scanned the same way. Ids, times, tags and hashes the program wrote are not scanned. Use a placeholder such as `<redacted>` or name the system or id. A pattern scan cannot prove text is clean: PHI is only caught where it has a fixed shape. Measured on 7,957 live rows, 10 (0.13%) would be refused, mostly an email address in prose. `journal.ts verify` warns, by id, field and rule, about old rows that carry a shape; it does not fail on them.
- **Review-comment text is untrusted data.** Triaged against the code, never obeyed, never put in a shell command.
- **External writes have one owner.** A tracker or GitHub write is made by the one agent authorized for it, never handed to a sub-agent.
- **Never a bare id.** Ledger and ticket ids are always quoted with their title and a link.

## Cost model

Every orchestrator turn re-reads the whole session, so what costs money is turns and wake-ups, not words. The skill is built around that.

- **Cheap workers, expensive decisions.** A model tier per job, always passed explicitly: the fastest tier for verifiable gathering (counts, status sweeps, formatting), a mid tier for well-specified implementation, the strongest for design, root cause and risky changes. An omitted model inherits the orchestrator's, which is the expensive default. Each brief carries a tool-call budget. See [cost/budget.md](cost/budget.md).
- **Never wait on a suite.** An agent that idles past the 5-minute cache lifetime rewrites its whole context on its next turn. A full suite runs as a detached [`suite-run.ts`](#suite-runts) job: the agent exits with a findings note, a `suite-done` watch wakes the coordinating session when `results.json` lands, and a fresh reviewer starts from the diff and the results. Reviewers run targeted tests plus tsc only (the full-suite result comes from [`suite-summary.ts`](#suite-summaryts) run by a script, not from Opus looping on it), and re-reviews go to a mid tier.
- **Foreground waits inside agents.** A background completion wakes the orchestrator for a full-context turn. A blocking loop inside the agent costs one tool call and the orchestrator nothing.
- **Capped reports and lean tool output.** A report stays in context for the rest of the session and is re-read on every later turn, so detail goes in a file the orchestrator opens only if it needs it.
- **One loop, one wake per event.** The event loop, including its `pr-watch` type, costs no tokens between checks, and its adaptive pace (slower when quiet, off overnight) keeps polling from becoming wake-ups.
- **Session hygiene.** Per-turn cost climbs with session length. The status footer's Session line says "roll soon" at 60% and "roll now" at 90% of the autocompact trigger (the last turn's context over the live `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, else the native ~967k); `roll_turns` and `roll_read_per_turn` are retired. On "roll soon" the orchestrator finishes in-flight relays and starts no long new chains; on "roll now" it runs the roll itself, unasked (`journal.ts triage`, `roll`, then `handoff --all --delta`), and does not ask you to compact. Rolls are layerable: `journal.ts handoff --delta` writes a small suffixed handoff (`HANDOFF-<date>b-...`) holding only what changed since the previous one, and `resume` plus `prime` make a fresh session cheap to start.
- **Measured, not guessed.** `token-metrics.ts` reads transcripts for numbers only. An end-of-day loop compares the day with a 7-day median, flags any metric more than about 20% worse, and treats each cost habit as an experiment to adopt or revert. See [cost/loop.md](cost/loop.md).

## Testing

```bash
npm test
```

Each script has a test file beside it. The tests run every script as a subprocess against a temporary ledger or temporary directories, use stubs for `gh` and git hosts, and never read your own config file (each test file sets `MAESTRO_LOCAL_CONFIG=''`). Tests that touch time pass an explicit `now`. Run one file with `node --test scripts/<name>.test.ts`. `node --test` runs files in parallel but the tests inside a file one after another, so the few files with the most tests are split: their cases live in `scripts/<name>.cases.ts` and run through `scripts/<name>.shard-N.test.ts` (see `scripts/lib/shard.ts`), and a test fails if a cases file is missing a shard. To run one of those, run its shards, e.g. `node --test 'scripts/journal.shard-*.test.ts'`. `npm test` also points `NODE_COMPILE_CACHE` at a fresh temp directory and sets `GIT_ALLOW_PROTOCOL=file`, so spawned scripts start faster and a fixture's fake github.com origin cannot reach the network. Shared logic that `journal.ts` and `ledger-index.ts` must agree on (the fold, `isOpen`, the stream registry) lives in `scripts/lib/ledger-core.ts`: change it there, once. `ledger-index.ts` needs a Node build with `node:sqlite` and FTS5.

**Continuous-roll drills.** `scripts/drills/` holds model-free checks of the promise that a session after `/compact`, after `/clear` and on a cold start sees the same state. Each drill copies a fictional ledger and vault into a temporary directory, so your real ledger and vault are never opened, and runs the SessionStart hook (`scripts/hooks/session-start-compact.ts`) as the harness would. `cold-start-drill.ts` reduces the ledger to its live rows (open, blocked, queued and asked items and their briefs) and checks that the `startup` context still carries yesterday's priorities file, every open id, the asks and the how-to pointers. `equivalence-drill.ts` runs the hook for `compact`, `clear` and `startup` on the same state and checks that the three carry the same facts. A drill that fails names the missing fact and does not change the hook. Both run in `npm test` through `scripts/drills/drills.test.ts`, and each can be run alone with `node scripts/drills/<name>.ts`. The crash drill needs the session marker and recovery work and is a visible TODO until then. See [playbooks/roll-drills.md](playbooks/roll-drills.md).

**The cold-start gate.** `scripts/drills/real-state-gate.ts` is the measure for continuous roll: the check that says a new session on your real state loses nothing. It copies the project's Journal directory (and, from `--vault` or `vault_root`, the project's `CONTEXT.md`, library and priorities folders) into a temporary directory, computes the truth set from the ledger (every open in-flight, blocked, queued and asked item, plus the newest priorities file), runs the SessionStart hook there for `startup`, `compact` and `clear` in a temporary home, and fails when any source lacks a fact. It reports `MISSING <source>: <kind> <id>` by id only, never ledger text, and never writes the originals. Facts that depend on work still landing (the worktree or branch a recoverable row records, recent decisions) print as `PENDING` and do not fail it until they are moved into the required set. Run it with `node scripts/drills/real-state-gate.ts --project <name>`; `--emit-context <file>` also saves the startup context for the agent eval in [playbooks/cold-start-eval.md](playbooks/cold-start-eval.md), where a fresh model answers eight questions from that context alone and a separate grader scores them. The `cold-start-gate` event type runs the gate every seven days and raises one alert when it fails (see [playbooks/event-types/cold-start-gate.md](playbooks/event-types/cold-start-gate.md)).

## Contributing

- **Keep it generic.** No organisation, personal path, ticket key or private name in anything shipped here. Install-specific values go through `local-config.ts`; org rules go in an overlay.
- **Keep it dependency-free.** Scripts use only `node:` built-ins and read their settings through `scripts/local-config.ts`.
- **A new event type** is `scripts/event-types/<type>.ts`, a playbook at `playbooks/event-types/<type>.md`, one line in `scripts/event-types/index.ts`, and tests with fixtures and no network. The suite fails if a type has no playbook.
- **A guarantee needs a runtime check.** If a rule can be enforced by a script, enforce it and test the refusal; do not rely on prose.
- **Tests land with the code they cover**, in the same commit, and the full suite passes before a PR opens.
- **Docs move with behaviour.** Change `SKILL.md`, the matching `reference/*.md` and this README in the same branch.
- **Small, reviewable PRs.** The size budget this repo ships applies to its own PRs: roughly five code files and four hundred code lines, mechanical changes in their own commit, conventional commit messages, and PRs opened as drafts.
- **What to share.** This folder is the shareable unit: `SKILL.md`, `reference/`, `cost/`, `playbooks/`, `scripts/` with their tests, and this README. Do not commit your own `Journal/`, tickets or run-time state files (`prs-snapshot.json`); those live under your ledger root.

### Loading the board automatically

`journal.ts prime` prints a short board built from the ledger, plus one update line when the skill's own checkout is out of date (that part runs `git fetch`, capped at 15 seconds and never prompting for a password, so give the hook a timeout above that, and skipped by `--no-update-check`), so it can run from a Claude Code `SessionStart` hook and its output becomes session context. Add this to your own settings file; nothing in this repo does it for you.

```json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume|clear|compact",
        "hooks": [
          { "type": "command", "command": "node /path/to/the-maestro/scripts/journal.ts prime --project <container-folder-name> --vault <ledger-root>" }
        ]
      }
    ]
  }
}
```

To get the post-compact checklist, give `prime` the hook's source: use one entry per source, each with `--source` (`startup` and `compact` print the checklist; `resume` and `clear` keep their context and get none). The flag is read from the command line, not from the hook's input, so a session that runs `journal.ts prime --source compact` by hand after a compaction gets it too.

```json
{ "matcher": "compact", "hooks": [{ "type": "command", "command": "node /path/to/the-maestro/scripts/journal.ts prime --source compact --project <container-folder-name> --vault <ledger-root>" }] }
```

### Text alerts

`scripts/lib/alert-policy.ts` decides when the loop texts you through `notify_command`, and the supervisor runs it on every chunk of its wait between launches, right after it writes its own heartbeat (right after the loop exits the newest heartbeat is the dead child's, which would read as DOWN). The same alert tick also runs on the supervisor's watchdog timer while the loop is up, so a pull-request event is still texted while the loop is up. A stall or a down loop is not. An allowlisted event (changes requested, conflict, approved-unmerged, reminder, notion change, a human thread or reply) is texted only when no session has seen it for 10 minutes. Loop health is not texted. DOWN, STALLED, recovered, a restart burst and a check that keeps failing are self-healing infra; the session already shows them on the footer Loop line and at session start. A normal start, and a normal restart after a digest, send nothing. At most one text goes out per 20 minutes, batched into one line (a send that fails still counts as an attempt, and the retry waits 20, 40, 80, then 160 minutes); nothing is sent from 23:00 to 07:00 (what is still unseen then goes out as one line after). The line is built only from an event's kind, repo and PR number, so no title, comment, org name or Notion text can reach the notifier; a test feeds a sentinel string through the inbox and asserts it never appears in the notifier's argv. State is `Events/alerts.json`.

Tests that spawn the supervisor or the event loop build their environment with `scripts/lib/test-env.ts` (a temp HOME, no user config, a temp event directory, and a notify command that only records its calls), never from the real environment, so a test run cannot send a text; `scripts/lib/test-env.test.ts` fails if a spawned script could resolve a real notify command.

### Event hooks

`scripts/hooks/event-inject.ts` is a SessionStart and UserPromptSubmit hook that shows the orchestrator the actionable events no session has seen yet. It reads only local files, fails open (any error prints nothing and exits 0), prints at most 8 headlines built from each event's allowlisted `kind` and `fields` (never a summary), then one `Loop:` health line when it says something worth seeing, and marks those events `seen`, not `handled`. It also prints a `Waiter:` line when a loop holds the lock but this window has no live waiter (see below). `node scripts/hooks/install-hooks.ts` only prints the `hooks` entries; you merge them into your own settings file, and there is no Stop hook.

#### Waiter registry (is anyone listening?)

A session hears the loop only through a background `events wait` or `digest-wait`, and a roll, a compaction or a closed terminal kills that waiter without a word. While either command waits it writes `<event_dir>/waiters/<pid>.json` (pid, window id, start time; no event text) and removes it on exit or on SIGTERM, SIGINT and SIGHUP. A record whose pid is gone is deleted when read, so a waiter that was killed hard never reads as armed. On SessionStart and every UserPromptSubmit, when a loop holds the lock and the window has no live waiter, the hook prints `Waiter: none armed for this session ...` with the exact command to start with `run_in_background`; once a waiter is armed the line stops. The window id is the one the rest of the ledger uses (`CLAUDE_CODE_SESSION_ID`, then `CLAUDE_PID`), so a window with no stable id would see the line every time. The registry is `lib/waiters.ts`.

#### Session launcher (nobody is listening)

When an actionable event has sat unseen for 3 minutes, no waiter is live, and no interactive transcript in `projects_dir` was written in the last 15 minutes, the loop supervisor can start a session by running `wake_launch_command` (an argv; the fixed prompt `the-maestro wake: run session-start, read the unseen digests, then follow the adopted queue.` is appended as its last argument). Launching is off until an install sets the key. At most 4 launches a day, 30 minutes apart; a failed launch counts. With no launch command but a `notify_command`, one fixed line (no event text) goes out instead, at most 4 a day and 30 minutes apart, and only when no pending event is a kind the text alerts already send, so those still get exactly one text; with neither, nothing happens. No event text, watch name or path ever reaches the command, and each launch or fallback text is logged as a row of time, action, reason and whether it worked in `<event_dir>/wake-launch.jsonl` (ticks that decide to do nothing are not logged).

On macOS, `wake_launch_command: ["node", "/path/to/the-maestro/scripts/wake-terminal.ts"]` opens a new Terminal window running `claude "<prompt>"` in the container root. It runs in your normal settings and permission mode, and `wake-terminal.ts` refuses every permission flag and any option it does not know.

On SessionStart only, the hook also prints the adoption block after the events and the loop line: `Adopted queue: <path> (until <time>). Read it and work it now.` when a live adopt record exists, the live wake schedule (one line per unexpired `wake` watch: id, target, prompt), and, only when the loop is not running, one `CronCreate` call per wake so a session can mirror the schedule until the loop is back. Prompts and paths are secret-scanned and withheld when they match. A broken record or registry prints nothing extra and never blocks the start.

### Rolling continuously

A compaction can happen at any moment, so three hooks make it lossless instead of relying on a manual roll. Neither calls a model, and neither is installed for you: `node scripts/hooks/print-settings-snippet.ts [--project <name>] [--vault <ledger-root>]` only prints the `hooks` entries, and you merge them into your own settings file.

- **PreCompact** (`scripts/hooks/precompact.ts`, matcher `auto|manual`) first appends a `note` row `precompact started`, so a hook the harness kills still leaves a trace. It then writes its own handoff, `Journal/HANDOFF-<date>-precompact-<window>.md` (named for the window, so two windows compacting the same day each keep their own; rewritten by that window on each run, no worktree sweep, 45 second cap, so compactions never use up the day's `b..z` suffixes); copies dirty and untracked source of active worktrees (dirty files touched within 72 hours, under the container's `.worktrees`) to `<scripts_dir>/scratch/snapshots/<date>/` (stops scanning at 80 seconds; a `.gitignore` of `*` is written beside the dated folders); and reads the transcript the hook is given (`transcript_path`) for messages that look like decisions. The whole transcript is scanned every run, and a message that looks like a decision counts as handled only when its own `[msg <timestamp> <hash>]` marker is already on a ledger row (the ask an earlier run raised). Nothing else hides it: not a row written near it in time, not an unrelated or resolved ask, and not a rule or decision row that resembles it (a recorded decision would hide its own reversal), because every such rule eventually hid a real decision, so the hook is deliberately noisy rather than lossy. Each ask ends by saying how to answer it: `journal.ts decide ... --msg "<the message's marker>"` for every real decision not already recorded (so it lands in DECISIONS.md or memory, not only the ledger, and the marker on its row stops the scan raising that message again), then `resolve` the ask. Every unhandled message is raised in the same run, 20 messages per `ask` row (so a long session costs a few rows, not a remainder that a `/clear` could strand); no other session's compaction can hide one. The snapshot is an allowlist: regular files only, never a symlink, and only source and docs by extension plus a few named config files; secret-named files, files over 1 MB and files or messages that match a secret or PHI shape are skipped or withheld. It always exits 0, so a failure cannot block compaction; it ends with a `note` row starting `precompact incomplete` naming the failed steps (including a snapshot that hit its 300-file or 20 MB cap or its time budget), or `precompact` on success. The started and result rows carry the same `session <id>` tag, so one session's result never hides another's killed run.
- **Thrash guard** (in PreCompact, `thrash` in `scripts/lib/continuous-roll.ts`): the hook reads the `compact_boundary` rows of the transcript it already reads (timestamp, `preTokens`, `postTokens`, nothing else). When this compaction comes under 10 minutes after the previous one, or with under 20k tokens of context growth since it, the hook appends a `compaction thrash` note naming the session, the count, the growth and the current setting against the floor, and `prime` prints one `!!` line for it until a later `precompact ack`. It never blocks and never skips a step: a guard that skipped the handoff could lose state, and the harness cannot be stopped from compacting. The prefix is deliberately not `precompact`, so the row is never mistaken for a hook result.
- **Snapshot resumes** (`snapshotDirty`): with hundreds of worktrees one `git status` each does not fit the tick's budget, so the walk keeps a cursor (`.snapshot-cursor`, beside the dated folders) and the next run resumes after the last worktree it read; the cursor clears when a walk finishes. A tick cut off by its deadline after reading some worktrees is progress, not an alert; one that read none still alerts. The hook runs once before a compaction, so for it a cut-off walk is still an incomplete step.
- **Watch check** (`continuity-watch.ts`): the hook also verifies that the `continuity` watch is registered and unexpired and that the event loop is alive (not stalled, down or absent). If not, the marker row is `precompact incomplete: continuity watch: <one line with the fix>` (the register command, or a note that the loop is not alive), and prime prints it as a `!!` line. The other steps still run, and the hook still exits 0. A later clean compaction in the same session, or an ack, clears it.
- **Repair alarm** (`continuityLines`): when PreCompact had to rewrite a handoff that was more than 10 minutes behind the ledger (two tick intervals), its marker starts `precompact: repaired` instead of `precompact:`, and prime prints a `!!` line asking whether the `continuity` watch is registered and the loop alive. It stays until an ack or a later compaction that needed no repair. A small lag, or a missing handoff, raises nothing.
- **SessionEnd** (`scripts/hooks/session-end-decisions.ts`, matcher `clear|resume|logout|prompt_input_exit|other`, timeout 30 seconds in the snippet because SessionEnd hooks otherwise get 1.5) runs only the decision scan, because PreCompact does not fire on `/clear` or when a session ends and the decisions typed since the last compaction would never be read. No handoff, no snapshot, no started row; a failure leaves a `precompact incomplete: decisions: ...` row tagged with the session, which `prime` reports until a later success or an ack.
- **SessionEnd requeue** (`scripts/hooks/session-end-requeue.ts`, a second SessionEnd entry with the same matcher, timeout 10 seconds): the in-flight rows the ending window holds a live lease on go back to queued and the leases are released, so another window can take them at once.
- **Leases and requeue**: `start` always takes a lease. An in-flight row whose lease lapsed with no agent still out is put back to queued by `status` (the footer heartbeat) and by `maintain`, with a `queue` row saying why. A row that was never leased is left to the stale warning. A marked `lease` row (`agent: true`) is an agent out until a matching return row, so a long agent run is not requeued under it.
- **Agent hooks** (`scripts/hooks/agent-dispatch.ts`, a `PreToolUse` hook with matcher `Agent`; `scripts/hooks/agent-return.ts`, a `SubagentStop` hook, each timeout 10 seconds): a dispatch finds the in-flight row this window already leases (its id in the prompt, or the description in its text) or opens one, marks the lease agent-out and records the next step. When the dispatch opens the row it also saves the prompt under `<ledger>/Projects/<project>/Journal/Briefs/` and links it with a `brief` row (see `start --brief`), so a cut agent can be re-dispatched from the file; a prompt that looks like it holds a secret is not saved, and the row is still opened. Decision (2026-10-15): the hook creates the row rather than blocking the dispatch, because a block makes agents the thing that gets skipped, and it tracks the orchestrator session only: a call a subagent makes itself carries `agent_id` and is ignored. These hooks only exist in `settings.json` once you merge `print-settings-snippet.ts` into it, and the footer's `ledger drift` line says when agents run without them. A stop marks the oldest open dispatch of that window and agent type "returned, verify" and shortens the lease to 60 minutes, so a hand-back nobody checks lapses and requeues. The hook never closes a row: verifying the work is the dispatcher's job. A stop is paired with its dispatch by the Agent call's tool-use id when it names the subagent's transcript (the harness writes the id into the subagent's `.meta.json`), else by window and agent type, oldest first. With two agents out on one row the first stop only records itself; the last one marks the row. The footer counts a row marked "returned, verify" as `N to verify`, apart from `N in flight`, so it moves when an agent finishes; a new dispatch on the row puts it back in flight, and verifying and closing it stays the dispatcher's job. Both read and append the ledger directly (no spawned process, about 90 ms against a 2 MB ledger), print nothing to stdout and fail open: an error is one stderr line and the call proceeds.
- **Autocompact check** (`scripts/lib/autocompact.ts`): reads the live `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` and `CLAUDE_CODE_AUTO_COMPACT_WINDOW` (the process environment first, then the settings file's `env` block, only those two keys) and works out the trigger in tokens. A trigger below `autocompact_floor` is a warning, never a write: the SessionStart hook puts it first in its context as `== Autocompact ==`, and `print-settings-snippet.ts` prints the current setting, any warning and a note on 200k-window models to stderr. That command now prints one snippet holding the roll hooks, the git guard, the lease and agent hooks and the two event-inject entries; `--autocompact-pct N` adds the `env` entry and is refused (exit 2, nothing on stdout) when N is under the floor. The command prints only; you paste the result into your own settings file.
- **SessionStart** (`scripts/hooks/session-start-compact.ts`, matcher `startup|resume|compact|clear`) prints `prime --source <source>` and the cold-start page for every start reason, capped at about 5k tokens (`start-here` prints only as the fallback when the cold-start part failed or was skipped; a part that fails or is missing is named and skipped; any line the secret scan flags, including an over-long one, is replaced by `[withheld: secret shape]` before the cap, so a secret-shaped stream name or id never becomes session context). This one entry now covers every start reason, so remove a separate plain `prime` SessionStart entry when pasting the snippet or the board prints twice. Every hook here is an optional, fail-open fallback: the state they print is on disk and a session that never ran them reads the same thing with the commands below.
- **Cold-start page** (`scripts/cold-start.ts`, `scripts/lib/cold-start.ts`): `cold-start.ts generate` prints, from the ledger and the library alone, current work per stream (in flight with its brief and report path, blocked, queued, the last note), decisions pending (open asks with their door and recommendation), decisions recorded (up to 8 decision rows that name a file, such as `decide` writes, dated since the previous working day, each with its file link; absent when there are none and dropped with How to work when the page shrinks) a Projects section (for each project of an active stream, at most 5: the first lines of its CONTEXT.md `## Now` and `## Next`, and pointers to its newest two priorities files with the carry count; a missing section or file is said, not skipped) and the current library pages per active stream, at most 12,000 characters. It is built at read time, so it cannot be stale. When it has to shrink it shortens wording in steps, then drops the How to work and Decisions recorded sections, then the Projects Now and Next text (the priorities pointers stay), and never drops an in-flight, blocked or ask id; every text and path goes through the library secret scan and is replaced by `[withheld: secret shape]` on a hit. `cold-start.ts check --ledger <ledger.jsonl> [--library <vault>]` is the cold-start test: no transcript, it builds the page, takes the current-work statement and exits 1 when an open item is not in it, the page was cut, a secret shape is on it or the page is over `--budget <tokens>` (default 10000, characters / 4; `generate` honours it as a cap). `check` also fails for each active stream (something open) that has no carry-over, meaning no priorities file dated the previous working day or later (Friday on a Monday) in one of its projects, or no current library page. Expect it to fail on a vault until the library covers every active stream and the roll carry-over has run for a day. When a cap cuts whole lines, the closing line names the open ids it can and counts the rest (`… and K more open ids not named`).
- **`prime`** prints its checks first, outside its 40-line board, to stdout and stderr (exit stays 0, because a failing SessionStart hook can drop its output): a `precompact started` row with no result row of its own session after it (a newer handoff does not clear it, because the hook writes its handoff before the snapshot and the decision scan), the latest `precompact incomplete` row, and `HANDOFF STALE` when the newest handoff predates the last ledger row written before the compaction began. A newer handoff clears a handoff-failure alarm; any alarm is dismissed with `journal.ts log "precompact ack" --kind note --model <name> --used tool:journal.ts`, which is the only way to clear a snapshot or decisions failure.

Not covered: a session that crashes or is killed (no SessionEnd fires) after decisions typed since its last compaction; a decision nobody typed (the hook only reads what you wrote); a message the decision pattern does not match; a transcript file that lags the conversation (the docs say it is written asynchronously), and worktrees outside the container's `.worktrees`.

### Git guard hook

Rules that only live in a prompt get forgotten under pressure, so `scripts/hooks/git-guard.ts` makes the git ones a runtime check. It is a `PreToolUse` hook on the `Bash` tool, printed by `print-settings-snippet.ts` with the other hooks (you merge it into your settings yourself). It stays out of the way in your own repos: when the repository's `origin` is under `github.com/jackreichert/` (following `-C` and `cd` to the repo the command runs in) it allows silently, and it stays active in every other repo; a missing or unreadable `origin` keeps the guard on. It answers ask, not deny: the harness shows its normal permission prompt and you decide. The idea comes from the git guardrails skill in [mattpocock/skills](https://github.com/mattpocock/skills/tree/main/skills/misc/git-guardrails-claude-code); this version asks instead of blocking and reads compound commands.

It asks for a push to `main`, `staging` or `develop` (set `GIT_GUARD_PROTECTED` to a comma list to change them), any force push (`--force`, `--force-with-lease`, a `+refspec`), `reset`, `rebase`, `merge`, `cherry-pick`, `revert`, `add -A` and `add .`, `commit -a`, `branch -D`, `clean -f`, a `checkout`, `restore` or `switch` that discards work, and a commit while HEAD is a protected branch. `status`, `diff`, `log`, `show`, `fetch`, `ls-remote`, `rev-parse`, `blame`, a plain commit or push on a feature branch and `add` by explicit path pass silently. A push or commit with no explicit branch reads HEAD with `git symbolic-ref`; a HEAD it cannot read counts as protected.

Commands are split on `&&`, `||`, `;`, `|`, `&`, newlines, subshells, `$(...)` and backticks, and the guard looks inside `bash -c`, `eval`, wrappers such as `env`, `sudo` and `xargs`, `git -C dir`, `git -c alias.x=...` and the repo's own aliases, so a risky verb inside a chain is still seen. A push whose destination the shell builds (`HEAD:$BASE`, `git push origin $B`, a `$(...)` or `{}` placeholder) also asks, because it cannot be shown to avoid a protected branch. If the hook itself breaks (bad input, an internal error) it prints a note to stderr and allows, so a broken guard cannot brick a session. It is a net for honest mistakes, not a sandbox: a script or Makefile target that runs git on its own is not seen.

## What this is not

- Not a project manager and not a ticket database. Problems that need fixing belong in xenophon or your issue tracker. The ledger is a record of activity.
- Not safe to run two dispatcher sessions that both `start` and `done` the same ledger without looking. The log is append-only and last write wins on the generated markdown.
- Not a license to write `main`, `staging`, `develop`, or a branch you did not author. Those stay protected, and pull requests open as drafts.
